# v0.15.0 — Release Criteria

Status: **Accepted — 2026-08-28** (the v0.15 scoping session; CEO-ratified on the Commander
recommendation after a pre-authoring audit that reversed the brief's premise twice). Acceptance of
this document fixes the release intent; thereafter changes require a new ADR (the v0.1.0–v0.14.0
rule).

The architecture ADR it depends on — **ADR-0074 (governed decision policy)** — is **Accepted
2026-08-28**, authored alongside this document at T-147 and accepted the same day. ✅ **The ladder is
unblocked; T-148 is the next ticket.** Its Accept-time provenance check resolved one `[inherited:]`
marker by deleting the claim it sat on — zero unresolved markers remain.

Owner: War Room Commander (synthesis); Backend Architect (the rule store, the evaluator, precedence);
Security Reviewer (§5 negative proofs, the fail-closed path, the wildcard blast radius); UX Reviewer
**for §7 only** — a rule surface that hides a rule's blast radius produces an operator who denies
their own product and does not know why.

Every criterion is *pass* (must be true), *block* (presence stops release), or *deferred* (explicitly
out of scope, with the trigger that promotes it back). A ticket is "done" when it closes one or more
criteria here and breaks none.

**No new criteria family is minted.** Rules extend `SEC`/`AUD`/`CON`; the evaluator extends `PERF`;
verification extends `VER`. Minting a family per release is the habit structural rule #2 exists
against.

## 1. Scope of v0.15.0 — and why this release exists at all

**The ratified path did not contain a v0.15.** `epic_story_catalog_v4.md` §Part 4 went
v0.14.0 → v1.0.0, and `backlog_v4.csv` had no row targeted at a v0.15 [read, 2026-08-28]. Inserting
one was the first decision of the scoping session, and it is justified on one argument rather than on
habit:

> **The boundary rule makes this work impossible to do later.** *"A freeze-track release may close an
> evidence gap on an existing governed mutation; it may not add a governed mutation"*
> [read: `docs/requirements/epic_story_catalog_v4.md:286-296`]. v1.0.0 is bound by it. A
> decision-plane change therefore **cannot land in v1.0.0**. It lands before v1.0.0, or the OpenAPI
> surface freezes over a policy plane that cannot deny.

This is the **S-28 precedent, applied again**: *"S-28 adds signature and key-id material to audit
responses, so freezing first would have frozen a surface we were about to change."* The same
reasoning that produced the v0.13.0/v1.0.0 split produces this release.

### The diagnosis this release answers

The product has a deep governance spine and a decision point that has never made a decision.
ADR-0074 §Context carries the measured detail; the three load-bearing facts:

1. **`policy-service` has no rules table and cannot return `deny`**
   [read: `services/policy-service/migrations/0001_policy.up.sql:24,48`;
   `internal/store/store.go:32-38`].
2. **Approval granularity is the resource, not the action** [read: `catalog.go:1246`] — so an
   unflagged host runs `remote.exec` ungoverned, and a flagged host gates `remote.file.list` as hard
   as an arbitrary command. **v0.14.0 created this pressure by shipping typed tools onto a plane that
   cannot tell them apart.**
3. **Every egress tool tells the model *"The call is policy-checked"*** [read:
   `catalog.go:130,213,321,478`] and no policy is checked.

### Hard constraints (the release's defining posture)

- **No new third-party dependency.** `task go-deps-check` stays green at 10 across 13 modules. This
  is what rules out CEL and every other expression runtime (ADR-0074 §Held in reserve).
- **No new daemon, edge, key, or runtime.** The service, the outbox, the audit chain and the tool
  catalog are all reused unchanged.
- **Additive and backward-compatible.** An empty `policy_rules` table must reproduce v0.14.0
  semantics **exactly** — proven, not assumed (CON-1).
- **Arguments stay out.** ADR-0074 §D5. The invocation row persists one F3-encrypted field with no
  args column [read: `catalog.go:181-188`]; a predicate over paths or commands needs a migration and
  an encryption-scope ruling, and gets neither here.
- Diff budget ≤12 files / ≤500 LoC per ticket; every UI change needs browser-rendered evidence.

## 2. The gate — **WD-15** (structural rule #2, and a numbering ruling)

A new WD-N is minted only when a release adds new **governed capability semantics**. A
machine-evaluated `deny` at the trust boundary — an outcome no human authorised in the moment — is
new governed capability. **This release earns a WD.**

⚠ **Numbering ruling (new, and it must not be re-derived later).** WD-1..11 are built; **WD-12 is
reserved to containment (B-040), WD-13 to v1.0.0, WD-14 to v1.1**
[read: `epic_story_catalog_v4.md:192,193,236,246`; `CLAUDE.md:56`]. Renumbering to keep the ladder
release-ordered would break criteria references across fourteen releases — the same class of mistake
as the "layer 6" near-miss that pass 3 avoided. **v0.15.0 therefore takes WD-15, and the WD ladder is
hereby allocation-ordered, not release-ordered.** Do not renumber; do not read a gap as an error.

**Gate = WD-1..11 regression on both stacks + WD-15 + smoke + a CEO §human pass.**

| ID | Criterion | Type |
|---|---|---|
| **VER-29** | WD-1..11 green on compose **and** the installed stack. The installed run rebuilds the offline bundle **and** the postgres companion from HEAD first (the standing T-033 + companion-staleness lesson). | pass |
| **VER-30** | **WD-15** — a rule-denied invocation produces **no connector lease and no broker egress**, and the denial is on the chain positively. Both halves required: absence alone is not the proof. | pass |
| **VER-31** | `task smoke` green, extended with at least one rule-evaluation leg. | pass |
| **VER-32** | CEO §human pass: author a rule, watch it deny, watch a more-specific `allow` **fail to rescue** a wildcard `deny` (ADR-0074 §D2), then delete the rule and watch the fallback restore v0.14.0 behaviour. | pass |

⚠ **If any of §5's negative proofs cannot be made to fail correctly, this release does not ship.** A
guard that has never been observed failing is not a guard (VER-16, generalised).

## 4. The evaluator (must-pass) — `CON`, `PERF`

| ID | Criterion | Type |
|---|---|---|
| **CON-3** | **Severity beats specificity**: `deny` > `requires_approval` > `allow`, and a wildcard `deny` beats a fully-specific `allow` (ADR-0074 §D2). Tested with that exact pair — the case an operator will hit. | block |
| **CON-4** | No matching rule falls back to the resource's `requires_approval` label (§D3). | pass |
| **AUD-41** | ⚠ **OPEN, Commander review of T-151c — the rule-authorship event puts the RULE's edge in `Edge`, which is a FILTERED field.** `ruleEvent` sets `Edge: r.Edge` [read: `services/policy-service/internal/store/rules.go:93-97`], i.e. the edge the rule *governs*. But `Edge` means, everywhere else, **the capability edge the action traversed** — and an operator authoring a rule traverses `human-agent`, not `agent-remote-session`. **The audit read surface filters on Actor, Outcome and Edge** (not Target) [read: `services/audit-service/internal/store/store.go:200-209`], so an operator filtering by `edge=agent-remote-session` to review egress activity now also gets rule-authorship events back. ⭐ **This is the third instance of one pattern this release has already recorded twice** — `tool.result:error` conflating an operator denial with a crash, and `policy_unavailable` conflating a denial with an outage. Each time, a field was overloaded so two different things look alike. **Not a defect** — nothing is missing or wrong, and the `Outcome` (`policy.rule:*`) does disambiguate. **Recommended fix (~2 lines): `Edge` = `human-agent` (the traversed edge), and the rule's own edge moves into the `Target` composite, which is UNFILTERED and already carries the rest of the tuple.** That keeps one meaning per field and the filter honest. Costs a verification cycle, hence a CEO call rather than a unilateral change. | pass |
| **AUD-40** | ⭐⭐ **RULE AUTHORSHIP MUST BE CHAINED — the hole this release left in its own evidence claim.** [ran: sweep for outbox writes across the rule CRUD path, 2026-08-28, control fired on a planted `Enqueue`] — **nothing is emitted.** Neither the T-148 store nor the T-151a handlers chain anything. So an operator can create a wildcard `allow`, act under it, and delete it, leaving the ledger showing one legitimate-looking `policy.decision:allow` with **no trace the rule ever existed** — an outsider verifying offline sees nothing wrong. This contradicts **ADR-0073 §1** (consequential actions on the one signed ledger, verifiable offline — authoring a rule changes what the system will allow or deny) and **ADR-0012** ("every important action is an event", Accepted since the baseline). ⚠ **It is a hole in these criteria, not just the code:** AUD-35..39 cover decisions, denials, the verifier, session reasons and volume, and **not one covers rule authorship** — the release's central new mutation was the only one left unaudited. Five operations chained transactionally (create / enable / disable / delete, plus the actor), landing at **T-151c**. | block |
| **AUD-39** | ⭐ **T-150 changes what the operator's DEFAULT audit view contains, and that must be stated rather than discovered.** `governed-actions@1` is an **exclusion** list holding exactly `{plan.requested, plan.expired}` [read: `services/audit-service/internal/store/preset.go:21-24`], so a new `policy.decision:allow` lands **inside** the default lens automatically — one extra event per governed egress invocation, where today an allow emits nothing. **This is correct** (ADR-0054 §3 and ADR-0074 §D4 both require every decision to be chained, and a policy decision *is* a governed action), but it is a legibility change to the very surface E-01 was built to fix — the v0.11 measurement was *"635 events, 601 (95%) ticker noise."* ⚠ **Excluding it later is NOT a config knob**: `preset.go:8-9` states that widening the excluded set is a criteria change requiring **a new ADR (AUD-28)**. So T-150 ships it in-lens, **reports the measured per-invocation event delta as a number**, and DOC-14 states the change. The number is what the v1.0.0 audit-surface review needs; an impression is not. | pass |
| **PERF-10** | ⚠ **`decideHandler` now touches Postgres on EVERY decision, including allows that previously touched nothing.** Pre-T-150 an unflagged resource returned `allow` with no store access at all; post-T-150 every call does an `EvaluateTuple` query plus a `RecordDecision` transaction. Two consequences to state rather than discover: **(1) availability** — if policy's database is unavailable, every decision now fails closed (500) where unflagged allows previously succeeded. That is the correct direction and both callers refuse a 500 safely, but it is a real reduction in the decide path's independence, and it is *implied* by AUD-35: you cannot chain a decision without a database. **(2) latency** — the hot path gains a query and a transaction, which is what PERF-9's measurement is for. Neither is a defect; both belong in the release notes rather than being found by an operator. | pass |
| **OI-38** | ⭐ **`POLICY_URL` becomes MANDATORY in `services/api` — fail fast at boot** (CEO ruling 2026-08-28). `server.New` silently tolerates an empty value (`if policyURL != "" { … }` [read: `services/api/internal/server/server.go:429-433`]), leaving `h.policy == nil`. Today that is survivable because nil only matters for flagged resources; **after CON-6 a nil policy means no session can ever be created**, which would surface as a mysterious runtime failure instead of a boot error. **Nothing currently omits it** — e2e sets it, smoke and review inherit it via compose `include`, the offline installer sets it, and `docker-compose.mvp.yml` runs postgres only — so this is **hardening, not a fix**. Also document `POLICY_URL` in `infra/docker-compose/env.example`, where it is currently absent. | pass |
| **AUD-38** | ⭐ **A policy-DENIED session must not be recorded as a policy OUTAGE.** `createWithApproval`'s deny branch calls `failClosed`, which hardcodes `session.ReasonPolicyUnavailable` [read: `services/api/internal/server/server.go:1060-1064`] — so a denied session would close with `closedReason: "policy_unavailable"`. **The policy was available; it said no.** In a product whose claim is that the record is trustworthy, a refusal recorded as an outage is the wrong kind of wrong, and it is exactly the misleading-evidence class this release exists to fix. **Unreachable today and silently reachable the moment T-150 wires the evaluator** — the recurring "caller never updated" trap. Fix: add `ReasonPolicyDenied = "policy_denied"` beside the existing reasons in `services/api/internal/session/session.go:44-50` and give `failClosed` a reason parameter. **No migration** — `closed_reason` is free TEXT with no CHECK [read: `services/api/migrations/0002_sessions.up.sql:17`]. **Do NOT reuse `ReasonApprovalDenied`**: that is the *operator* resolve-deny path, and conflating a machine deny with a human one repeats the `tool.result:error` mistake recorded above. ⚠ **This was the Commander's underspecified brief, not an implementer error** — T-149b's brief said "failClosed + 403" and never named the reason. | block |
| **CON-6** | ⭐ **`services/api` consults the decision point on EVERY session-start, not only for `requires_approval`-labelled resources** — **CEO ruling 2026-08-28, option (a)**. Today it short-circuits: `if res.Labels["requires_approval"] != "true"` creates the session and returns without ever calling policy [read: `services/api/internal/server/server.go:993-1005`], so a rule targeting `session.start` on an unflagged resource would **silently never fire**. An operator would write it, see it saved and enabled, and get nothing. That is not a coverage gap, it is a **misleading control**. Landed at **T-150b**; CON-1 still holds because an empty rule table falls back to the label and reproduces v0.14.0 exactly. | block |
| **PERF-9** | Evaluation adds no unbounded work to the invocation path: rule matching is bounded and indexed, and the decide call's latency is measured and recorded, not assumed. ⭐ **SCOPE RULING (CEO 2026-08-28): this is a RECORDED MEASUREMENT in the ADR-0052 §OI-c shape — measure it, write the number down — NOT shipped instrumentation.** There is no latency-instrumentation precedent in any service [ran: `grep -rn 'time.Since\|latency'` over `services/`, 2026-08-28 — three hits, none instrumentation], and building a metrics surface would be new scope and probably a new dependency, which `go-deps-check` would refuse by design. | pass |

## 5. Negative proofs and fail-closed (must-pass) — `SEC`

| ID | Criterion | Type |
|---|---|---|
| **SEC-55** | **A rule-denied invocation never reaches the broker.** No connector lease is issued, no SSH egress occurs. Mutation-proven: break the deny path, watch the egress happen, **and check which assertion fires** (VER-16 generalised; ops rule 5). | block |
| **SEC-56** | A policy-service outage on the decide call **fails closed**, not open. The existing behaviour is asserted rather than inherited — [read: `services/api/internal/server/server.go:1198-1199`] shows the *approval-resolve* path returns 502 and leaves the session parked; the *decide* path must be re-read and proven on its own. | block |
| **SEC-59** | ⚠ **OPEN — `store.CreateSession` is now an UNGOVERNED session-creation path with zero callers, still on the interface.** T-150b routed every session-start through `createGoverned`, leaving `CreateSession` dead from production code [ran: repo-wide sweep over `services/`, 0 non-test call sites, control fired on a planted call] — but it is still declared on the `Store` interface [read: `services/api/internal/server/server.go:89`] and implemented [read: `services/api/internal/store/sessions.go:29`]. **It inserts a session directly in `pending` — broker-attachable, with no policy consultation at all.** It is now the only remaining way to create a session that bypasses the decision point, it is well-named, and it sits on the interface looking like the obvious method to call. **A future handler that uses it silently reopens the exact CON-6 hole this release just closed.** Framing matters: this is a governance-bypass hazard, not dead-code tidiness — filed as the former so it is not deprioritised as the latter. Fix: remove it from the interface and the store, or rename it to announce the danger. Out of T-150b's ratified scope (it touches the interface and every fake); its own small ticket. | pass |
| **PERF-11** | **Every session-start now costs two DB writes and an HTTP round-trip** (park → decide → approve) where an unflagged start previously cost one insert. The companion to PERF-10 on api's side. ⭐ **Not purely a cost:** the always-park flow means there is **never a window in which a session is broker-attachable before policy has answered** — the old unflagged path created a `pending` (attachable) row immediately with no policy involved, so this is strictly safer as well as slower. Record the number alongside PERF-9's at the capstone. | pass |
| **SEC-58** | ⭐ **A policy `deny` is NEVER approvable by a human.** The gateway today carries only `PolicyAllow` [read: `services/mcp-gateway/internal/catalog/catalog.go:1517`] and parks every non-allow decision for approval [`catalog.go:1278,1301-1303`]; the wait loop then executes when the resolve flips the stored decision to `allow` [`catalog.go:1332-1341`]. **So a `deny` would become a prompt a human can click past — the exact inverse of ADR-0074 §D2.** A denied invocation must fail closed with no park, no approval path, no lease and no egress. ⭐ **And the DEFAULT branch matters more than the deny branch: any decision the gateway does not recognise must ALSO fail closed, never park.** Today the dispatch is `if decision == PolicyAllow` followed by an unconditional park, so an unrecognised value is human-approvable — which is how this hole exists at all. T-149b replaces it with an explicit switch (allow / requires_approval / deny / fail-closed default). **Proven in-process, not by e2e:** `PolicyDecider` is an interface and `BrokerExecer`/`BrokerFiler` are separate interfaces [read: `catalog.go:744-757`], so a stub policy returning `deny` plus a **spy broker that fails the test if it is ever called** demonstrates no-lease/no-egress directly. Mutation-proven at T-149b. | block |
| **SEC-57** | A rule cannot widen authority. A rule whose outcome is `allow` does **not** grant an agent a verb its grant or token scope withholds — grants and rules are both floors, never ceilings for each other. | block |

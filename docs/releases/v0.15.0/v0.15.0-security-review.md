## (f) ⚠ FINDING — SEC-57 ("a rule cannot widen authority") is `block`, and has **zero** dedicated tests

**SEC-57** reads: *"A rule cannot widen authority. A rule whose outcome is `allow` does not grant an
agent a verb its grant or token scope withholds — grants and rules are both floors, never ceilings for
each other."* It is marked `block` in criteria §5, alongside SEC-55/56/58, all of which carry named,
mutation-proven tests. **SEC-57 has none** [ran: `grep -rln "SEC-57" services/ tests/`, 2026-09-01 —
zero hits outside the criteria doc itself].

**Architectural reasoning for why it holds today** (`[read: ...]`, not `[assumed]`):

1. **Agent-token axis.** `Service.Invoke` runs the SEC-16 scope check (`capb.Scope.Resource` /
   `capb.Scope.Operations`) [read: `services/mcp-gateway/internal/catalog/catalog.go:881-901`]
   **before** `runGovernedStep` is ever called — a scope violation returns a `toolError` and the
   function returns; `runGovernedStep`, and therefore the policy evaluator, is never reached. A rule's
   `allow` outcome can only be observed once the token's own scope has already passed; it has no code
   path back to widen `capb.Scope`.
2. **Grant axis.** `Service.RunStep` [read: `catalog.go:1156-1184`] hardcodes
   `s.registry.Lookup(remoteExecTool)` — a delegated Run step has no tool-selection surface for a rule
   to interact with — and the delegating grant's resource/budget scope is validated at Run **launch**
   (ADR-0061's immutable-plan-template posture: the plan a grant authorizes is fixed before any step
   executes), not re-derived from a policy decision per step.
3. Both axes are therefore **independent floors evaluated in series**, the identical shape v0.14.0's
   SEC-52 review certified for the D7 authority narrowing ("two independent controls... not merely
   intended"). A policy rule only ever narrows (via `deny`/`requires_approval`) or skips a human
   confirmation (`allow`) on a call that already cleared its own axis's floor.

**This is a reasoned architectural verification, not a mutation-proven negative test** — it does not
satisfy VER-35's letter ("every negative proof in §5 observed failing on a mutation, with the firing
assertion named"). **Recommendation:** either a) accept this review's reasoning as sufficient given the
two floors are structurally disjoint from the evaluator's own code path, and record that explicitly in
the release notes, or b) file a small follow-up ticket that writes the missing test — e.g. a wildcard
`allow` rule for `agent-remote-session`/`remote.exec`/`*`, driven by an agent token scoped to a
*different* resource or with an empty (file-verb-excluding) operations list, asserting the call is still
refused by the SEC-16 gate. This is a **decision for the Commander**, not a call this ticket makes
unilaterally — §8 of this ticket's brief is explicit that findings are reported, not silently fixed
outside the ratified shape.

## Verdict

**No exploitable defect found in what T-147..T-153 changed.** The release adds a real decision point —
`deny` is reachable, chained, and fail-closed on every path that can reach it — on top of existing
governance primitives: same edge, same credential custody, same audit chain, no new daemon, datastore,
network path, or key (`go-deps-check` stays at 10 across 13 modules, unchanged).

**The one gap this review adds to the record (SEC-57) is a missing PROOF, not a missing PROPERTY** — the
architectural reasoning above is sound and independently re-derivable from the current source, but a
`block` criterion resting on reasoning instead of a named, mutation-observed assertion is exactly the
gap VER-35 exists to catch. It is flagged here rather than fixed, per this ticket's scope boundary.

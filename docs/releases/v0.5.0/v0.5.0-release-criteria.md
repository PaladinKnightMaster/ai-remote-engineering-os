# v0.5.0 — Release Criteria

Status: **Accepted — 2026-06-23** (War Room opening scoping consult + council review;
CEO sign-off). The single architecture ADR it depends on (**ADR-0061 — Governed
Runs**) is already **Accepted** (`ad24e53`); acceptance of *this* document fixes the
release intent. Future changes to this document require a new ADR (criteria drift is a
load-bearing decision — same rule as v0.1.0–v0.4.0).

Owner: War Room Commander (synthesis); Workstream Architect (Run lifecycle +
evidence packet + Run-vs-Workstream scope); Permission Model Reviewer (typed launch
edge + step bracket edge + subject-pin); MCP Gateway Reviewer (the split
governed-core refactor; default-deny); Audit/Evidence Reviewer (evidence packet +
chain integrity); Offline-Install Engineer (OI-12 — api migration, no new unit).

This document defines what shipping **v0.5.0 — "Governed Workstreams" (layer 1: the
Run engine)** means. Every criterion is *pass* (must be true), *block* (presence
stops release), or *deferred-to-v0.6+/P1* (explicitly out of scope, with the trigger
that promotes it back). The criteria are the exit gate for every v0.5.0 ticket: a
ticket is "done" when it closes one or more criteria here and breaks none.

---

## 1. Scope of v0.5.0

v0.5.0 is the **first consumer** of the agent surface built in v0.3.0 (the typed MCP
gateway) and hardened in v0.4.0 (per-workload keys). It builds the **Run engine** —
the execution layer beneath the chartered Workstream module: an operator authors an
**ordered, durable, governed, evidence-bound Run** of steps (each a `remote.exec` on
a resource), launches it once, and the engine drives the steps to completion
**through the existing governed invocation path** (policy → approval → connector
lease → broker exec → audit), one step at a time, fail-closed.

**Naming (ADR-0061).** The v0.5.0 entity is a **Run** — the `run` node of the
chartered Workstream lifecycle (objective → … → run → evidence-packet → done). The
full **Workstream** (long-lived objective, sources, rules, schedule, scoped memory,
owner) is the **P1 module that *creates* Runs**, and is **out of scope** here. The
roadmap nests: **v0.5 operator-driven Runs → v0.6 agent-driven Runs → P1 Workstreams
orchestrate Runs.**

**Why operator-initiated.** An agent-initiated Run would force an agent-delegation
identity model and a token-minting workload that would undo v0.4.0's isolation
(R-1), plus a multi-minute held agent connection (R-2). Operator-initiated dissolves
both: a human initiator with an existing auth model and a fully asynchronous operator
experience. Agent-driven Runs are v0.6 (the trigger to extract a standalone service).

**Hard constraint (preserved).** The gateway remains the **sole** governed-step
orchestrator (the broker `/v1/exec` is subject-pinned to `mcp-gateway` per ADR-0060
— `services/api` cannot drive egress). v0.5.0 adds **no new egress path, no new
credential custody, no new key, and no new token-minting workload**; the Run engine
is a service-service peer exactly like `api`.

Concretely, on top of the v0.4.0 spine, v0.5.0 delivers:

- **The Run engine in `services/api`**, behind a self-contained `internal/run`
  package (the v0.6 extraction seam): durable `runs` + `run_steps`, a crash-safe
  sequencer with a reclaimable single-driver claim, and the operator surface
  (compose, informed launch, per-step status, cancel).
- **One new gateway capability** — a **split, behavior-preserving** refactor that
  extracts the governed core (`runGovernedStep`) from the agent MCP wrapper, plus
  **one** subject-pinned internal route `POST /v1/steps` the engine drives per step
  (held-call, reusing the proven `waitForApproval`).
- **Run governance & audit** — informed launch (full-plan review) as a typed
  `human-agent` authorization; per-step approval with Run context; `run.*` lifecycle
  events + a `run:<id>` correlation namespace + a terminal **Evidence Packet**.

**Out of scope** (→ §14): the full Workstream module (objective/schedule/scoped
memory); agent-initiated Runs + delegation identity; plan-level blanket approval;
parallel / branching / retry DAG; cross-resource transactional plans; a gateway-side
exec worker; SSH pooling + full per-edge rate-limiting; persisted-command GC;
Memory/Context Index (P2); a full per-workload key registry + rotation/JWKS.

v0.5.0 adds **no new agent tool**: a Run is an ordered sequence of the existing
`remote.exec` invocation, driven by the operator's engine — the tool catalog is
unchanged.

The wedge is **one operator-authored multi-step Run driven to completion through the
unchanged governed chain — resumable, cancelable, fail-closed, and terminating in a
replayable evidence packet** (WD-5). Everything else exists to make that true and
verifiable.

## 2. WD-5 — the single load-bearing wedge (the demo)

**WD-5.** On a real (not mocked) stack, an operator composes and drives a multi-step
Run end-to-end. WD-5 comprises a **happy path** (1–3, 7) plus three independent
**recovery/negative scenarios** (4 abort, 5 cancel, 6 crash-resume) — each a separate
Run, not one impossible run:

1. **Compose + informed launch.** The operator composes an ordered plan (≥3 steps,
   mixing ungated and `requires_approval`-flagged resources), **reviews the full
   plan**, and launches it. Launch is a typed, audited `human-agent` authorization
   (CSRF-gated) — `run.launched` is chained (actor = operator, the plan's resource
   set).
2. **Sequential governed execution.** The engine drives the steps one at a time via
   `POST /v1/steps`. Each step opens an invocation and runs the **unchanged** chain
   (policy `Decide` → connector lease → broker exec); the launching operator is the
   actor; the step bracket edge is `human-agent → agent-remote-session`. An **ungated
   step runs** without prompting.
3. **Flagged step parks + informed approval.** A flagged step **parks** and surfaces
   on the existing `/invocations` console **with its Run context** ("step k of n" +
   the plan). Approve → the held `POST /v1/steps` call resumes, claims, and execs the
   step; the Run advances. The command is **sealed at rest** while parked.
4. **Fail-closed abort.** A **denied** (or failed/timed-out) step marks the Run
   `failed` and **dispatches no further steps** (`run.aborted`). No further egress.
5. **Operator cancel.** A separate leg: the operator **cancels** a running Run
   mid-flight (`run.canceled`); no further steps dispatch; an in-flight step
   finalizes per the running-orphan policy.
6. **Resume-with-skip (the hard case).** The engine is killed mid-Run and restarted;
   it reclaims the Run and **resumes at the first non-terminal step without
   re-executing** any completed step (deterministic idempotency, no double-exec).
7. **Evidence packet + replayable chain.** The terminal Run assembles an **evidence
   packet** (ordered steps + policy decisions + approvals + stdout-SHAs + outcomes);
   the full chain (`run.launched` → per-step `tool.invoked`/`policy.decision`/
   `approval.*`/`credential.leased`/`remote.exec`/`tool.result`, each carrying
   `run:<id>` → `run.completed`/`aborted`/`canceled`) is **hash-intact** and
   replayable via `audit-service verify`.

**This single demo is the release gate.** It is built as an extension of the
`tests/e2e` live harness and re-run on the installer-produced stack (`task wd1`).
The kill-mid-Run resume (6), the denied-abort (4), and cancel (5) are live, not
mocked.

## 3. Capability-edge security (must-pass)

Every boundary stays gated by `packages/go/middleware` `RequireCapability`. v0.5.0
adds the Run plane without weakening any v0.4.0 invariant.

| Edge | Caller → callee | Token / gate |
|---|---|---|
| `human-agent` (operator → api, **launch/cancel a Run**) | operator cookie + CSRF (ADR-0050) | v4 local (unchanged) |
| `service-service` (api Run engine → gateway `POST /v1/steps`) | api asymmetric private; gateway verifies w/ api public; **subject-pinned `subject=="api"`** | v4 public (ADR-0060) |
| `human-agent → agent-remote-session` (per-step bracket) | operator = actor; `policy.Decide` subject = operator | (the step's audited edge) |
| `service-service` (gateway → policy/connector/broker) | **unchanged** from v0.4.0 | v4 public / pinned |

- **SEC-23 (block) — typed launch authorization.** Launching (and canceling) a Run
  is a `human-agent` capability on `services/api` (operator gate + CSRF), audited
  (`run.launched` / `run.canceled`). No anonymous or agent-plane launch path exists
  at v0.5.0.
- **SEC-24 (block) — the step plane is subject-pinned.** The gateway `POST /v1/steps`
  route is on the existing service-service verifier and pins `subject == "api"` (the
  R5-ext discipline, mirroring the existing internal resolve/list plane). No other
  workload can drive a governed step.
- **SEC-25 (block) — no privilege escalation.** The Run engine holds **no** new key,
  **no** credential-secret, and **mints no agent/service token it did not already
  hold as `api`**. It drives egress only by asking the gateway (the sole
  orchestrator). A code path that lets the engine reach the broker/connector directly,
  or mint a foreign-edge token, is a release blocker.
- **SEC-20/21/17/18 (block, carried).** The v0.4.0 gateway invariants are preserved
  unchanged: gateway keyless of the symmetric cluster key (SEC-20); bounded blast
  radius (SEC-21); no decrypt path on the gateway (SEC-17); broker exec parity +
  subject-pin (SEC-18). The split refactor (RUN-2) must not regress any of them.

## 4. Run engine architecture (must-pass)

- **RUN-1 (block).** The engine lives in `services/api` as a self-contained
  `internal/run` package (sequencer + Run store + a clean gateway-client interface),
  the v0.6 extraction seam — `api`'s public signature and existing call sites are
  unchanged (additive wiring, the `WithGateway` precedent).
- **RUN-2 (block).** The gateway governed-core refactor is **behavior-preserving**:
  `runGovernedStep(initiator, resourceID, command, idempotencyKey, waitTimeout)` is
  extracted from `catalog.Service.Invoke` and the existing **agent `task e2e` stays
  green before** the new route is added. Default-deny for unknown tools and
  tool-telemetry-to-audit are preserved.
- **RUN-3 (block).** Exactly **one** new internal gateway route `POST /v1/steps`
  (service-service, subject-pinned `subject=="api"`, SEC-24) runs one governed step
  to terminal and returns its outcome + invocation id. It is **not** in the OpenAPI
  fragment (internal RPC, like broker exec / connector lease / the resolve plane).
- **RUN-4 (block).** The step call uses the **held-call** model — it reuses
  `waitForApproval` with a **caller-supplied extended timeout** (the Run approval
  window, ≫125s) so a slow approval does not fail the plan. `api` uses a **separate
  long-timeout client** for the step call (the existing 10s gateway client is
  unchanged for resolve/list).
- **RUN-5 (pass).** The launching operator is threaded as the step **initiator**
  (actor + `policy.Decide` subject); the gateway store's hardcoded agent actor / edge
  is generalized to carry the operator + the `human-agent → agent-remote-session`
  bracket edge.

## 5. Run governance & approval (must-pass)

- **GOV-1 (block) — informed launch.** Launching consents to the **unattended**
  execution of all ungated steps, so the operator reviews the **full plan** before
  launch (the launch-time analog of ADR-0059's informed approval). Verifiable as:
  (a) the compose UI presents every step (resources + commands) before the Launch
  action (FE-14, browser-evidenced), and (b) `run.launched` records the plan's
  **resource set + a content-free plan digest** — **never** the commands (ADR-0049
  content-free chain; commands stay in the operator-only `run_steps` store).
- **GOV-2 (block) — per-step approval, no theater, with plan context.** Ungated steps
  run; a flagged step **parks** and is approved on the existing `/invocations`
  surface **carrying its Run context** ("step k of n" + the plan) — informed
  approval, plan edition. The agent plane never sees the command (unchanged).
- **GOV-3 (pass) — self-approve preserved.** The launching operator approving a
  flagged step in their own plan is the existing ADR-0054 same-operator self-approve
  posture (segregation-of-duties stays deferred). Plan-level grant-with-preview is
  deferred (§14).

## 6. Durability, resume & lifecycle (must-pass)

- **DUR-1 (block).** `api` owns durable `runs` + `run_steps` (the latter carrying
  `resource_id`, `command`, `invocation_id`, `status`, terminal outcome). The
  operator command at rest follows the existing operator-command posture and is
  additionally sealed gateway-side once dispatched (F3, ADR-0059).
- **DUR-2 (block) — reclaimable single-driver claim.** The sequencer claims a Run
  (status-guarded single-winner) before driving it; the claim is **lease/
  staleness-based and reclaimable** — a crashed driver does not strand the Run; a
  restart or sweep reclaims a stale claim (the `ReapStale` pattern). Two drivers
  cannot double-drive one Run.
- **DUR-3 (block) — resume-with-skip, no double-exec.** On reclaim the sequencer
  resumes at the first non-terminal step. Each dispatch uses a deterministic
  idempotency key `run:<id>:step:<index>`, so a re-issued already-completed step
  dedups via the existing PERF-2 path and returns the original invocation — **never a
  second exec** of a side-effecting command (proven live, WD-5.6).
- **DUR-4 (block) — running-orphan is fail-closed.** A step crashed mid-exec (stuck
  `running`) marks the step and the Run `failed` for operator review, backed by a
  gateway reaper extension ageing stale `running` → `failed`. No silent re-exec, no
  stuck Run.
- **DUR-5 (block) — stop-on-failure + operator cancel.** A denied/failed/timed-out
  step marks the Run `failed` and dispatches no further steps. The operator can
  cancel a running Run mid-flight (typed, audited; `run.canceled`); no further steps
  dispatch. Cancel handles both in-flight sub-cases: a **parked** step is finalized
  (the gateway invocation is resolved terminal and the held `/v1/steps` call is
  released — no lingering row or connection); a **mid-exec** step applies the DUR-4
  running-orphan policy.
- **DUR-6 (pass) — non-atomicity is an explicit non-guarantee.** A Run is an *ordered
  governed pipeline, not a transaction*; fail-closed stops *further* egress but does
  not roll back already-applied steps. Stated in the operator UI and these criteria.

## 7. Audit & Evidence Packet (must-pass)

- **AUD-14 (block) — Run lifecycle events.** `api` chains `run.launched` (actor =
  operator, plan resource set), `run.completed`, `run.aborted`, `run.canceled` via
  its transactional outbox (ADR-0045). New event vocabulary; content-free ingest
  (ADR-0049) preserved.
- **AUD-15 (pass) — correlation + chain integrity.** Each step invocation keeps its
  by-design dual anchor (`invocation:<id>` gateway/broker, `session:<id>`
  policy/connector) and **additionally carries the parent `run:<id>`**; the Run record
  lists its ordered step/invocation ids. The single hash chain stays intact +
  replayable (`audit-service verify`).
- **EVD-1 (block) — Evidence Packet contract.** A terminal Run's evidence packet is
  **assembled at read time from existing durable state** — the `runs`/`run_steps`
  records (operator-only command store) + the linked chain anchors (per-step
  `policy.decision` / `approval.*` / `remote.exec` stdout-SHAs / `tool.result`, keyed
  by `run:<id>`) — **not** a new stored blob/table. Commands stay **operator-only and
  out of the chain** (ADR-0049/0059); the packet references them through the same
  operator-only read posture, never the agent plane. It is the replayable proof of the
  whole Run (the chartered "evidence-bound run"). The exact assembled shape is fixed at
  the T-058 consult with the Audit/Evidence Reviewer.
- **EVD-2 (pass) — reproducibility.** Operator-authored Runs are trivially
  reproducible (the plan is the input); the evidence packet records the plan verbatim
  so a Run is re-constructable for incident replay.

## 8. Frontend (must-pass)

- **FE-14 (block) — compose + informed launch.** A new operator surface (a `/runs`
  route in `apps/web`) lets the operator compose an ordered plan (reusing the FE-12
  resource picker), **review the full plan**, and launch it (typed client from the
  OpenAPI fragment + CSRF). Carries the DoD browser-rendered-evidence requirement +
  the design-system preflight.
- **FE-15 (block) — per-step status + cancel.** The Run view shows per-step status
  (pending/running/parked/completed/failed) live and offers **cancel** for a running
  Run. Browser-rendered evidence required.
- **FE-16 (pass) — parked-step plan context.** The existing `/invocations` approval
  surface additively shows a parked step's Run context ("step k of n" + plan) — an
  additive `<ApprovalPrompt>`/list change, defaults preserve the v0.3/v0.4 copy.

## 9. Offline install & operability (must-pass)

- **OI-12 (block).** The Run engine ships **inside `services/api`** — **no new
  systemd unit and no new Caddy route**. `install.sh` runs the new `api` migration
  (`runs` + `run_steps`); a fresh installer-driven boot brings the stack `active` and
  **WD-5 passes on the installed stack** (`task wd1`); `task offline-bundle`'s size
  gate still holds; bundle rebuilt from HEAD before the run ([[t033]] lesson). No
  SaaS runtime dependency (doctrine gate holds).

## 10. Performance & resource safety (must-pass)

- **PERF-6 (block) — bounded plan + bounded concurrency.** Plan size is bounded at
  launch (a concrete cap, e.g. ≤50 steps) and concurrent Runs per operator are
  bounded — the one genuinely new abuse vector (a pathological plan or a Run flood;
  ties to PERF-3). The held-call cost is one service-to-service connection + one
  gateway goroutine per *active* step, bounded by the concurrency cap.
- The v0.3/v0.4 floors (bounded exec PERF-1, idempotency PERF-2, per-agent
  concurrency PERF-3, fresh-dial PERF-4, asymmetric-verify PERF-5) are unchanged. SSH
  pooling + full per-edge rate-limiting remain **deferred** (§14).

## 12. Verification & gates (VER)

- **VER-14 (block).** `task lint` / `task test` / `task build` / `task licenses` /
  `task sec13-gate` stay green across the changed surfaces (`api` incl.
  `internal/run`, gateway, `apps/web`, `packages/{ui,shared-types}`). Zero new
  third-party dependency target (hand-rolled sequencer — no workflow/DAG engine;
  supply-chain doctrine).
- **VER-15 (block) — codegen drift zero.** Unlike v0.4.0, v0.5.0 **does** add
  operator-facing routes (create/list/get/cancel a Run) to the OpenAPI fragment →
  `gen.go` + `openapi.ts` regenerate **byte-deterministically** (VER-2). The internal
  `POST /v1/steps` is **not** in the fragment (service-service RPC).
- **VER-16 (block).** `task release-check` stays green end-to-end; its `e2e` leg runs
  **WD-5** (multi-step Run + kill-mid-Run resume + denied-abort + cancel) and its
  `smoke` leg covers the new `/runs` surface (FE browser DoD).
- **G1.** WD-5 is the live cross-boundary proof — a real operator → informed launch →
  api Run engine → gateway `/v1/steps` → policy → connector → broker → sshd → audit,
  across N steps with approval, cancel, and crash-resume, no mocked boundary.
- **G2.** ADR-0061 is the sole architecture ADR (Accepted, G2-clean — extends
  ADR-0057, edits no Accepted ADR). This document, once Accepted, is change-controlled
  (drift requires a new ADR).

## 13. ADR dependencies

- **ADR-0061 — Governed Runs (Accepted `ad24e53`).** The sole new ADR. Settles:
  entity = Run; engine in `api` behind an `internal/run` extraction seam; the gateway
  stays sole orchestrator (split refactor + one subject-pinned `/v1/steps` route);
  held-call exec reusing `waitForApproval`; typed informed launch + the
  `human-agent → agent-remote-session` step edge; reclaimable-claim crash-safe resume
  + deterministic idempotency keys; fail-closed running-orphan + operator cancel +
  non-atomicity; `run.*` events + `run:<id>` + the evidence packet; bounded plan +
  concurrency. No other ADR is required; any divergence surfaced at a ticket consult
  files a new ADR (never edits an Accepted one).

## 14. Deferred → v0.6+ / P1 (with promotion triggers)

- **The full Workstream module** (objective, sources, rules, schedule, scoped memory,
  owner — the chartered P1 module that *creates* Runs) — **trigger:** P1 Workstreams
  scoping once the Run engine is proven.
- **Agent-initiated Runs + a delegation identity model** — **trigger:** v0.6; also the
  trigger to **extract** `services/workstream-engine` from the `internal/run` seam.
- **Plan-level grant-with-preview** (approve the whole plan incl. flagged steps up
  front) — **trigger:** v0.6 ergonomics once per-step is proven.
- **Parallel / branching / retry DAG; cross-resource transactional plans** — out of
  scope; the wedge is strictly sequential, stop-on-first-failure.
- **A gateway-side "execute granted invocations" worker** — **trigger:** higher
  concurrency / agent-driven Runs (decouples exec from the held caller).
- **SSH connection pooling + full per-edge rate-limiting; persisted-command GC** — the
  v0.4.0 residuals; **trigger:** sustained multi-Run load / forensics retention need.
- **Memory/Context Index (P2); full per-workload key registry + rotation/JWKS** —
  unchanged deferrals from v0.4.0.

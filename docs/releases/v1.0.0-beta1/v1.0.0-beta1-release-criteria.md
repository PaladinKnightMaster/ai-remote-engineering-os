# v1.0.0 Beta 1 — release criteria

**Status: DRAFT for CEO ratification, 2026-11-18.** Authored in the Commander seat. Themes ruled by the CEO on
2026-11-16 [read: `docs/product/beta1-scoping/ecosystem-map.md:6-7`]. Ladder tickets are written just in time
(§11). The two ADRs this release needs (§8) are written and accepted **before** the tickets that build on them.

---

## 1. Scope — and why this release exists

v0.17.0 made installing the product a three-line job. The ecosystem pass that followed showed what a
stranger hits next [read: `docs/product/beta1-scoping/terminal-inventory.md` §(b)]:

1. **They cannot connect an agent.** The only way to get an agent token is a script holding the operator's
   password, and the token dies after five minutes. Every agent integration, B-041 included, is blocked
   until this changes [read: `services/api/internal/server/server.go:1295`; `packages/go/auth/auth.go:21`].
2. **They cannot do the basics.** There is no way to add their own server, edit or delete a target, sign
   out or change their password. Recovering a lost password is documented nowhere and has never been run
   [read: `apps/web/src/components/OnboardingChecklist.tsx:171-172`; `docs/api-contracts/openapi.v3.fragment.yaml:267-296`;
   ran: no `apps/web/src` file calls `/v1/auth/logout`].
3. **Nothing agentic happens end to end.** The gateway can govern any MCP client, but no harness has been
   run against the real governed chain (B-041) [read: `docs/spike/b041-deep-pass.md` §0].

**The question this release answers (the MVP sentence, for CEO confirmation):** *can someone who is not us
install it in three lines, add their own server, connect one agent from the browser, and watch that agent do
governed work on that server, with every action on a ledger an outsider can verify offline?*

| Theme | What | Decided by |
|---|---|---|
| **A1. Agent onboarding in the browser** | Create an agent and a Jira-style access key in the cockpit (7–365 days, or no expiry if switched on), exchanged by the bridge for the 5-minute token, and a local **`aireos-mcp-bridge`** so every MCP client renews unattended | **ADR-0080 (Proposed; revision with the bridge pending, §8)** |
| **A2. The missing basics** | Add your own server, edit and retire targets, sign out, change password, a tested upgrade, a tested lost-password recovery | this document (no new trust decision, except §5's two open questions) |
| **B. Governed harness integration (B-041)** | A real agent harness doing governed work end to end through the bridge, plus the deep pass's gateway mismatches M3–M7 | **ADR-0081 (to be written, §8)** + **WD-13** |

**Explicitly NOT in scope:** teams and a second operator (theme C, next release; ADR-0046's Zitadel trigger);
containment (B-040 / WD-12); backup and restore; any target type other than SSH; reading command output
(v0.16.0 P15b). ⚠ **Governance of a third-party harness is COOPERATIVE, not enforced**, until containment
lands: a harness that runs tools of its own outside the gateway is not stopped by us. This must be stated in
the release notes and the integrator guide, not left to be discovered [read: `CLAUDE.md` §Current phase, containment bullet].

⚠ **The API surface is NOT frozen in this release.** The freeze lands at v1.0.0 final, after the integration has
been used (CEO, 2026-09-01) [read: `CLAUDE.md` §SEQUENCING]. Beta 1 changes the surface on purpose (§4, §6).

## 2. The gate — WD-13, and a stranger is the gate

By the gate-sizing rule (*a new WD only for new governed capability*), B mints **WD-13**, the number reserved
for v1.0.0 [read: `CLAUDE.md` §WD ladder]: an agent harness acting through the governed chain is new governed
capability. A1 and A2 change who can reach the chain and how, so they are gated by SEC proofs, not a WD.

**The gate is:**
1. **HUM-1: the stranger test, by someone who is not the CEO** (§7). v0.17.0 waived it; here it is a
   **precondition** of the release, not a goal [read: `docs/releases/v0.17.0/v0.17.0-release-criteria.md:113`].
2. **WD-13**: a real harness through the bridge, the governed chain and a real target (§6).
3. The **SEC** negative proofs in §6a.
4. **WD-1..15 regression** on both stacks, `task smoke`, the later-host test, and an **upgrade from the signed
   v0.17.0 release** (BAS-8).

## 3. A1 — enrolled agents and the bridge — `AGT`

| ID | Criterion | Type |
|---|---|---|
| **AGT-1** | **An operator creates an agent in the cockpit**: name, **one** resource and its allowed operations (today's token scope, SEC-16 unchanged). The cockpit lists, disables and deletes agents; disabling or deleting revokes all its keys. Per ADR-0080 D1. | **block** |
| **AGT-2** | ⭐ **Access keys are managed like a personal access token** (ADR-0080 D2): lifetime chosen at creation, **7 / 30 (default) / 60 / 90 days or a custom date up to 365 days**, never extendable; **up to two active keys per agent** so rotation needs no downtime; each key shows created, expires, **last used** and state; keys expiring within 7 days are flagged. | **block** |
| **AGT-3** | **"No expiry" keys exist only after the operator switches them on** under Settings (off by default, audit-chained, refused to a paired session), and such a key is labelled "never expires" on every screen that lists it. | **block** |
| **AGT-4** | **A key is shown once** (copy and download-as-file), carries the `aireos_agent_` prefix and a checksum, is **stored only as a hash**, and is never returned again. Per ADR-0080 D2. | **block** |
| **AGT-4a** | **`POST /v1/agent-tokens/exchange`** takes the key as a Bearer header (no cookie, no CSRF) and returns the **same 5-minute agent token** `IssueAgent` mints today, scoped to the agent's resource and operations, plus the key's own expiry. **Every exchange is audit-chained** (`agent.token.exchanged`, actor `agent:<name>`, key id, no key material). Per ADR-0080 D3. | **block** |
| **AGT-4b** | **Revoking a key stops new exchanges at once**, and the agent loses access **within one token lifetime** (≤5 minutes), measured end to end. Per ADR-0080 D4. | **block** |
| **AGT-5** | ⭐ **`aireos-mcp-bridge` ships as a signed release artifact** with an SBOM, for **Linux amd64, Windows amd64 and macOS arm64** (agent hosts are usually laptops, not servers). It speaks stdio MCP to the client and HTTPS to the gateway, opens no port, renews the token itself **both before expiry and once after a `401`** (each path proven; the prototype never exercised the second), **trusts only the CA root the operator downloaded, checked against the fingerprint the cockpit shows**, **cancels its upstream call when the client cancels, closes stdio, or passes its own deadline** (SEC-74), and sends `notifications/progress` during an approval hold when the client asked for progress. Per ADR-0080 D7. Prototype: `docs/spike/bridge-check-2026-11-18.md`. | **block** |
| **AGT-6** | **The cockpit's enrollment screen shows ready-to-paste configuration** for the bridge (every client) and for the direct helper path (Claude Code `headersHelper`, Codex `http_headers_helper`), including the **tool-timeout setting** each client needs to survive an approval wait (M3, §6). | **block** |
| **AGT-7** | **The CA root is downloadable from the cockpit** with its fingerprint (public data). Per ADR-0080 D9. | **block** |
| **AGT-8** | **Hands-on proof per named client**: each client the integrator guide names has been run through the bridge against the real stack, across **at least two token renewals** and **one call held for approval for more than two minutes**. Minimum set: **Claude Code, Cline, and one Python harness (OpenHands SDK)**. A client the guide names without such a run is a defect. | **block** |
| **AGT-9** | **A paired phone session cannot enroll, list or revoke agents** (deny-by-default, ADR-0068 D5). | **block** |

## 4. Gateway mismatches from the deep pass — `GWY`

The surface is not frozen (§1), so these are fixed now rather than carried into the freeze
[read: `docs/spike/b041-deep-pass.md:269-275`].

| ID | Criterion | Type |
|---|---|---|
| **GWY-1** | **M7 — a `401` says what happened.** `WWW-Authenticate: Bearer error="invalid_token"`, with **expired** told apart from **malformed**, so a helper or the bridge knows to renew (ADR-0080 D8). | **block** |
| **GWY-2** | **M4 — the gateway answers `ping`** (the MCP spec requires it; today it returns `-32601`) [read: `services/mcp-gateway/internal/server/server.go` `serveMCP`]. | **block** |
| **GWY-3** | **M3 — an approval wait does not kill the call.** Either the client honours the bridge's progress notifications (the spec lets a client reset its timeout on progress; ADR-0080 D7 rule 5), or its configuration (AGT-6) raises its tool timeout above the approval wait. **The guide says which, per client.** Whichever is chosen is proven by AGT-8's held call. Measured so far: Claude Code gives up at about 60 s, and so does **Cline (default 60 s, configurable to 3600)**; the bridge does not change this [ran: `docs/spike/b041-deep-pass.md:271` for Claude Code; `docs/spike/bridge-check-2026-11-18.md` §2–§3 for Cline]. | **block** |
| **GWY-4** | **M5 — the tool name decision is made and recorded**: keep `remote.exec` (every client tried so far rewrites the dot itself) or rename to a name matching `^[a-zA-Z0-9_-]+$`, with an alias for one release if renamed. | pass |
| **GWY-5** | **M6 — protocol version negotiation**: the gateway accepts the newest MCP revision whose required parts it implements, and otherwise answers with the newest it supports (today pinned to `2025-06-18`) [read: `services/mcp-gateway/internal/mcp/transport.go:18`]. | pass |

## 5. A2 — the missing basics — `BAS`

| ID | Criterion | Type |
|---|---|---|
| **BAS-1** | **Add your own server in the cockpit**: name, host, port, user, approval flag and the server's **host key**, pasted by the operator (an `ssh-keyscan` line or the content of `/etc/ssh/ssh_host_*.pub`), with its fingerprint shown back before saving. Then the existing key panel generates the access key. **No new network path**: the cockpit never fetches a host key itself. The guide tells the operator where to get it. | **block** |
| **BAS-2** | **A targets screen** lists every target with its host, user, key state and approval flag (today targets appear only in dropdowns). | **block** |
| **BAS-3** | **Edit a target**: host, port, user, approval flag and host key. Changing the **host key** shows old and new fingerprints and needs a confirmation. Every edit is audit-chained with before and after values. | **block** |
| **BAS-4** | **Remove a target, including one that has had sessions.** A target with history is **retired**, not deleted: it disappears from the screens, refuses new sessions and Runs, and **keeps every session and audit link intact**. Removing also deletes its stored connector key (today it is left behind) [read: `services/api/migrations/0002_sessions.up.sql:11`]. ⓘ Open question Q1 (§10). | **block** |
| **BAS-5** | **Sign out**: a visible control that calls `POST /v1/auth/logout`, clears the cookie, and returns to the login page [read: `docs/api-contracts/openapi.v3.fragment.yaml:409`]. | **block** |
| **BAS-6** | **Change your password while signed in**: needs the current password, enforces the same rules as setup, and is audit-chained (`operator.password.changed`, no password material). This is not a reset; **a forgotten password stays a root action on the server** (deliberate, ADR-0046 / ADR-0078). ⓘ Open question Q2 (§10). | **block** |
| **BAS-7** | **Lost-password recovery is tested, not just written down**: on a real later host, root resets the password by the documented command; the new password signs in, the old one is refused, and the reset is audit-chained. The guide's trouble table gets the row it lacks today [read: `docs/product/beta1-scoping/terminal-inventory.md` J15.2]. | **block** |
| **BAS-8** | ⭐ **Upgrade from the signed v0.17.0 release** is a documented, rehearsed procedure: install the published v0.17.0 artifacts on a later host, create a target, an agent and some history, then upgrade by the guide's lines. Targets, history and the operator survive, **the audit chain verifies offline across the upgrade**, and the guide's lines are run verbatim (as `task docs-rehearsal` does). | **block** |
| **BAS-9** | The cockpit shows **which version is running** [read: `apps/web/src/routes/Dashboard.tsx:31-38` shows none]. | pass |

## 6. B — governed harness integration (B-041) — `HAR`

| ID | Criterion | Type |
|---|---|---|
| **HAR-1** | ⭐ **WD-13: a real harness does governed work end to end**: OpenHands SDK (the deep pass's first candidate) enrolled through the cockpit, connected through the bridge, runs a multi-step task on a real SSH target; at least one step is held for approval and approved from the cockpit, one is denied by a policy rule before any human is asked, and the chain records all of it and verifies offline. | **block** |
| **HAR-2** | **The harness is configured for the air gap**, with each setting the deep pass measured stated in the guide (for example OpenHands fetches a price table from `raw.githubusercontent.com` unless `LITELLM_LOCAL_MODEL_COST_MAP=True`), and HAR-1 runs **with egress captured and shown to be zero**, with a negative control in the same run [read: `docs/spike/b041-deep-pass.md` §4]. | **block** |
| **HAR-3** | **Cooperative governance is stated**: the integrator guide and release notes say that a harness's own built-in tools (its shell, its file editor) are not governed unless disabled, and the guide shows how to disable them for each named harness. | **block** |
| **HAR-4** | **An integrator guide** written for someone who has never seen the product: enroll, download CA and bridge, paste configuration, first governed call, what a held call looks like, how to revoke. Every line rehearsed as in BAS-8. | **block** |
| **HAR-5** | openworker as a second harness, if it fits after HAR-1. | pass |

## 6a. Negative proofs — `SEC` (each with a `[test: Name]` marker — VER-41)

⚠ **`block-criterion-check` will be RED on this document by design until the tests exist.** Each building
ticket adds its row's marker when it lands the test. A green gate at scoping would mean the claims were
exempted, not proven.

| ID | Criterion | Type |
|---|---|---|
| **SEC-68** | **An access key never appears** in any API response after creation, the audit chain, any log line, or the database except as its hash — searched for by its bytes, with a planted control in every location. | **block** |
| **SEC-69** | **A revoked, expired or disabled-agent key is refused** by the exchange (and a no-expiry key cannot be created while the setting is off), and **all failures look the same** (one response, one status, similar timing), so the endpoint tells an attacker nothing. Rate limit observed firing. | **block** |
| **SEC-70** | **An exchanged token cannot exceed the enrollment**: a different resource or an operation outside the registered set is refused by the gateway (SEC-16 applied to exchanged tokens). | **block** |
| **SEC-71** | **The bridge refuses a CA whose fingerprint does not match** and never falls back to the system trust store; and refuses a server whose certificate does not chain to the pinned root. | **block** |
| **SEC-72** | **Changing a target's host key is refused without the confirmation step**, and a session to a target whose live host key differs from the pinned one still fails closed (no silent re-pin). | **block** |
| **SEC-73** | **A retired target refuses** new sessions, Runs and agent calls, and **its history still verifies**. | **block** |
| **SEC-74** | ⭐ **A call the agent gave up on never runs.** On the real stack, through the bridge: a call is held for approval, the client times out (and, separately, cancels and closes stdio), and the operator then approves. **The command must not execute**, and the chain must show the invocation was abandoned, not completed. Negative control: the same sequence with the bridge's cancellation disabled must execute, which is what the prototype did [ran: `docs/spike/bridge-check-2026-11-18.md` §4]. | **block** |

## 8. ADR dependencies

- **ADR-0080 (Proposed, revised 2026-11-18) — agent access keys and the bridge.** Revised on two CEO
  directions:
  - **D2: Jira-style access keys.** 7, 30 (default), 60 or 90 days, or a custom date up to 365 days; "no
    expiry" behind a Settings switch; two keys per agent for rotation; last used.
  - **D7: the `aireos-mcp-bridge`**, including the rules that it never outlives its client's call and that
    it sends progress during an approval hold.
  - **Kept:** the 5-minute token stays internal, because it is what makes revocation work. The OAuth
    trigger is narrowed.

  **Awaiting CEO acceptance; must be Accepted before T-180.**
- **ADR-0081 (to be written) — B-041 governed harness integration.** Must decide at least: which harnesses are
  supported and how each is pinned; how a harness's own tools are disabled or declared (HAR-3); the air-gap
  settings (HAR-2); WD-13's shape. Inputs: `docs/spike/b041-deep-pass.md` §"Recommendation inputs".
- ⓘ BAS-1..9 need no ADR as drafted. **If Q1 or Q2 (§10) is answered in a way that changes an Accepted
  decision, that answer is its own ADR.**

## 9. Recorded risks

1. ⚠⚠ **A long-lived access key now lives on agent machines** (ADR-0080 Consequences). Bounded by one
   resource, its operations, every policy and approval gate, revocation within five minutes, and the audit of
   every exchange; still the largest new exposure in the release.
2. ⚠ **We start shipping software onto other people's laptops** (the bridge, three platforms). That is new
   signing, SBOM and support surface, and the first artifact we ship for Windows and macOS.
3. **Agent clients change every few weeks.** AGT-8's runs are pinned to versions; the guide must say which
   versions were run, and the claim decays. Re-run at the capstone.
4. **HUM-1 needs a human who is not the CEO.** Without one, this release cannot ship. Recruit now.
5. **Scope is three themes, one of them release-sized.** Cut order if the ladder slips: BAS-9, GWY-4/5,
   HAR-5 first; then BAS-2's screen polish. **Never A1 or HAR-1**: without them there is no MVP.

## 10. Open questions for the CEO

- **Q1 — removing a target with history (BAS-4).** Recommended: **retire** (kept for the record, hidden,
  refuses use). The alternative, deleting the history with it, breaks the audit link and is not recommended.
- **Q2 — does changing the password end your other signed-in sessions (BAS-6)?** Operator cookies today are
  self-contained 8-hour tokens with no server-side list, so they cannot be ended early. Recommended for Beta 1:
  **state it** ("other browsers stay signed in until they expire, at most 8 hours") rather than redesign
  sessions now. Ending them would need a session-version check in every request, which touches ADR-0046 and
  is its own ADR.
- **Q3 — confirm the MVP sentence** in §1 as HUM-1's script.

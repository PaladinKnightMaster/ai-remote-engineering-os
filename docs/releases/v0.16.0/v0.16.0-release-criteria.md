## 1. Scope of v0.16.0 — and why this release exists at all

**One question unifies everything in this release: can somebody who is not us rely on what we claim?**

Two independent forces arrived at that question in the same week.

**(a) A measured finding from v0.15.0.** That release produced **five separate instances of the same
defect** — a control that was correct while nothing verified it was connected to anything:

| # | The control | What was actually true |
|---|---|---|
| 1 | **SEC-57** — "a rule cannot widen authority", `block` | **Zero tests anywhere in the repo** |
| 2 | The capstone's own new **WD-15 guard** | **Never observed failing** |
| 3 | The **fix** for SEC-57 | Shipped a control that **could not discriminate** — it ran against an unflagged resource, where the call executes with no rule at all |
| 4 | **ADR-0070 §D4** release-key fingerprint | **Never published, across two signed releases** — and ADR-0070:194 names it the *only* mitigation for first-contact trust |
| 5 | The v0.15.0 **runbook** | Its Step 2 **was not executable** on the host that cuts releases |

⭐ **Every one was caught by opening something nobody had opened** — running the runbook, grepping for
the fingerprint, asking what a control would do if the thing under test were absent. **None came from
re-reading, and none from a green suite.** That is ops rule 11/12's thesis, confirmed five times in a
single release.

**(b) The decision to publish.** The product is going public as an open-source repository (CEO,
2026-09-01). The moment strangers depend on it, ungated instruments stop being internal hygiene and
become claims other people rely on.

**These are the same work.** Publication readiness and instrument governance both answer the shared
question, so this release does them together rather than as two separate chores.

⚠ **What this release deliberately does NOT do.** It adds **no new governed capability**, ships **no
new edge, verb, or decision point**, and changes **no runtime behaviour** of the governance plane. If
a ticket here begins changing what the product *does* rather than what can be *verified about it or
read about it*, that ticket has left scope.

## 2. The gate — **NO NEW WD.** ⭐ This must be ratified explicitly.

**v0.16.0 mints no WD gate.** By the project's own gate-sizing rule — *a new WD only for new governed
capability* — a release that adds no governed capability has nothing for a new WD to measure.
**Minting one would produce a gate that measures nothing new**, which is precisely the defect class
this release exists to remove. Recorded explicitly because the reflex on a new release is to mint one.

**Gate = WD-1..15 regression on both stacks + `task smoke` + the new instrument gates, each
mutation-proven + a CEO §human pass on the published-repo experience.**

⚠ **The §human pass here differs in kind from VER-32's.** It is not *"does the feature work"* but
**"does a stranger succeed"** — see PUB-6. That is the only instrument that has ever caught this
project's install-path defects: the v0.12 quickstart rejecting Ubuntu 24.04's own default sshd, and a
bundle version stale for eight releases *because the default matched it*.

## 7. ADR dependencies

- **A new ADR is required for the licence choice (PUB-2).** It is a strategic decision, not a file:
  the product's doctrine is **no SaaS runtime dependency**, and a permissive licence permits exactly
  the cloud rehosting that doctrine exists to refuse — while a copyleft licence deters the
  contributors and corporate users the publication is *for*. **Commander recommendation: Apache-2.0**
  — the patent grant matters for a security product, it is corporate-safe, and the realistic
  rehosting risk for a solo pre-1.0 governance plane is small beside the cost of deterring the
  contributors this is meant to attract. **The ADR must record the rejected alternatives, not only
  the pick.**
- No other ADR is expected. ⚠ **If a ticket here needs one, that is the signal it has left scope**
  (§1) — stop and re-scope rather than mint capability inside a hardening release.

## 9. Recorded risks

1. ⚠⚠ **PUB-1 is irreversible.** Everything else here can be revised afterwards; a pushed history
   cannot. It is `block`, and it is the release's highest-stakes single step.
2. ⚠ **VER-42 will surface rot.** Four suites have never been gated. **That is the point** — but it
   means the ticket's true size is unknown at scoping, and it must not be smuggled into a capstone.
   Budget it as the release's largest.
3. ⭐ **The open-source burden is likely to INCREASE solo workload, not reduce it** — at least
   initially. Recorded because the stated motivation was to *reduce* it. A new repository with no
   users typically attracts support questions rather than patches, each costing triage and review.
   **The defensible reasons to publish are different ones**: an auditability claim nobody can inspect
   is a weak claim; prior art and positioning against `ironclaw`; and permanently forcing the *"would
   a stranger succeed"* discipline that has produced this project's best catches. **Publish for
   those, and price the triage as a cost rather than a saving.**
4. ⚠ **A hardening release is the easiest place for scope to creep**, because every gap is visible at
   once. §1's exclusion and §7's ADR tripwire exist to catch that.

# v0.14.0 — Cumulative Security Review (SEC-52)

Status: **Complete — 2026-08-24** (T-144b). Reviewer: War Room Commander (Commander seat, per criteria
§12c). Reviewed at `de69ce8`, with all nine tools registered and every capstone gate green.

**Scope, per §12c — what this release changed, not a product re-audit:** (a) the D7 authority
narrowing, (b) the new egress path, (c) the seam's dispatch source, (d) the D3 approval binding.

**Why this document exists.** v0.2.0, v0.3.0 and v0.4.0 each red-teamed before tag; v0.13.0 had the
S-21 capstone. v0.14.0 was authored with none — the omission was found by the CEO asking whether the
workflow contained an audit step, not by any gate. **T-144 proves the release works; this asks whether
it is safe.** Those are different questions.

## (a) The D7 authority narrowing — **CLOSED, and stronger than the criteria required**

**The risk.** SEC-16's gate treated an empty `Operations` list as *unrestricted*. Correct while `exec`
was the only operation; the moment a second egress verb existed, **every agent token ever minted
without an explicit operations list would have silently gained file read and write on every resource in
its scope.** No test would have caught it. This was found while authoring ADR-0071, not by a gate.

**Verified in the as-built at this review** (not accepted from the ticket reports):

1. **`runGovernedStep` has exactly two callers** — `Invoke` (`:927`) and `RunStep` (`:1171`). There is
   no third path to a governed operation.
2. **`Invoke` carries the D7 gate**: an empty `Operations` list is unrestricted **for `exec` alone**;
   every other verb must be explicitly present or the call is refused.
3. **`RunStep` hardcodes `s.registry.Lookup(remoteExecTool)`** (`:1157`). The operator Run path has **no
   caller-controlled tool selection at all** — it cannot resolve a file tool under any input.

**Consequence:** ADR-0071 §D6's "Runs stay exec-only" is **structurally enforced, not merely intended**,
so the fact that `RunStep` does not carry the agent-token scope check is moot: it has no file surface to
reach. **The complete attack surface for reaching a file operation is the D7-gated path.** That is a
closed argument, not a defence-in-depth claim.

**Proof quality:** SEC-48 asserts both directions in one test (empty scope refused for
`remote.file.read`, accepted for `remote.exec`) and was **mutation-proven independently by the
Commander** — each half failing at its own assertion (`server_test.go:412` and `:422`), so the two
directions are not accidentally coupled.

## (b) The new egress path — **CLOSED**

- **SEC-51 subject pin**: `/v1/file` rejects any workload other than `mcp-gateway` with 403, copied
  verbatim from `/v1/exec`'s R5-ext pin. Mutation-proven at T-139b.
- **The credential path is unchanged.** `LoadTargetCoords` and `leaser.Lease` are protocol-agnostic and
  were **not forked** — the file leg leases exactly as exec does. connector-service remains the sole
  decrypt authority (ADR-0053), and the broker remains the sole SSH egress (SEC-18). **No new network
  path, no new key, no new daemon** (C2 held).
- **Bounds fail closed** (PERF-17/18/19): 1 MiB default cap; the read path **refuses** an over-cap file
  rather than truncating, because a truncated file is a corrupt file and a digest that matches nothing;
  the write path refuses **before dialling**; over-cap, timeout, permission-denied, no-such-path,
  is-a-dir and not-a-dir are distinguishable typed errors mapped to distinct HTTP statuses.
- ⭐ **A failed write cannot destroy the target.** Review caught that the first implementation opened
  with `O_TRUNC` and removed the file on any failure — so a transient chmod error deleted a
  correctly-written file, and any failure after open destroyed a pre-existing one. Now: write to a temp
  sibling with `O_CREATE|O_EXCL`, chmod, then `PosixRename` atomically. **The invariant is that a
  non-succeeding write leaves the target byte-for-byte unchanged**, and the cleanup path references
  only the temp file, so it is *structurally* incapable of deleting the target.
- **`O_EXCL` on the temp file** closes the symlink-preplacement vector, since the temp name lands in a
  directory the target host controls.

## (c) The seam's dispatch source — **CLOSED, with one latent hazard recorded below**

**The risk** (found at T-138 review): the seam decides *which operation crosses the trust boundary*. If
that decision reads caller-supplied input rather than persisted state, a reattach can select a
different operation than the one approved — tool confusion.

**Verified:** `store.Create` conflicts on `(agent_subject, idempotency_key)` and **not** on the tool, so
a reattach returns the *original* row while the caller's declared tool differs. Both `performAndFinish`
call sites now take the tool from the persisted row (`inv.Tool` / `claimed.Tool`).

⭐ **Two independent controls now close this, and the second was emergent rather than designed:**

1. Dispatch reads the persisted tool.
2. **Descriptor parsing is prefix-bound** — each tool's parser accepts only its own prefix and refuses
   otherwise, so even if (1) regressed, a cross-tool reattach could not parse the other tool's
   descriptor. A reattach declaring `remote.file.write` against an invocation persisted under
   `remote.exec` refuses at `parseFileWriteDescriptor`, because `"echo hi"` carries no write prefix.

⚠ **This means the per-tool descriptor prefixes are a SECURITY CONTROL, and no test names them as one.**
A future refactor unifying them into a shared format would remove a control silently. Recorded in
criteria §14e; **it belongs in any future ADR that touches the descriptor format.**

### ⚠ FINDING SEC-52-1 — mixed provenance at the allow-now call site (latent, not exploitable)

The two `performAndFinish` call sites are inconsistent:

| Site | Path | Arguments |
|---|---|---|
| `:1346` | post-approval | `claimed.ResourceID`, `claimed.Command`, `claimed.Tool` — **all persisted** |
| `:1289` | allow-now | **`req.ResourceID`, `req.Command`** (caller), `inv.Tool` (persisted) |

**Not exploitable today.** `:1289` is reachable only when `created == true` — the `!created` branch
returns earlier — so the invocation was created from this very `req` and `req.Command == inv.Command`
by construction.

**But the safety rests on an invariant that is invisible at the call site**, and T-138's fix moved only
`tool` to the persisted row while leaving `command` and `resourceID` on `req`. One refactor that lets
the `!created` branch fall through, or that moves this call, reintroduces exactly the vector T-138
closed.

**Remediation (zero behaviour change, recommended for T-145):** read `inv.Command` and `inv.ResourceID`
at `:1289`. They are equal to the `req` values by construction, so nothing changes at runtime — but the
invariant becomes *unnecessary* rather than merely *satisfied*, and both call sites read alike.

## (d) The D3 approval binding — **CLOSED**

**The risk.** ADR-0071 §D3 narrows informed approval: for a write the operator approves **path, size,
digest and mode — not the bytes.** §14c then decided the approved content is held in memory for the
blocking call and **never persisted** (verified: `Content` does not appear anywhere in the gateway's
store layer, so it *cannot* reach the database). That makes the bytes caller-supplied at execution —
deliberately the same shape as the T-138 vector.

**SEC-49 is what makes that safe, and it is therefore structurally load-bearing, not defensive.**
Execution recomputes sha256 over the bytes about to be written and refuses on mismatch, **before**
calling the broker. Mutation-proven independently by the Commander: with the check disabled, the mutant
**actually wrote the swapped payload** to the target path — the vector demonstrated, not asserted.

Descriptor parsing and digest extraction both **fail closed**: a descriptor that does not parse refuses
rather than proceeding unverified.

**Operator-facing honesty (FE-43)** is part of this control, not cosmetic: the prompt states the
consent limitation for a write ("you are approving the path, size, digest and mode — not the file's
contents") and the disclosure consequence for a read and a list ("the file's contents will be disclosed
to the agent"). An accurate prompt that omits the consequence is still uninformed consent.

## Verdict

**No exploitable defect found in what v0.14.0 changed.** The release adds governed capability on an
existing boundary: same edge, same credential custody, same sole-SSH-egress broker, same policy decision
point, same approval primitive, same chained-hash audit — **no new daemon, datastore, network path, or
key.**

The one finding (**SEC-52-1**) is a latent consistency hazard with a zero-behaviour-change remediation,
not a vulnerability.

⭐ **The honest summary of this release's security posture is that the new tools are better governed
than the one they sit beside** — typed, bounded, digest-anchored, separately grantable, and honestly
described to the operator — **while `remote.exec` remains able to do the same things less legibly.**
Closing that gap is containment's job, and containment is deferred.

# v0.14.0 — Release Criteria

Status: **Accepted — 2026-08-19** (the v0.14 checkpoint consult; five decisions D1–D5 CEO-ratified on
the Commander recommendation after a pre-authoring audit that changed the scope twice). Acceptance of
this document fixes the release intent; thereafter changes require a new ADR (the v0.1.0–v0.13.0 rule).

The architecture ADR it depends on — **ADR-0071 (governed file transfer)** — is **Accepted** and was
authored alongside this document at T-137.

Owner: War Room Commander (synthesis); Backend Architect (the seam, the broker leg, bounds); Security
Reviewer (D7 scope gate, approval binding, negative proofs); UX Reviewer **for §7 only** (the approval
descriptor is operator-facing and a bad rendering makes the governance claim hollow).

Every criterion is *pass* (must be true), *block* (presence stops release), or *deferred* (explicitly
out of scope, with the trigger that promotes it back). A ticket is "done" when it closes one or more
criteria here and breaks none.

**No new criteria family is minted.** The tool family extends `SEC`/`AUD`/`CON`; bounds extend `PERF`;
verification extends `VER`. Minting a family per release is the habit structural rule #2 exists against.

---

## 1. Scope of v0.14.0 — and why it is a capability release

**v0.13.0 shipped zero features by design, and that was correct** — it answered the buyer question
with hardening. **Two consecutive capability-free releases would not be correct.** This release widens
the product's outward surface for the first time since v0.3.0.

### The diagnosis this release answers

The gateway registry holds six tools. Five are control-plane — they orchestrate this product. **One
reaches the outside world.** Six releases deepened the spine around a single capability; that
asymmetry, not any missing control, is the gap. The most conspicuous absence is file transfer:
`grep -rn "sftp\|scp"` over the repository returns nothing.

### D1 — Story disposition (**RATIFIED 2026-08-19**)

**In:** the `remote.file.*` family (read / write / list) on the agent-direct path, the plane-agnostic
seam that admits it, the broker file leg, the approval descriptor, the SEC-16 scope narrowing, and the
operator rendering of a file invocation.

**Out, by decision not omission:** file steps in Runs and Workstreams (ADR-0071 D6 — it changes the
OpenAPI fragment, and the freeze lands at v1.0.0); recursive/glob transfer; resume and chunking;
screenshare / remote PC control (deferred at the checkpoint to a deliberate two-release program);
containment (B-040, deferred with its consequence recorded).

### Hard constraints (the release's defining posture)

| # | Constraint |
|---|---|
| **C1** | **Zero OpenAPI fragment change.** Gateway tools are an MCP surface. If a ticket needs a fragment change, it is out of scope or needs a new ADR. |
| **C2** | **No new daemon, no new datastore, no new network path, no new key.** The broker stays the sole SSH egress (SEC-18). |
| **C3** | **No new capability edge.** File tools ride `agent-remote-session` (ADR-0071 D1). |
| **C4** | **No migration.** Token operations and grant verbs are already free-form text arrays. If a ticket needs a migration, the scope is wrong. |
| **C5** | **Nothing above the seam changes.** The concurrency cap, approval park, idempotency, fail-closed rule and audit brackets are untouched. |

**The boundary rule holds:** this release adds governed capability on an existing boundary. It does not
place the trust root on a new dependency (`pkg/sftp` is a pure-Go library inside the existing broker,
not a daemon, not a trust anchor).

## 12d. Toolchain currency (must-pass) — `VER` — **CEO-RATIFIED 2026-08-19**

Raised by the CEO asking why `go 1.23` was pinned. **It was never decided.** The directive was written
once at the repo skeleton commit (`97ebb69`, 2026-05-19) and never revisited across thirteen releases,
under ADR-0041's clause: *"the current Go stable release line **at time of first service
implementation**"* — a point-in-time snapshot with **no refresh trigger**. Nobody chose 1.23 on merit;
it is a fossil of the scaffolding date.

**The consequence, verified against go.dev rather than recalled.** Go supports a release until two
newer majors exist. Go 1.23 shipped 2024-08-13; 1.24, 1.25, 1.26 and 1.27 have shipped since, and
**1.23's final patch was 1.23.12 on 2025-08-06**. This product has therefore been built for roughly a
year on a toolchain receiving no stdlib security fixes — **while shipping a signed CycloneDX SBOM that
records that toolchain** (ADR-0070). Our own attested bill of materials is what surfaces it, which is
precisely the outcome the v0.13.0 evidence-hardening line existed to avoid.

**Spike evidence, run before deciding:**

| Check | Result |
|---|---|
| Full Go tree under `golang:1.26.7` — build, vet, test | ✅ **BUILD_OK, VET_OK, 26/26 packages, zero failures, no source changes.** The `go 1.23` directive is a *minimum*, not a ceiling, so a newer toolchain compiles the tree untouched |
| `golangci-lint@v1.61.0` under Go 1.26 | ❌ **Does not compile** — its vendored `golang.org/x/tools@v0.24.0` fails with `invalid array length -delta * delta` |

**The lint toolchain is the real cost, not the compiler.** golangci-lint v2 changed its config schema,
so the 5.9 KB `.golangci.yaml` needs migration, and new linter defaults may surface findings across all
twelve modules. That is the unknown this ticket is sized around.

**Lint solution CONFIRMED empirically 2026-08-19 — a version watched passing, not a direction:**

| Candidate | Result on Go 1.26 |
|---|---|
| `v1.61.0` (current) | ❌ **Compile-fails** — vendored `golang.org/x/tools@v0.24.0`: `invalid array length -delta * delta` |
| `v1.64.8` (last of the v1 line) | ❌ **Compiles, then cannot analyze** — `could not load export data for golang.org/x/sync/semaphore` |
| **`v2.13.0`** | ✅ **Analyses Go 1.26 code cleanly — ZERO export-data errors.** Refuses only the config: `unsupported version of the configuration: ""` |

**So the cheap path is closed: the entire v1 line is unusable on 1.26**, and T-146 must migrate to v2 —
`.golangci.yaml` needs the `version: "2"` schema (golangci-lint ships a `migrate` command for it).

**Finding volume looks small, but the measurement is partial and stated as such:** `v2.13.0 --no-config`
on `services/session-broker` (the largest module) produced **4 findings, all `errcheck` on unchecked
`Close()` returns** — mechanical. ⚠ **That was the DEFAULT linter set on ONE module.** Our 5.9 KB
`.golangci.yaml` enables more than the default set, and eleven other modules were not measured, so the
post-migration count may be higher. T-146's consult re-measures with the migrated config across all
modules before committing to a single-ticket scope.

| ID | Criterion | Type |
|---|---|---|
| **VER-23** | **The Go toolchain used to build shipped artifacts is inside Go's supported window** (currently 1.25/1.26/1.27). v0.14.0 moves the **builder** to **Go 1.26**, the mature supported line — not 1.27, which released 2026-08-19 with zero field time, and a security product does not adopt a `.0` on its release day. | pass |
| **VER-24** | **The `go` directive in each `go.mod` is NOT raised in this release.** Building on a newer toolchain gains the stdlib security fixes; raising the directive additionally opts into new GODEBUG defaults that can change crypto/TLS behaviour at runtime. **Those are separate decisions and this release makes only the first.** Raising the directive is deferred with its own trigger (§14). | pass |
| **VER-25** | `golangci-lint` is upgraded to a release supporting Go 1.26, `.golangci.yaml` is migrated, and **any new findings are fixed or explicitly waived with a reason** — never silenced by disabling a linter wholesale. | pass |
| **VER-26** | **OI-4 re-asserted on the new toolchain** — the core bundle stays under the 150 MB gz cap. Headroom was ~107 MB at v0.13.0, so this is expected to pass, but a different toolchain produces different binaries and this is asserted, not assumed. | pass |
| **VER-27** | **Reproducibility re-measured in the new builder.** v0.13.0's published claim was measured in a `golang:1.23` image; it does not transfer. The measurement must be redone or the claim narrowed in writing. | pass |
| **VER-28** | **ADR-0072 supersedes ADR-0041's version clause** with a support-window policy, and the release checklist asserts it — so the next move is triggered by a rule rather than by someone noticing. ADR-0041 is **not edited** (G2). | pass |

**Sequencing (CEO-ratified):** the toolchain move is **its own ticket, T-146, running after the feature

## 14d. Minor residual — two error treatments for the same input class (T-140a)

`Invoke` now has **two different treatments for malformed tool arguments**, and the inconsistency is
recorded rather than papered over:

- `def.Target` failure → **raw Go error** (`catalog.go:447`) → a JSON-RPC protocol error.
- `def.Describe` failure → **`toolError`** → a 200 result with `isError`, which the model can read and
  act on.

**This was a self-contradiction in the T-140a brief** — it asked for "a tool error, not a Go error" and
in the same sentence "the same treatment `def.Target` gets", which are different things. The
implementer flagged it rather than silently picking one, and implemented the explicitly testable
clause. **That call is accepted**: within `Invoke`, `toolError` is what every agent-actionable refusal
uses (concurrency cap, scope denial), and ADR-0057's agent-facing honesty argues for the model being
able to read "your arguments were malformed" rather than receiving an opaque protocol fault.

**Not fixed here, deliberately.** `def.Target`'s Go-error treatment predates this ticket and changing
it would alter `remote.exec`'s observable behaviour — out of scope for a ticket whose entire proof is
behavioural neutrality. **Trigger: if the two are ever unified, `def.Target` moves to `toolError`, not
the reverse.** Today the divergence is unreachable in production because `Target` validates first, so
`Describe`'s error branch never fires for `remote.exec`; T-140b must not assume that stays true once a
tool's `Target` and `Describe` validate different fields.

## 14c. ⚠ OPEN DESIGN QUESTION found by the T-140 audit — **must be settled before T-141 is briefed**

**ADR-0071 §D3 says the descriptor goes in the invocation's `command` field. It does not say where a
parked write's CONTENT lives.** For `remote.file.write` that is load-bearing, and the as-built has no
place to put it:

- `services/mcp-gateway/migrations/0001_invocations.up.sql` defines `invocations` with **no content
  column**; `command` (added later, BYTEA, F3-sealed) is the only payload-bearing field.
- Flow: agent calls `remote.file.write` → policy says `requires_approval` → the invocation **parks** →
  operator approves → `performAndFinish` resumes with `claimed.Command`, the descriptor. **The bytes
  are not there.**

Three candidate mechanisms, none yet chosen:

| Option | Assessment |
|---|---|
| **(a)** New column for content | ⛔ **Violates C4 (no migration)** and puts raw file bytes in the gateway's database |
| **(b)** Pack content into the `command` blob alongside the descriptor | No migration; inherits F3 at-rest encryption automatically. Ugly, and makes `command` two things |
| **(c)** Hold content in memory for the blocking call | Viable **because approval is synchronous block-and-wait** — the caller's goroutine is still open. Fails on gateway restart mid-park (fail-closed, acceptable) and must be reasoned through carefully against the idempotent-reattach path |

⭐ **Why (c) is not obviously unsafe:** on reattach a *different* caller supplies its own content, which
looks like the T-138 tool-confusion vector — **but SEC-49's digest binding closes it.** The approved
descriptor carries the sha256, and execution must verify the bytes hash to it, so a swapped payload is
refused. **That makes SEC-49 structurally load-bearing rather than belt-and-braces**, and it must be
implemented before or with whichever option is chosen — not after.

⚠ **T-140b has already made a de-facto choice for READ, and the T-141 consult must ratify or replace it — for all three tools at once, not piecemeal.** `remote.file.read`'s descriptor is `"remote.file.read " + path`, and `performAndFinish` recovers the path with `strings.TrimPrefix(command, prefix)`. **The persisted `Command` is therefore doing double duty: a human-readable descriptor AND a machine-parsed payload.** That works for read because the path *is* the entire payload; it is exactly what fails for write, where D3 deliberately excludes the bytes.

Two things the T-141 consult owes, together:

1. **The mechanism** — options (a)/(b)/(c) above, decided once for the whole family.
2. **Fail-closed parsing.** `TrimPrefix` **silently returns the whole string** when the prefix is absent, so a malformed descriptor would be reinterpreted as a path rather than refused. The invariant holds by construction today (`describe` writes the prefix, dispatch reads the same persisted row), so it is unreachable — **but it is a silent fallback on a governance path, in a product whose core rule is fail loud**, and T-141/T-142 will copy the pattern twice more. Use `strings.CutPrefix` with an explicit refusal and apply it to `remote.file.read` in the same change, so all three are consistent. **Deliberately not patched at T-140b:** a 3-line retrofit ahead of the mechanism decision would only have to be redone once (1) lands.

### ⭐ DECIDED at the T-141 consult, 2026-08-19 — **option (c), and the evidence is what chose it**

**Option (b) — packing content into the `command` blob — is REJECTED on a fact, not a preference.**
Verified in code at this consult:

- `command` is written once at `Create` and **never cleared, nulled or updated** thereafter.
- `ReapStale` only flips `status` → `failed`; its "bounds command retention" comment means it bounds how
  long a row sits *parked*, **not that it erases the payload**.
- **No code path anywhere deletes an `invocations` row.**

So (b) would retain **every file ever written through this product, in full, forever, in the gateway's
governance ledger** — with no erasure path. That is not a bloat concern, it is a data-governance defect,
and it directly contradicts ADR-0064's tombstone/forgetting semantics for memory. Building the erasure
path it would need means a migration, which **C4 forbids**.

**DECISION: option (c).** The approved bytes are held in memory for the life of the blocking call and
threaded to `performAndFinish`. **Content never enters the database.**

**SEC-49 is what makes this safe, and it is therefore load-bearing rather than defensive.** The
persisted descriptor carries the sha256; execution recomputes it over the bytes about to be written and
**refuses on any mismatch**. This is the same shape as the T-138 tool-confusion vector — caller-supplied
data at execution time — but with a decisive difference: the caller's bytes are **verified against
persisted state**, not trusted. A swapped payload is refused cryptographically, not by convention.

**Residual, stated rather than discovered later:** a gateway restart while an invocation is parked loses
the content, and the invocation then fails closed. That is the correct failure direction and it is
honest — but it means a parked write does not survive a gateway bounce, and the release notes should say
so plainly rather than let an operator discover it.

**Also decided here (the second item below): fail-closed descriptor parsing.** `strings.CutPrefix` with
an explicit refusal, applied to `remote.file.read` in the same change so all three tools share one
pattern. The digest extraction for SEC-49 must fail closed identically — a descriptor whose digest
cannot be parsed **refuses**, it does not proceed unverified.

**This is a mechanism choice inside D3's stated intent, not a contradiction of it, so it does not
require a new ADR** — but it is consequential enough to be a recorded decision rather than an
implementer's improvisation. **Commander owes a decision at the T-141 consult.**

T-140 (read) is unaffected: a read has no payload to park.

## 14e. Emergent property confirmed at T-141 — tool confusion is now doubly defended

Worth recording for **SEC-52**, because it was not designed in and a reviewer should not have to
rediscover it. The T-138 tool-confusion vector is now closed by **two independent controls**:

1. **Dispatch reads the persisted tool** (T-138) — the caller's declared tool cannot select the operation.
2. **Descriptor parsing is prefix-bound** (T-141) — each tool's parser accepts **only its own prefix**
   and refuses otherwise, so even if (1) regressed, a cross-tool reattach could not parse the other
   tool's descriptor and would fail closed at the parse.

The consequence: the `TestReattachDispatchesOnPersistedToolNotCallerTool` guard still uses an
*unregistered* placeholder tool, which at first looks like it only tests the benign form now that
`remote.file.write` is real. Traced through, the dangerous form is closed by (2) — a reattach declaring
`remote.file.write` against an invocation persisted under `remote.exec` refuses at
`parseFileWriteDescriptor`, because `"echo hi"` carries no write prefix. **No change required; recorded
so SEC-52 does not have to re-derive it, and so a future refactor that collapses the per-tool prefixes
knows it is removing a control.**

## 15. Designated drop candidate

**`remote.file.list` (T-142), in that order alone.** Cleanly severable: it shares `file.read`'s verb,
adds no governance semantics, and `remote.exec` can list a directory today. Dropping it costs
ergonomics, not the release's claim.

**Irreducible core (never drop):** the seam (T-138) · the broker leg (T-139) · `read` and `write`
(T-140, T-141) · both negative proofs (SEC-48, SEC-49) · the capstone.

Recorded here in advance, per VER-10, so a cut is a decision rather than an improvisation — the gap
v0.13.0 shipped with and had to fix mid-ladder.

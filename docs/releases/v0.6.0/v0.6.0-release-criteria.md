# v0.6.0 — Release Criteria

Status: **Accepted — 2026-06-30** (v0.6 opening ADR consult + self-audit + this criteria
consult; CEO sign-off — DEL-* code family, all-three-live WD-6 negatives, principal-operator
Run ownership). The single architecture ADR it depends on (**ADR-0062 — Agent-initiated
Runs**) is already **Accepted** (`b07e887`); acceptance of *this* document fixes the release
intent. Future changes to this document require a new ADR (criteria drift
is a load-bearing decision — same rule as v0.1.0–v0.5.0).

Owner: War Room Commander (synthesis); Permission Model Reviewer (delegation identity +
actor/principal split + policy-subject=agent + subject-pins); MCP Gateway Reviewer (the
`run.launch` tool + the keyless launch surface + the gateway→api forward; default-deny);
Audit/Evidence Reviewer (grant lifecycle events + delegation provenance + chain integrity);
Offline-Install Engineer (OI-13 — api migration + gateway tool + the gateway→api env wire,
no new unit).

This document defines what shipping **v0.6.0 — "Agent-initiated Runs" (the delegation-grant
model)** means. Every criterion is *pass* (must be true), *block* (presence stops release),
or *deferred-to-P1* (explicitly out of scope, with the trigger that promotes it back). The
criteria are the exit gate for every v0.6.0 ticket: a ticket is "done" when it closes one or
more criteria here and breaks none.

---

## 1. Scope of v0.6.0

v0.6.0 is the **second initiator** for the Run engine built in v0.5.0 (ADR-0061): where v0.5
let an **operator** author and launch a governed Run, v0.6 lets an **agent** launch a
governed Run **bounded by an operator-issued delegation grant**. The Run engine, the gateway
`/v1/steps` path, policy → connector → broker, and the audit chain are **reused unchanged**;
the new work is the **grant primitive**, the **actor/principal split**, and a **keyless agent
launch surface**.

**The privilege delta (ADR-0062).** Agent-initiation removes both pillars v0.5 stood on: an
`agent-tool` token is SEC-16-scoped to one resource + one verb (it cannot author a multi-step
plan; widening is escalation), and **no human is present at launch** (informed-launch
authorization is absent). v0.6 supplies the missing authority as a **scoped, audited,
revocable delegation grant** — the consent moves **from per-plan (v0.5) to per-grant (v0.6)**.

**Hard constraint (preserved).** The agent never mints; `services/api` and the gateway remain
the **sole** signing authority; the gateway stays the **sole** governed-step orchestrator;
the broker remains the **sole** SSH egress. v0.6.0 adds **no new egress path, no new
credential custody, no new key, and no new token-minting workload**. Critically, the
**agent-facing launch surface stays on the keyless gateway** — the symmetric-key-holding
`api` is **not** made agent-reachable (ADR-0060/SEC-20 preserved; the self-audit reversal).

**Standards lineage (ADR-0062 §Context).** The model is a localized composition of RFC 8693
(token-exchange actor/principal), RFC 7662 / reference-token revocation (the revocable-record
grant), capability-security POLA (the bounded grant), and STS/GCP-style bounded delegation —
specialized for offline-first / self-hosted (a local Postgres record, no external authz).

Concretely, on top of the v0.5.0 Run engine, v0.6.0 delivers:

- **The delegation grant** — a durable, **revocable, server-side record** in `services/api`
  (`delegation_grants`) that pre-authorizes one agent for a bounded resource+verb set, with
  TTL + bounds + a step budget, plus the operator issuance surface (`/v1/grants`).
- **The keyless agent launch path** — a new `run.launch` gateway MCP tool (the agent's
  existing `aud=mcp-gateway` token) that **forwards** the {agent, grant, plan} to `api` over
  a **gateway-pinned (`subject=="mcp-gateway"`) internal route**; `api` validates the plan
  against the grant and drives the **unchanged** `/v1/steps` path.
- **The actor/principal split** — `{actor=agent, principal=operator}` threaded across
  `/v1/steps`, the gateway invocation, and the `api` `runs` rows; policy-subject = the agent
  (flagged steps still park); the grant cascade-revocable.

**Out of scope** (→ §14): plan-level grant-with-preview beyond the grant; the `internal/run`
extraction; fine-grained (per-command / Cedar-style) grant policy; segregation-of-duties on
who issues vs approves; the gateway-side exec worker; parallel/branch/retry DAG; the full
Workstream module (P1); Memory/Context Index (P2); the per-workload key registry/JWKS.

v0.6.0 adds **no new egress tool**: a Run is still an ordered sequence of the existing
`remote.exec` invocation. The one new tool is `run.launch` — a **launch** verb that mints no
egress; it hands a plan to the governed engine.

The wedge is **one agent-launched, grant-bounded Run driven to completion through the
unchanged governed chain — unattended where ungated, parked where flagged, denied where
out-of-grant, and cancelable by revoking the grant** (WD-6). Everything else exists to make
that true and verifiable.

## 2. WD-6 — the single load-bearing wedge (the demo)

**WD-6.** On a real (not mocked) stack, an operator delegates and an **agent autonomously
drives a grant-bounded Run** end-to-end. WD-6 comprises a **happy path** (1–5) plus three
independent **live negatives** (N1 out-of-grant, N2 revoke-cancels, N3 keyless-surface):

1. **Grant issuance.** The operator issues a delegation grant (agent X; resources {an ungated
   R1, a `requires_approval`-flagged R2}; verbs {`exec`}; a TTL; `max_steps_per_run`,
   `max_concurrent_runs`, `step_budget`). Issuance is a typed, audited `human-agent`
   authorization (CSRF-gated); `grant.issued` is chained (actor = operator).
2. **Agent launches, bounded.** Agent X — using its **existing `aud=mcp-gateway` token** —
   calls the new **`run.launch`** MCP tool with the grant id + an ordered plan mixing R1/R2.
   The **keyless gateway** verifies the agent token and **forwards** {agent-subject, grant-id,
   plan} to `api` over the **`subject=="mcp-gateway"`-pinned** internal route. `api` validates
   **plan ⊆ grant**, creates the Run, and chains `run.launched` carrying **actor = agent,
   principal = operator, grant_id**.
3. **Unattended ungated execution.** The engine drives the R1 steps via the **unchanged**
   `POST /v1/steps`; each opens an invocation and runs the unchanged chain (policy `Decide`
   subject = **the agent**; bracket edge `agent-tool → agent-remote-session`, with principal +
   grant recorded). An ungated step **runs unattended** — no human prompt (the autonomy
   payoff).
4. **Flagged step parks + delegated informed approval.** The R2 step **parks** on the
   existing `/invocations` console **carrying its delegated context** (the agent actor + the
   grant + the principal) beside the verbatim command (operator-only, ADR-0059). A live
   operator approves → the held `/v1/steps` call resumes, claims, and execs → the Run
   advances to completion. The command is **sealed at rest** while parked.
5. **Evidence packet + replayable chain.** The terminal Run assembles an **evidence packet**
   recording the **delegation provenance** (grant id, principal, actor = agent) + the ordered
   steps + policy decisions + approvals + stdout-SHAs + outcomes. The full chain
   (`grant.issued → run.launched → per-step tool.invoked`/`policy.decision`/`approval.*`/
   `credential.leased`/`remote.exec`/`tool.result`, each carrying `run:<id>` → `run.completed`)
   is **hash-intact** and replayable via `audit-service verify`.

**Live negatives (separate grants/Runs, all live in the gate):**

- **N1 — out-of-grant denied.** Agent X launches a plan targeting a resource or verb **not in
  its grant** (or under an expired/revoked grant). `api` **denies at plan-vs-grant** before
  any dispatch; **no egress**; the denial is audited. An agent **cannot** widen its own scope.
- **N2 — revoke cancels in-flight.** A grant with an **in-flight** Run is revoked; the
  revocation **cascades** — the Run is **canceled** (no further steps dispatch), with
  `grant.revoked` + `run.canceled` chained. An in-flight (e.g. parked) step finalizes per the
  running-orphan policy.
- **N3 — keyless-surface / agent-cannot-mint (the SEC-20 proof).** A **direct agent → `api`
  launch attempt is rejected** (no agent-facing `api` route exists; the agent reaches the
  engine only via the keyless gateway), **and** an **agent-forged foreign-edge/audience token
  is rejected** by the verifier (SEC-21 carried). The key-holding workload is provably not
  agent-reachable.

**Regression guard.** **WD-5 (operator-initiated Runs) stays green** — the actor/principal
split touches `/v1/steps`, so the operator-Run path is re-proven behavior-preserving.

**This single demo (happy path + N1 + N2 + N3) is the release gate.** It is built as an
extension of the `tests/e2e` live harness and re-run on the installer-produced stack
(`task wd1`). The denial (N1), the revoke-cascade (N2), and the keyless-surface proof (N3)
are **live, not mocked**. Step-budget / concurrency-cap exhaustion is unit/integration-tested
off the gate (PERF-7).

## 3. Capability-edge security (must-pass)

Every boundary stays gated by `packages/go/middleware` `RequireCapability`. v0.6.0 adds the
delegation path **without weakening any v0.4.0/v0.5.0 invariant**.

| Edge | Caller → callee | Token / gate |
|---|---|---|
| `human-agent` (operator → api, **issue/revoke a grant**) | operator cookie + CSRF (ADR-0050) | v4 local (unchanged) |
| `agent-tool` (agent → gateway, **`run.launch`**) | the agent's existing `aud=mcp-gateway` token (SEC-16) | v4 public (ADR-0060) |
| `service-service` (gateway → api, **the launch forward**) | gateway asymmetric private; api verifies; **subject-pinned `subject=="mcp-gateway"`** | v4 public (ADR-0060) |
| `service-service` (api Run engine → gateway `POST /v1/steps`, now `{actor,principal}`) | **unchanged**; still `subject=="api"`-pinned (SEC-24) | v4 public / pinned |
| `agent-tool → agent-remote-session` (per-step bracket, delegated) | actor = agent; `policy.Decide` subject = **agent**; principal + grant recorded | (the step's audited edge) |
| `service-service` (gateway → policy/connector/broker) | **unchanged** from v0.4.0 | v4 public / pinned |

- **SEC-26 (block) — the agent never mints; grant authority is server-side.** The delegation
  grant is a **server-side record** (§DEL-1), not a credential the agent holds; the agent
  references it by id. `api`/gateway remain the sole signers; **no new token-minting workload**
  exists. A code path that lets the agent mint a token, or that materializes the grant as a
  bearer the agent carries, is a release blocker.
- **SEC-27 (block) — the launch surface is keyless; `api` is not agent-reachable.** The agent
  launches only via the `run.launch` tool on the **keyless gateway**; the gateway forwards to
  `api` over a `subject=="mcp-gateway"`-pinned internal route. **No agent-facing `api` route
  exists.** A direct agent→`api` launch path — putting an agent-reachable surface on the
  symmetric-key holder — is a release blocker (the ADR-0060/SEC-20 regression guard; proven by
  WD-6 N3). **New verify edge (ADR-0060 mirror).** The forward is the **first gateway→api
  service call**; `api` today wires a **symmetric-only** verifier (`main.go buildAuth`,
  `AIREOS_PASETO_KEY`) and would reject the gateway's `v4.public` token outright. v0.6 gives
  `api` a **dual-mode verifier holding the gateway's public key** (the exact mirror of how
  ADR-0060 gave the gateway `api`'s public key); `api` verifies the inbound forward
  (`subject=="mcp-gateway"`, `aud=="api"`, `v4.public`) before honoring it. The gateway's
  public key is provisioned to `api` at install (OI-13); the symmetric key is unchanged on the
  non-gateway planes (no SEC-20 regression — `api` gains a *verify* key, not a mint key).
- **SEC-28 (block) — actor/principal split, subject-pins untouched.** `/v1/steps` carries
  `{actor, principal}`; `api` binds **both** server-side from the grant; the gateway trusts
  neither from an agent. The v0.4 subject-pins (broker `mcp-gateway` PIN-1, connector
  `session-broker` PIN-2) and the `/v1/steps` `subject=="api"` pin are **unchanged** (SEC-25
  carried). An agent cannot set or spoof the principal.
- **SEC-29 (block) — plan-vs-grant is the enforced scope.** Before any dispatch, `api`
  validates, server-side: `agent-token.subject == grant.agent` ∧ `grant.status == active` ∧
  `now < expires_at` ∧ `∀ step: resourceId ∈ resources ∧ verb ∈ verbs` ∧
  `len(steps) ≤ max_steps_per_run` ∧ `active-runs-under-grant < max_concurrent_runs` ∧
  `step_budget ≥ len(steps)`. This **is** the relocated, generalized SEC-16 (the gateway no
  longer sees an agent token on the delegated path). A rejected plan **denies + audits** (WD-6
  N1).
- **SEC-20/21/17/18/25 (block, carried).** The v0.4.0/v0.5.0 invariants are preserved
  unchanged: gateway keyless of the symmetric cluster key (SEC-20); bounded blast radius +
  no foreign-edge mint (SEC-21); no decrypt path on the gateway (SEC-17); broker exec parity +
  subject-pin (SEC-18); the v0.5 step-pin discipline (SEC-25). The new tool + forward + split
  must not regress any of them.

## 4. Delegation & Run-engine architecture (must-pass)

- **DEL-1 (block) — the grant primitive.** A new `delegation_grants` table + a self-contained
  store in `services/api` (the `internal/run` seam, or a sibling `internal/grant`): a
  **revocable, server-side record** — `principal`, `agent`, `resources[]`, `verbs[]`,
  `expires_at`, `max_steps_per_run`, `max_concurrent_runs`, `step_budget`, `status`
  (`active`/`revoked`/`expired`). **Not** a bearer token (RFC 7662 / reference-token custody:
  instant revocation + stateful budget; the agent holds nothing mintable). The grant command
  carries **no** secret-class material (it carries no command at all).
- **DEL-2 (block) — agent launch via `run.launch` + the gateway forward.** A new gateway MCP
  tool `run.launch` (named `run.*`, not `workstream.*` — ADR-0061 naming discipline) accepts
  {grant-id, ordered plan} under the agent's existing `aud=mcp-gateway` token. The gateway
  **does not drive the Run**: it forwards {agent-subject (from the verified token), grant-id,
  plan} to a **new internal `api` route** over a **`subject=="mcp-gateway"`-pinned**
  service-service edge (the mirror of `/v1/steps`'s `onlyAPI` pin); `api` creates the Run and
  the **existing sequencer drives it through the unchanged `/v1/steps`**. The gateway change
  is a **behavior-preserving split** — the agent `task e2e` **and** the operator-Run WD-5 stay
  green **before** the new tool/forward ride on it (gateway-reviewer mandate; default-deny +
  tool-telemetry-to-audit preserved).
  **`run.launch` is a control-plane tool, not a governed-exec tool** — it has **no
  single-resource target**, so the gateway's per-call SEC-16 resource/operation scope check
  (the agent-plane `Invoke` check, `catalog.go:228-233`) **does not apply** to it; the
  api-validated **grant** is the scope (SEC-29). `run.launch` mints no egress (it dispatches no
  `remote.exec`) — it hands a plan to the engine and returns the new run id. The exact
  launch-token scope shape (resource-unscoped vs a distinct `launch` operation) is nailed at
  the T-065 consult. **Launch idempotency:** an agent retries programmatically, so `run.launch`
  carries an idempotency key (deterministic per intended launch) so a retried call **re-attaches
  to / returns the same Run** rather than double-launching and double-consuming the grant
  budget (the operator `POST /v1/runs` non-idempotency, `runs.go`, is acceptable for a human;
  an agent's is not).
- **DEL-3 (block) — plan-vs-grant validation in `api`** (the SEC-29 enforcement point; the
  relocated, generalized SEC-16). Rejection denies + audits before any egress.
- **DEL-4 (pass) — the extraction stays deferred.** The grant + the agent-launch path ride the
  existing `services/api` `internal/run` seam; **no** standalone `services/workstream-engine`
  is extracted (the locked v0.6 decision; the seam stays lift-and-shift for a future real
  second consumer).
- **DEL-5 (pass) — actor/principal threaded end-to-end.** `runs` gains nullable `grant_id` +
  `actor` columns (null = a v0.5 operator-direct Run; additive, back-compatible); the gateway
  invocation + `/v1/steps` carry `{actor, principal}`; the bracket edge is
  `agent-tool → agent-remote-session` with `principal` + `grant_id` recorded (NOT `agent-agent`
  — there is no second agent; the canonical seven-edge set is unchanged, avoiding an ADR-0046
  edge-set revision).

## 5. Grant governance & approval (must-pass)

- **GOV-4 (block) — per-grant consent replaces informed-launch.** The operator's consent to
  unattended execution is the **grant issuance** (a typed, audited `human-agent` act:
  resources + verbs + bounds + TTL), not a per-plan review. The agent then composes plans
  **within** the grant without per-plan human review. The coarsening of consent (resource+verb
  vs per-command) is **explicit** in the criteria + the issuance UI, and **contained** by the
  grant bounds + flagged-resource parking (GOV-5).
- **GOV-5 (block) — flagged steps still park; policy-subject = the agent.** Ungated steps run
  unattended; a flagged step **parks** on the existing `/invocations` surface for a **live
  human**. `policy.Decide` receives **the agent** as subject (not the operator) — so ADR-0054's
  same-operator self-approve **cannot** auto-resolve a flagged step under the absent operator's
  identity. Approval gating is resource-label-driven (unchanged), so an agent subject neither
  self-allows nor needs a policy entry.
- **GOV-6 (block) — informed approval of a delegated step.** The parked `/invocations` view
  surfaces the **delegated context** (the agent actor + the grant id + the principal) beside
  the verbatim command, so the approving human knows an **agent** is asking under operator
  *X*'s grant (extends FE-16; operator-only command posture, ADR-0059, unchanged).
- **GOV-7 (pass) — an operator can only delegate authority it holds.** Grant issuance is bounded
  by the issuing operator's own authority; at the single-bootstrap-operator posture (ADR-0046)
  that is unbounded, and narrows automatically when multi-operator lands (SoD stays deferred).

## 6. Durability, resume & lifecycle (must-pass)

- **DUR-7 (block) — instant revocation cascades to in-flight Runs.** Revoking a grant
  (`status → revoked`) **also cancels the grant's active in-flight Runs** via the existing
  `CancelRun` path (whose `run.canceled` + the sequencer's between-step `RunStatus` stop halt
  further dispatch). Revocation blocks **both** new launches **and** in-flight Runs — not just
  new launches. An in-flight (e.g. parked) step finalizes per the DUR-4 running-orphan policy
  (not force-killed). Proven live (WD-6 N2).
- **DUR-1..6 (block/pass, carried).** The v0.5.0 Run-engine durability is **reused unchanged**
  for agent-launched Runs: durable `runs`/`run_steps` (DUR-1); reclaimable single-driver claim
  (DUR-2); resume-with-skip, no double-exec via deterministic `run:<id>:step:<index>` keys
  (DUR-3); fail-closed running-orphan (DUR-4); stop-on-failure + operator cancel (DUR-5);
  non-atomicity as an explicit non-guarantee (DUR-6). An agent-launched Run is the same
  `runs`/`run_steps` driven by the same sequencer.

## 7. Audit & Evidence Packet (must-pass)

- **AUD-16 (block) — grant lifecycle events.** `api` chains `grant.issued` (actor = operator)
  and `grant.revoked` via its transactional outbox (ADR-0045). New event vocabulary;
  content-free ingest (ADR-0049) preserved (the grant's resources/verbs/bounds are referenced,
  never any command).
- **AUD-17 (block) — delegation provenance in the chain.** `run.launched` and each step's
  `tool.invoked`/`tool.result` carry **actor = agent + principal = operator + grant_id** (in
  addition to `run:<id>` + the by-design dual anchor). A delegated step is distinguishable in
  the chain from a direct agent call (by `run:<id>` + principal + grant_id) and from an
  operator Run (by actor = agent). The single hash chain stays intact + replayable
  (`audit-service verify`).
- **EVD-3 (pass) — evidence packet shows delegation.** The terminal Run's evidence packet
  (assembled at read time from existing durable state, no new blob — EVD-1 contract carried)
  records the **grant id + principal + actor = agent**, so a delegated Run is replayable and
  **attributable to both** the agent that drove it and the operator that authorized it.
  Reproducibility (EVD-2) carries: the plan + the grant are the inputs.

## 8. Frontend (must-pass)

- **FE-17 (block) — grant management UI.** A new operator surface (a `/grants` route in
  `apps/web`) lets the operator **issue** a grant (pick the agent + resources + verbs + TTL +
  bounds + step budget), **list** active grants (with their bounds + status), and **revoke**
  one (typed client from the OpenAPI fragment + CSRF). Carries the DoD browser-rendered-evidence
  requirement + the design-system preflight.
- **FE-18 (block) — delegated context on `/invocations`.** The existing approval surface
  additively shows a parked **delegated** step's context (the agent actor + the grant + the
  principal), beside the existing Run context — an additive `<ApprovalPrompt>`/list change;
  defaults preserve the v0.3/v0.4/v0.5 copy (a non-delegated invocation shows no delegation
  context). Browser-rendered evidence required.
- **FE-19 (pass) — agent-launched Runs visible to the principal operator.** Agent-launched
  Runs appear in the **principal operator's** `/runs` view (owner-scoped to the grant's
  principal, §10), labeled as agent-driven (actor = agent + the grant), and the principal can
  **cancel** a runaway agent Run directly (complementing grant revoke). Browser-rendered.

## 9. Offline install & operability (must-pass)

- **OI-13 (block).** The grant store ships **inside `services/api`** (the `delegation_grants`
  migration) and the `run.launch` tool ships **inside the gateway** — **no new systemd unit,
  no new Caddy route** (both the launch forward and `/v1/steps` are internal service-service).
  The new wiring is **(a)** the **gateway → api URL env** (the gateway must know `api`'s URL
  for the launch forward — the mirror of the existing `GATEWAY_URL` on `api`) and **(b)** the
  **gateway's public key provisioned to `api`** (so `api`'s new dual-mode verifier validates
  the inbound forward — SEC-27; the install-time mirror of the gateway's existing
  api-public-key env, ADR-0060/OI-11). Both land in `install.sh`/the unit env. `install.sh`
  runs the new `api` migration; a fresh installer-driven boot brings the stack `active` and
  **WD-6 passes on the installed stack** (`task wd1`);
  `task offline-bundle`'s size gate still holds; **bundle rebuilt from HEAD before the run**
  ([[t033]] lesson). No SaaS runtime dependency (doctrine gate holds).

## 10. Performance & resource safety (must-pass)

- **PERF-7 (block) — grant bounds + concurrency reconciliation.** `step_budget`,
  `max_steps_per_run`, and `max_concurrent_runs` are enforced at plan-vs-grant (SEC-29). The
  one genuinely new abuse vector is a compromised agent flooding Runs under its grant —
  bounded by the grant. **`max_concurrent_runs` must be reconciled with the gateway's
  per-initiator in-flight cap** (PERF-3, `maxInFlight` default 4): with actor = agent, all of
  an agent's in-flight steps bucket under one subject, so a grant allowing more concurrent
  Runs than the cap would cause the gateway to refuse a step, which the sequencer reads as a
  governance refusal and **fails the Run**. The grant bound and the cap must agree (and whether
  a *parked* step counts as in-flight — a latent v0.5 operator-side edge — is verified). Tested
  by an integration/unit leg off the WD-6 gate.
- **Cap layering.** A delegated Run sets `runs.operator = principal` (the ownership decision,
  §8/FE-19), so it counts against the principal's v0.5 per-operator active-run cap
  (`maxActiveRunsPerOperator`, `runs.go`) **as well as** the per-grant `max_concurrent_runs`.
  The criteria's intent: the **per-grant** cap is the delegation bound; the per-operator cap is
  a global safety ceiling. The two must not be set so an agent's normal grant activity starves
  the principal's own launch budget — the concrete values are reconciled at the T-066 consult.
- The v0.3/v0.4/v0.5 floors (bounded exec PERF-1, idempotency PERF-2, per-agent concurrency
  PERF-3, fresh-dial PERF-4, asymmetric-verify PERF-5, bounded plan + concurrency PERF-6) are
  unchanged. SSH pooling + full per-edge rate-limiting remain **deferred** (§14).

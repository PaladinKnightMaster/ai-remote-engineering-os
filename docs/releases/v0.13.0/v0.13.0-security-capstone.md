# v0.13.0 security-audit capstone (S-21) — GATE-1

**Run 2026-08-18 at `41da1b9`. Commander-authored.**

Per the release criteria, *the audit **is** the gate*. This is a cumulative red-team across the
governance spine, not a checklist. It records the attacks attempted, what each returned, and an
explicit verdict — including the attacks that found nothing, because a capstone listing only its
findings hides its coverage.

**Scope: GATE-1 and GATE-3.** GATE-2 (full WD-1..11 on both stacks + smoke) and GATE-5 (the `§human`
offline verification) belong to T-136 and are not claimed here.

---

## 1. GATE-3 — the two negative proofs

Both must **fail correctly**: pass on clean input, fail on tampered. Either one failing to do so
blocks the release.

### SEC-43 — a forged chain fails head verification ✅ RE-RUN ON THE CURRENT TREE

SEC-43 was last proven at `9b31c15`, which **predates T-131** (`1c94399`) — a commit that changed
`services/api` and added a newly chained event. The proof was re-run rather than inherited:

```
LEG A  UPDATE against audit_events (seq 636) REJECTED while audit_events_no_mutate is armed:
       ERROR: audit_events is append-only (ADR-0045): UPDATE rejected (SQLSTATE P0001)

LEG B  tampered actor at seq 1 (signed head covers through seq 636)
       chain.Verify = INTACT   <- the setup, not the proof
       audit-service verify    = BROKEN, exit 1  (first divergence index 15, seq=16)
       aireos-verify (offline) = BROKEN, exit 1  (exported bytes only, NO database access)

pre-tamper controls PASSED on BOTH verifiers before any tampering
```

`ok aireos.local/tests/e2e 432.419s` · `ok …/internal/checkpoint` ×2 · zero FAIL/panic · exit 0.

**LEG A is the part that matters most**, and it is why ADR-0069's threat statement is now testable
rather than asserted: the append-only trigger has guarded the table since v0.1.0, so the attack needs
**owner** privilege to drop it — not the "write access" the war room originally claimed.

### SEC-45 — a mutated bundle fails signature verification ✅

Re-proven on the **current** signed artifacts after the clean-tree rebuild: 14/14, both artifacts,
byte flips verified real (28→227, 53→202, exact XOR 0xFF), and the check asserts the literal
`signature does NOT verify` line rather than a bare non-zero exit — so a `tar` failure cannot
masquerade as a signature proof.

**GATE-3: PASS.**

## 2. Red-team — attacks attempted

| # | Attack | Result |
|---|---|---|
| A1 | Create a resource in product code without chaining `resource.created` | **No bypass.** Exactly one product-code `INSERT INTO resources` exists (`services/api/internal/store/store.go:96`), inside the transaction that enqueues the event. The other three inserts are `_integration_test.go` files. |
| A2 | Make the release gate report provenance-green without checking anything | **FINDING F-1 — see §3.** |
| A3 | Same trick against `sec45-check` | **Closed.** It refuses on a missing key, missing artifacts, or a missing `.sig`/`.sbom.json` — three separate loud exits, no self-skip path. |
| A4 | Pass `aireos-verify` a gapped or truncated export | **Closed.** The reader errors when `eventsSeen != manifest.EventCount`; the export bypasses all filters by construction, so a filtered (gapped) export cannot be produced through the supported path. |
| A5 | Hide an action by driving it into the `governed-actions@1` preset | **Closed by design.** The preset is an **exclude** list of exactly `{plan.requested, plan.expired}` (`services/audit-service/internal/store/preset.go:21`), so a new outcome surfaces by default rather than needing to be added. Excluded outcomes remain retrievable on the unfiltered path. |
| A6 | Tamper *above* the last signed head and have it verify clean | **Not a defect — correct behaviour, and stated.** The verifier reports `INTACT+UNATTESTED` for the tail rather than a false green. The cadence window is a disclosed residual (ADR-0069), not a silent one. |
| A7 | Forge heads with a key lifted from a non-audit service | **Closed.** The signing key lives *alone* in `/etc/aireos/audit.env` (`infra/offline/install.sh:294`), not the shared environment file — so only an `audit-service` RCE reaches it. That residual is stated in the threat model §5. |

## 3. Finding F-1 — `task release-check` green does not imply provenance was verified

**Severity: LOW** (build-time; not a shipped-product vulnerability). **Class: S-25** — a guardrail that
can pass without checking anything, landing on the release gate itself.

Two facts compose into the hole:

1. `provenance-check` **is** wired into `release-check` (`Taskfile.yml:231`), and it **self-skips to
   exit 0** when `dist/offline` contains no `*.tar.gz`.
2. `sec45-check`, which **cannot** self-skip, is **deliberately not** wired into `release-check`.

So on a tree where the build failed, the artifacts were cleaned, or the release-check was run before
building, the provenance leg reports OK having verified nothing — at exactly the moment it matters.

**Why the self-skip is defensible and still a finding.** Its rationale is sound: most `release-check`
runs happen in a dev loop before anything is built, and failing there would train people to ignore
the gate. The defect is not the skip — it is that **the skip is invisible in the aggregate verdict**.

**Mitigation, and it is already the plan.** The release cut (T-136) must not treat `release-check`
green as provenance evidence. It must run, with artifacts present on disk:

```
RELEASE_PUBLIC_KEY=<real key> task provenance-check
RELEASE_PUBLIC_KEY=<real key> task sec45-check
```

Both were run in this cycle against the fixture key and are green. **Recorded as a T-136 obligation**
rather than fixed here: changing `release-check`'s skip semantics this late would alter a gate whose
behaviour every prior ticket in this release was verified against.

## 4. What this capstone did **not** cover

Stated so the verdict is not read for more than it proves:

- **GATE-2** — full WD-1..11 on both stacks plus smoke. T-136. The last full installed-stack run was
  T-127a, which predates T-131; **the installed stack has not been regression-run since**.
- **GATE-5** — the `§human` offline verification. T-136, and it is the release's entire claim: an
  evidence export and a public key on a machine with no database and no product install.
- The **four named external cross-checks** (agent-governance-toolkit, SkillSpector, agentfield,
  clawpatrol) were not independently re-verified here. The positioning correction that matters
  commercially — Microsoft's toolkit independently reaching ~5 of our 7 controls, including the
  credential-broker property — is recorded in the threat model §6. Given that T-134's external check
  found a **twice-committed error** in our own ASI08 mapping, treating any remaining external claim
  as verified would be unwarranted.

## 5. Verdict

**GATE-1: PASS, with one LOW finding (F-1) carried to T-136 as an obligation rather than a fix.**
**GATE-3: PASS — both negative proofs green, both shown failing correctly, SEC-43 re-run on the
current tree rather than inherited.**

**No exploitable bypass was found in the governance spine.** The controls that this release added —
chain-head signing, anchoring, offline verification, bundle signing, SBOM coverage — each resisted
the attacks aimed at them, and the two that could have silently degraded (`sec45-check`,
`aireos-verify`) refuse loudly instead.

The honest through-line is unchanged from the threat model: **the enforcement and the thing enforced
still sit inside a single trust boundary.** An `audit-service` RCE signs forged heads; a Postgres
owner drops the append-only trigger; a compromised build host signs a malicious artifact. None of
those is closed by this release, all three are stated, and each has a named successor. That is the
release's actual security posture, and the capstone's job was to confirm it is described accurately
rather than to claim it is better than it is.

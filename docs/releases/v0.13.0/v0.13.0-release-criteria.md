# v0.13.0 — Release Criteria

Status: **Accepted — 2026-08-10** (v1.0.0 scoping consult; the consult answered the war room's open
buyer question — **no near-term buyer** — which split E-06, and the three decisions inside this
document (§1 D1, §3 D2, §4 D3) were CEO-ratified on the war-room recommendation). Acceptance of this
document fixes the release intent; thereafter changes require a new ADR (the v0.1.0–v0.12.0 rule).

The two architecture ADRs it depends on — **ADR-0069 (audit chain authenticity)** and **ADR-0070
(release provenance)** — are **not yet written**. T-123 and T-128 author them.

Owner: War Room Commander (synthesis); **Security Reviewer (release lead)**; Backend Architect
(chain-head signing, key custody, rotation); DevOps/Release Guard (bundle signing, SBOM, provenance,
reproducibility); ADR Author. **No UX or Design System Reviewer** — there is no UI in scope, and
pulling them in invites exactly the polish work this release forbids.

Every criterion is *pass* (must be true), *block* (presence stops release), or *deferred* (explicitly
out of scope, with the trigger that promotes it back). A ticket is "done" when it closes one or more
criteria here and breaks none.

**No new criteria family is minted.** Chain authenticity extends `AUD`/`SEC`; bundle provenance
extends `OI`/`VER`; the disclosure documents extend `DOC`/`SEC`. Minting a family for a single
release's rider is the habit structural rule #2 was written against.

## 1. Scope of v0.13.0 — and why this is not v1.0

**The question that decided the release.** The post-Beta war room (2026-08-10) left one item open:
*is there a near-term buyer, pilot, or demo for v1.0?* It had gone unanswered across three turns.
**Answered at this consult: no.** There is no external recipient of the bundle in the near term.

That answer splits **E-06**. The epic bundled two different kinds of work under one release:

- **Hardening** — the security-audit capstone, the ASI mapping, audit-chain authenticity, bundle
  provenance, the enforcement tests, the quickstart gate, and the boundary statements. This is pure
  upside. It gates nothing, constrains nothing, and every finding it closes is one a reviewer would
  otherwise find for us.
- **The freeze** — the OpenAPI surface freeze, its compatibility policy, and the upgrade/migration
  statement. This buys nothing without someone writing against the surface, and it constrains every
  release after it.

**v0.13.0 ships the hardening. The freeze defers.** 1.0 is minted when layer 2 is real, at which
point the freeze has a consumer and is stamped on a surface that has already been hardened. The path
renumbers accordingly: **v0.13.0 Evidence Hardening → v0.14.0 Containment (WD-12) → v1.0.0 Beta 1,
where layer 2 lands *and* the surface freezes (WD-13) → v1.1 Session & Evidence (WD-14) → v1.2+**.
See `docs/requirements/epic_story_catalog_v4.md` §Part 4 for the renumbering map against the
war-room table.

**This ordering is better than the war room's, not merely cheaper.** S-28 adds signature and key-id
material to audit responses. Freezing first would have frozen a surface we were about to change.

The rule has now held under pressure three times. It is ratified doctrine. **A fifth admitted

### Hard constraints (the release's defining posture)

v0.13.0 adds **no capability edge**, no actor class, no credential path, no egress path, and **no
agent-plane change of any kind**. The `mcp-gateway` stays keyless (SEC-20). ADR-0053's sole-decrypt
authority is untouched. Both agent read planes (`agent-memory`, `agent-workspace`) are byte-unchanged.
**No new UI.** No `packages/ui` change. No new third-party runtime dependency in the product; SBOM
and signing tooling are build-time only.

**What it does add, enumerated so nothing is smuggled:** one `audit-service` migration (`chain_heads`),
one Ed25519 signing keypair per install, one append-only anchor file, one offline verifier binary,
one detached bundle signature, one SBOM artifact, one audit event on an existing route, and the
removal of one route.

**The wedge:** *an auditor who receives an evidence export and a public key, on a machine that has
never touched the product, can prove the record is ours and unaltered — and can read, in our own
threat model, exactly which claims we do not yet make.*

**Out of scope** (→ §15): the OpenAPI freeze and compat policy; the upgrade statement; an external
signer/witness process; containment; generalized session revocation; audit provenance as a structured
field; any UI change.

## 2. The gate — **no new WD** (structural rule #2, re-tested)

> A new WD-N is minted **only** when a release adds new governed capability, not once per release out
> of habit.

Re-tested against the as-built, not inherited:

| Item | New governed capability? | |
|---|---|---|
| S-28 chain signing | A signing key and a verifier. No operator or agent verb; nothing new can be *done* under governance. | **No** |
| S-29 bundle signing | Build-time artifact. Not in the running product at all. | **No** |
| B-033 / B-035 | An event on an existing route; a removal. | **No** |
| S-25 / S-26 | Tests. | **No** |

**v0.13.0 mints no walkthrough demo.** WD-1..11 regress unchanged. What replaces a new WD is
something stronger than a walkthrough: **two negative proofs** (SEC-43, SEC-45), in the SEC-21
tradition — a demo shows the happy path works, a negative proof shows the attack fails.

**The gate is therefore:**

- **GATE-1 — the S-21 security-audit capstone is signed.** As originally designed: the audit *is* the
  gate. A cumulative red-team across the full governance spine, cross-checked against the named
  governance category (agent-governance-toolkit, SkillSpector, agentfield, clawpatrol).
- **GATE-2 — full WD-1..11 regression green on both stacks** (compose `task e2e` + installed `task wd1`),
  plus smoke.
- **GATE-3 — the two negative proofs green.** SEC-43 (a chain forged by DB write access fails head
  verification) and SEC-45 (a mutated bundle fails signature verification). **Either one failing to
  *fail correctly* blocks the release.**
- **GATE-4 — the quickstart gate (OI-36) green** from the built bundle on a fresh host.
- **GATE-5 — §human.** The CEO drives the **offline verifier as a third party would**: an evidence
  export and a public key, on a machine with no database access and no product install. This is the
  release's entire claim, and the §human has caught defects no automated gate could on two
  consecutive releases (v0.11: 4 review-caught defects a green suite missed; v0.12: two step-1
  blockers).

## 3. Audit chain authenticity (must-pass) — `AUD`, `SEC`

**The finding, verified against code at this consult, not inherited.**
`services/audit-service/internal/chain/chain.go:21` computes
`chainHash = SHA256(prevHash_bytes || framed(core fields))` with `crypto/sha256` — **no key, no HMAC,
no signature**. The file header states audit-service "is the sole chain authority: only it computes
prevHash and chainHash." An attacker with database write access recomputes the chain from genesis and
`chain.Verify` returns clean. **The chain proves ordering, not authenticity** — and the audit trail is
the core product claim, which is what makes this the sharpest of the three war-room findings.

**Refinement the war room did not have.** A chain-verify CLI already exists
(`services/audit-service/main.go:103`, asserted by `task wd1`). It verifies ordering and reads events
from the store, so it needs database access. **This release does not build a verifier from scratch —
it adds authenticity to the chain and makes the existing verifier usable by a third party with no
database.** That materially lowers the cost of T-126.

### D2 — Trust model (**RATIFIED 2026-08-10**)

**In-service signing + anchoring outside Postgres + offline verification.** `audit-service` holds an
Ed25519 chain-head key distinct from the cluster key, reusing the per-workload asymmetric key
machinery established at v0.4.0 (ADR-0060). This closes the stated attack — database write access can
no longer produce a chain that verifies.

**It does not close audit-service RCE**, which can still sign forged heads. That residual is
**stated** (DOC-34), on exactly the doctrine this release is built on: v0.13 states the boundaries it
has not yet enforced rather than letting a red-teamer discover them. The strong form — an external
signer or witness that the writer cannot compromise — is scoped as a named successor in the v0.14
Containment ADR, where it belongs: it is new infrastructure with its own failure modes, it would mint
a WD, and it contradicts a release whose defining posture is zero new capability.

| | Criterion |
|---|---|
| **AUD-35** | `audit-service` signs chain heads with an **Ed25519 key distinct from `AIREOS_PASETO_KEY`**, generated per install by `install.sh` alongside the existing per-workload keys. The cluster key is never the signing key. |
| **AUD-36** | A `chain_heads` row is written at a **bounded cadence** (every N events or T seconds, whichever comes first — not per-event), recording `chainHash`, event id, sequence, timestamp, `keyId`, and signature. Cadence is configurable and defaults are recorded in ADR-0069. |
| **AUD-37** | Each signed head is **anchored to an append-only file outside Postgres** on the install host. Loss of the database does not lose the heads, and **divergence between the file and the table is itself a detectable finding** the verifier reports. |
| **AUD-38** | A self-contained **evidence export** (events + heads + signatures + `keyId`) that carries everything a third party needs. |
| **AUD-39** | Heads carry a `keyId`; the verifier accepts a **key ring**, so rotation does not invalidate historical heads. **No rotation UI** — rotation is an operator file operation, documented. |
| **SEC-42** | The offline verifier verifies an export with **no database access and no product install**, using the public key alone. |
| **SEC-43** | **G1, the release's defining test.** Mutate an event row in the database, recompute the entire chain from genesis so that `chain.Verify` returns clean, then prove **head-signature verification FAILS and names the first divergent head.** Green on both stacks. |
| **SEC-44** | The public key is distributed **out-of-band** — fingerprint published in the release notes — and the verification path **never depends solely on material inside the artifact it verifies**. A trust root shipped inside the thing it validates is circular and does not satisfy this criterion. |
| **PERF-14** | Head signing does not measurably regress the audit write path. Bounded cadence, never per-event; measured against the v0.12 baseline. |

## 4. Release provenance — bundle signing + SBOM (must-pass) — `OI`, `VER`

**The finding, verified at this consult:** `Taskfile.yml` has `offline-bundle` and `release-check`
and **no sign, sbom, or checksum target**. For an air-gapped product **the offline bundle is the trust
root**, and today's release gates are functional (size, version), not provenance. An operator on a
disconnected network has no cryptographic way to confirm the bundle is the one we built.

### D3 — The provenance claim we can actually make (**RATIFIED 2026-08-10**)

**There is no pipeline to put provenance in.** This repo has no git remote and no CI — its own
standing convention. "Attested by our builder" is unavailable, and any criterion written as though a
hosted builder exists would be unmeetable. **No SLSA level is claimed**, and the release notes say so
plainly rather than implying a level by silence.

The honest provenance story for an air-gapped product with no CI is **reproducibility**: build the
bundle twice from the same commit and diff. **v0.13 measures it and publishes the result either way.**
Reproducibility is *not* a release blocker; **measuring it is.** A bundle that does not reproduce is a
published finding — which is more valuable than an unexamined claim, and consistent with every other
disclosure in this release.

| | Criterion |
|---|---|
| **OI-32** | A **detached Ed25519 signature** over the bundle tarball, produced as part of `task offline-bundle`. |
| **OI-33** | A verify script an operator can run **before** trusting the bundle, plus a published key fingerprint. Subject to SEC-44's non-circularity rule. |
| **OI-34** | An **SBOM (CycloneDX 1.6 JSON)** covering Go and node dependencies, shipped in the bundle. The existing `go-licenses` output is retained, not replaced. |
| **OI-35** | **Reproducibility is measured**: build twice from the same commit, diff, record the result in the release artifacts. Non-reproducibility is a **finding, not a block**. |
| **VER-11** | `task release-check` **fails** if the signature or SBOM is absent, or if SBOM coverage omits a shipped component. A provenance gate that does not fail is the S-25 failure class. |
| **SEC-45** | **G1 negative proof.** Mutate a single byte in the bundle → signature verification fails. |
| **OI-39** | Bundle size stays within the **OI-4 150MB cap** with the new artifacts included. |

## 8. Resource lifecycle (must-pass) — `CON`, `AUD`

**B-035's sequencing constraint, quoted:** *"removal must be the LAST fragment change, in the same
ticket that stamps the frozen fragment, codegen drift zero."*

**Read by its intent.** The constraint exists so that a **breaking removal never lands after the
freeze** — B-035's own rationale says "removal is cheap now and irreversible after." Landing it
*earlier* than the freeze is explicitly safe and is what the rationale recommends. With the freeze
deferred to v1.0.0, the intent-preserving reading is: **remove it before the freeze, at any point; the
freeze stamps whatever remains.**

**This is not a convenience reading — leaving it costs correctness.** B-033 was narrowed to
`CreateResource` **only because** `PUT` was being removed. Carrying `PUT` while keeping B-033 narrowed
ships a live, capability-gated mutation of a governed target that **chains no audit event at all**, in
the release whose entire claim is the evidence trail. The alternatives were to widen B-033 or to
disclose the hole in the very document that is the gate. Removal is cleaner than both.

| | Criterion |
|---|---|
| **CON-5** | **`PUT /v1/resources/{id}` is removed** from the fragment, the handler, and the generated clients. Codegen drift zero. Verified at T-122b: `apps/web` has never had a call site. B-039 — the only consumer that would justify it — is post-Beta, i.e. outside the frozen band entirely. Re-adding a path later is explicitly **non-breaking** under S-20. |
| **AUD-40** | **`CreateResource` chains an audit event**, matching every other governed mutation in the product (grants, workstreams, memories, context sources, pairing). `DeleteResource` was done at T-118c. **G1: proven live, not unit-mocked.** |

## 13. Verification & gates (`VER`)

- **VER-2** — codegen drift zero (§9).
- **VER-6 — G1 (live cross-boundary test).** Every ticket names the live test that proves its claim
  before sign-off; a mocked boundary does not satisfy it. The release's named live tests are
  **SEC-43** (forged chain fails head verification), **SEC-45** (mutated bundle fails signature
  verification), **OI-36** (quickstart from the built bundle on a fresh host), and **AUD-40**
  (`CreateResource` chains its event on the real path).
- **VER-7 — G2 (ADR divergence).** Any Accepted-ADR contradiction found during implementation is
  flagged at decision time → conform or file a **new** ADR. **Never edit an Accepted ADR.**
- **VER-8 — Diff budget.** ≤12 files / ≤500 LoC per ticket unless explicitly approved (generated
  `gen.go`/`openapi.ts` and SQL count but are mechanical).
- **VER-9 — Commander review gate.** Every implementer diff is Commander-reviewed against G1/G2 before
  `main` is fast-forwarded; **only the Commander advances `main`**.
- **VER-10 — Drop decisions are explicit.** A cut item is cut by a **recorded CEO decision**, its
  criteria flip to *deferred* with a trigger in §15, and the release notes say what was cut and why.
  A silent drop is a release-criteria violation.
- **VER-16 — The negative proofs must fail correctly.** SEC-43 and SEC-45 are *inverted* tests: a
  green suite that does not actually detect the forgery is the S-25 failure class applied to the
  release's own gate. Each must be shown failing against an untampered input and passing against a
  tampered one.

## Appendix — research status at authoring time

Three background verifications were dispatched at the start of this consult. **They gate v0.14 and
v1.0, not v0.13**, and are recorded here so the next session does not re-dispatch them blindly.

- **matchlock (v0.14 containment) — COMPLETE.** Fits the OI-4 cap: ~18–20MB expected delta against
  34MB headroom, because the guest kernel is a purpose-built minimal 6.19.8 config at **7.3MB
  gzipped** (25.3MB expanded — store it gzipped or the high case busts the cap by ~1.3MB). **Three
  corrections to the war-room record:** (1) the real cap risk is **not** matchlock — it ships no
  workload rootfs, so an air-gapped deployment must also carry an unbounded OCI agent image (50–150MB),
  which is what actually breaks 150MB; (2) **"raw TCP goes to passthrough uninspected" is wrong** —
  `pkg/net/proxy.go:159` gates passthrough on `IsHostAllowed(dstIP)` and emits a blocked event, so
  raw TCP gets L3/L4 destination-IP allowlisting with an audit record, and the accurate statement is
  that *DNS-name policy cannot be enforced on raw TCP, only resolved IPs*; (3) **Firecracker is
  pinned to v1.10.1, published 2024-11-13 — ~21 months stale**, so we inherit its CVE tail on the
  component whose entire job is containment. Air-gap depends on an **undocumented `file://` kernel
  ref**; there is no `kernel pull` subcommand, so pre-seeding is an unsupported code path needing a
  pin test. Other claims confirmed (nftables via pure-Go netlink, synchronous Unix-socket hook,
  `Import(io.Reader)`, no kernel in the .deb). MIT, not archived, single maintainer confirmed.
- **openworker (v1.0 integration) — COMPLETE.** Both original blockers **downgraded**: the WSS relay
  cannot open without a cloud sign-in token, and telemetry is double-gated and structurally inert
  signed-out (opt-out verified honored in code). **Three new findings:** an **unconditional Tauri
  auto-updater** (every 30 min, no opt-out — avoided by running the headless Python server); the
  default model is `gpt-5.5`, i.e. live OpenAI egress until repointed; and **`GET /v1/inbox` mutates
  state**, auto-resolving orphaned pending items — *a naive poller silently discards pending
  approvals*, which for a product whose claim is the approval moment is the finding that matters
  most. Poll per-session or not at all. Bus factor worse than reported: 80% single-author, and the
  marquee name has one commit; velocity decaying 70→53→7/week; 239 open PRs against 130 total
  commits. MIT confirmed; block-and-wait is genuine (indefinite `asyncio.Event`, needs our own
  timeout). **Verdict: integrable headless, with conditions. Re-measure before the v1.0 commit point.**
- **pgGraph (B-024, v1.2+) — COMPLETE. RLS claim CONFIRMED, and the disqualifier is not the one we
  wrote down.** Traversal enforces **table-level `SELECT` only, not RLS** — stated by the project
  itself in `graph/src/acl.rs`'s header and `docs/known-issues.mdx`, so this is disclosed design, not
  an oversight. **Mechanism:** `graph.build()` compiles registered tables into an immutable
  memory-mapped CSR artifact; traversal walks that integer array and **never touches the table access
  path**, so RLS never runs. Access control is a *preflight table gate* (`pg_class_aclcheck`), not a
  row filter. **The finding that actually decides it:** `hydrate` is a **caller-supplied boolean**.
  With `hydrate => true` (default), hydration re-queries base tables as the calling role and
  non-hydrated rows are dropped; with `hydrate => false` there is **no base-table query at all** and
  the caller gets RLS-blind topology. `graph.weighted_shortest_path` has **no `hydrate` parameter at
  all** — unconditional RLS-blind path disclosure to anyone holding table `SELECT`. Tenant scope is
  likewise **caller-asserted** (`tenant TEXT DEFAULT NULL`, "not verified against the calling role's
  identity"). **That is the disqualifier: containment stops being by-construction and becomes
  argument-validation** — the exact regression our own first war-room self-finding warns about.
  **Tombstones compound it:** under `hydrate => false` or `weighted_shortest_path`, a tombstoned
  node's coordinates stay reachable until sync/vacuum folds it in, which breaks tombstone-as-
  governance-guarantee independently of RLS. Credits where due: `graph.build()` **fails closed** on
  RLS-enabled tables by default (`graph.allow_rls_tables = off`, `PG021`), **no query function is
  `SECURITY DEFINER`** (no escalation on the traversal edge), `LEAKPROOF` appears nowhere (correct),
  and the docs are **extensively explicit** about all of this rather than silent. Crate list confirmed
  zero-ML (**two additions to our record: `thiserror`, `serde_json`**); `superuser = true` /
  `trusted = false` confirmed; **prebuilt attested GHCR images exist for PG14–18**, which removes the
  from-source pgrx build cost we feared — but there is **no documented air-gapped path**, so we would
  mirror GHCR ourselves. **Verdict: adoptable behind an ADR for operator-plane analytics only —
  never on the agent-facing memory read path**, and note that it puts a new superuser-installed C
  extension inside the same Postgres that holds the audit chain, which is its own blast-radius
  conversation. *Caveats on the research: `main` was read at 2026-08-10 without pinning a SHA, and
  the exact default-`hydrate` filtering behaviour is an **assessment, not a verified fact** — re-pull
  `administration-and-security.mdx` and the `page.retain` logic directly before it goes into an ADR.*

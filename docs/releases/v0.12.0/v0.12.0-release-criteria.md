# v0.12.0 — Release Criteria

Status: **Accepted — 2026-08-02** (v0.12 "Access & Onboarding" scoping consult; the eleven decision
points D1–D11 that this document implements were CEO-ratified on the war-room recommendation). The
single architecture ADR it depends on (**ADR-0068 — Paired operator sessions**) is **Accepted**;
acceptance of *this* document fixes the release intent. Future changes to this document require a new
ADR (criteria drift is a load-bearing decision — the v0.1.0–v0.11.0 rule).

Owner: War Room Commander (synthesis); Permission Model Reviewer (the paired-session tier, the
`approvals@1` scope, the WD-11 negative leg); Security Reviewer (the pairing mechanism, the
off-by-default posture); Frontend Lead (the `Button` tier, the mobile approval surface, the consent
dialog); Offline/Install Owner (the deployment profile and its installer assertion).

This document defines what shipping **v0.12.0 — "Access & Onboarding"** means. Every criterion is
*pass* (must be true), *block* (presence stops release), or *deferred* (explicitly out of scope, with
the trigger that promotes it back). The criteria are the exit gate for every v0.12.0 ticket: a ticket
is "done" when it closes one or more criteria here and breaks none.

**New criteria family minted this release: `ONB` (onboarding).** Every other family continues its
existing ladder (SEC-34…, GOV-12…, AUD-32…, FE-36…, OI-21…, PERF-12…, DOC-23…, CON-3). Deployment
profiles deliberately do **not** get a new family — they are install-level and belong to `OI`.

## 1. Scope of v0.12.0

v0.12.0 is the **second of the three-release Beta-1 path** ratified 2026-07-24
(`docs/requirements/epic_story_catalog_v4.md` §Part 4): **v0.11 Operator Experience → v0.12 Access &
Onboarding → v1.0 MVP Beta 1**. Where v0.11 fixed defects and added no capability, v0.12 is **the
release that adds surfaces** — deliberately, so that the release which freezes the API adds nothing.

It delivers four epics, and it is **the fattest release on the path**:

- **E-02 — Operator mobile & QR pairing (REQ-001, B-015, gap G1).** An **unmet P0 promise**: REQ-001
  names "browser/**mobile**" and mobile was never built. Ships as **paired operator sessions** — the
  first revocable session in the product (ADR-0068 §D4) — narrowed to the approval surface
  (`approvals@1`, §D5) and **disabled by default** (§D10).
- **E-03 — Deployment profiles (REQ-002, B-016, gap G4) — P0 gap.** The topology spec requires that
  "all documentation and installers must identify which profile is active"; **`install.sh` has no
  profile concept — verified at this consult.** Ships as a required profile flag plus an **enforced
  installer assertion**, and adopts **no ZTNA dependency** (§D1).
- **E-04 — First-run onboarding (REQ-022, B-017, gap G3).** No first-run experience exists. Ships as a
  checklist **derived from live state** (no flag, no migration) plus a demo path whose target is the
  **installed host itself** (§D8).
- **E-05 — Consent surface (B-018, gap G5) — design-gated, split.** **E-05a `Button`** (a defect on
  already-shipped functionality — no button in the product has a hover or active state) is **not
  droppable**. **E-05b `ConfirmDialog`** is the **designated drop candidate** (§D3).

**Hard constraints (the release's defining posture).** v0.12.0 adds **no capability edge**, no actor
class, no credential path, no egress path, and **no agent-plane change of any kind** — the
`mcp-gateway` stays keyless (SEC-20), ADR-0053's sole-decrypt-authority posture is untouched, and both
agent read planes (`agent-memory`, `agent-workspace`) are byte-unchanged. It adds **no new
third-party dependency**: the QR encoder and the confirm dialog are both vendored (§D7).

**What it *does* add, enumerated so nothing is smuggled:** one api migration (0016), two env vars
(`AIREOS_DEPLOYMENT_PROFILE`, `AIREOS_PAIRING_ENABLED`), four new API routes plus one additive field
on `/v1/auth/me`, one new token tier (`PairedTTL`), three new audit outcomes, and two new
`packages/ui` components.

**The zero-install-wiring-diff criterion that held for v0.9–v0.11 cannot hold here and is not
claimed** (§9, OI-21) — it is replaced by an explicitly enumerated diff.

**Out of scope** (→ §14): generalizing revocation to all operator sessions; `vpn-first`/`dmz-first`
proven end-to-end; adopting any ZTNA dependency; mobile beyond the approval surface; Radix adoption;
push notification to the paired device; multi-device policy.

The wedge is **an operator who installs the stack under a declared profile, is walked to a first
governed action without reading source, pairs a phone with a QR code, approves from that phone, and
revokes it from the desk.**

## 2. The gate — WD-11 for pairing only (structural rule #2, re-tested)

**v0.12.0 mints exactly one new walkthrough demo.** Under the ratified structural rule — *a new WD-N
is minted **only** when a release adds new governed capability, not once per release out of habit* —
one of the four epics qualifies. This was **re-tested against the as-built at the scoping consult, not
inherited** (ADR-0068 §D9):

| Epic | New governed capability? | |
|---|---|---|
| **E-02 pairing** | A new session type, a new token tier, the **first revocation primitive**, and a new consent-bearing act (pairing a device). | **Yes → WD-11** |
| E-03 profiles | An install-time env var and an installer assertion. No route, edge, actor, token, or consent moment. | **No** → rides `task wd1` |
| E-04 onboarding | A checklist derived from existing reads; the demo resource is created through the **existing** governed path. | **No** |
| E-05 consent surface | Presentation of gates that already exist; **consent copy is byte-unchanged**. | **No** |

**The gate is therefore:**

- **GATE-1 — WD-11 green on both stacks, with its negative leg.** The full pairing walkthrough
  (request → QR → redeem → approve from the paired session → revoke from the desk) green on the
  Dockerized compose stack (`task e2e`) **and** on the installed privileged-systemd stack
  (`task wd1`). The audit chain verifies intact end-to-end.
- **GATE-2 — Full WD regression.** **WD-1 … WD-10 all green** on both stacks. The audit chain
  verifies intact.
- **GATE-3 — Browser smoke green** (`task smoke`, all cases), including the new pairing, Button, and
  (if E-05b ships) consent-dialog assertions.
- **GATE-4 — CEO §human walkthrough, on a fresh install.** Driven live in a real host browser (the
  Windows-host route recorded in the v0.9.0–v0.11.0 runbook Step 6), covering:
  1. **First-run from an un-seeded stack** — the checklist appears, walks to a working operator +
     resource, and the demo path completes **one real governed action** end to end.
  2. The installed stack **reports its active deployment profile** in the cockpit.
  3. **Pairing**: enable it, render the QR, redeem it on a real phone (or a second browser profile),
     **approve a held invocation from the paired session**, then **revoke that session from the desk**
     and watch the phone lose access.
  4. **Buttons have hover and active states** across the routes, and (if E-05b ships) the six consent
     gates render the product's own modal rather than a native `window.confirm`.

**Why GATE-4 is on a fresh install and not a seeded one.** Every gate this product owns starts from a
*provisioned* stack, and `task smoke` runs against a seeded backend — but a first-run experience is
**by definition** about the un-seeded state. Rather than mint new ceremony, the §human leg runs on the
stack `task wd1` already builds from scratch (ADR-0068 §D9).

**Regression posture.** WD-4 and WD-6 are **elevated**: WD-4 owns the keyless-gateway/token-forgery
negatives that a new token tier could weaken, and WD-6 owns the delegation-grant revocation cascade
whose shape §D4 reuses. WD-1 is elevated because install wiring changes for the first time since
v0.5.0.

## 3. Deployment profiles (must-pass)

- **OI-21 — The profile is required and persisted.** `install.sh` requires
  `AIREOS_DEPLOYMENT_PROFILE ∈ {lan-only, vpn-first, dmz-first}` (prompt-or-env per ADR-0051) and
  persists it in `aireos.env`. An absent or unrecognised value **fails the install loudly** — it never
  defaults silently. *(This closes the topology spec's own clause: "all documentation and installers
  must identify which profile is active.")*
- **OI-22 — The assertion is enforced, not documented.** `install.sh` **refuses** `vpn-first` or
  `dmz-first` when `AIREOS_SITE_ADDRESS` is unset, `localhost`, or a loopback literal, with a message
  naming the profile and the conflict. **A unit test proves the refusal** — no VPN is stood up.
  *(block if violated — a profile that is only a label fails the requirement it exists to close.)*
- **OI-23 — Idempotence preserved.** Re-running `install.sh` with an unchanged profile is a no-op;
  changing the profile on a re-run updates `aireos.env` and re-asserts OI-22. ADR-0051's idempotence
  guarantee is not weakened.
- **OI-24 — The stack reports its profile.** `GET /v1/auth/me` carries the active profile as an
  **additive** field, and the cockpit displays it. **No new route** is minted before the E-06 freeze,
  and **no audit event** is chained for it *(a static installation property is not a governed action;
  chaining one would manufacture the content-free volume ADR-0067 §D3 exists to stop)*.
- **OI-25 — Verification depth is stated honestly.** `lan-only` is proven end-to-end by `task wd1`.
  `vpn-first` and `dmz-first` carry a **documented support statement** plus OI-22's assertion, and the
  release notes **do not claim** to have tested a topology that was not stood up.
  *(block if violated — overclaiming here is the failure mode the whole profile exercise exists to
  correct.)*
- **OI-26 — No ZTNA dependency.** NetBird, OpenZiti, Pangolin and Headscale are **not adopted**;
  `task licenses` shows no new dependency from E-03. They remain Tier-1 watch items.

## 4. Paired sessions — security (must-pass)

- **SEC-34 — Revocation is real and checked per request.** A paired session's liveness is verified
  against its `paired_sessions` row on **every** request, not at mint time. A **revoked** session and
  an **expired** session are both refused. *(block if violated — this is the criterion the whole
  release turns on.)*
- **SEC-35 — The scope denies, and the denial is proven.** A live paired session is **refused**:
  launching a Run, issuing or revoking a grant, registering or removing a context source, minting an
  agent token, and opening a terminal session. WD-11's negative leg asserts the **denials**, not only
  the permissions. *(block if violated — SEC-21's precedent: a capability claim is proven by what it
  refuses.)*
- **SEC-36 — `approvals@1` is single-sourced and versioned.** The scope's membership is defined in
  **one** place in `services/api` — not in the frontend, not in the database, not in a migration — and
  is enumerated here: **read pending approvals/invocations · approve/deny · read the audit surface ·
  read its own session**. Widening it is a criteria change and therefore requires a new ADR.
- **SEC-37 — No credential ever crosses the pairing channel.** What crosses is a one-time secret
  exchanged for a narrower session. The operator password, `AIREOS_PASETO_KEY`,
  `AIREOS_RESOURCE_SECRET_KEY`, and every connector credential are untouched; ADR-0053's sole-decrypt
  authority is not on this path. *(block if violated)*
- **SEC-38 — The paired session cannot reach another service.** It exists on the `services/api`
  operator plane only; `packages/go/middleware`'s `RequireCapability` gains **no database
  dependency**, and `session-broker` / `policy-service` / `connector-service` / `audit-service` /
  `mcp-gateway` are byte-unchanged. *(block if violated)*
- **SEC-39 — No sliding refresh on the paired plane.** `PairedTTL = 8h` with **no** server-side cookie
  rotation: the paired session expires hard and must be re-paired. The desktop plane's ADR-0047
  sliding refresh is unchanged.
- **SEC-40 — The agent plane is untouched.** SEC-20 holds (the gateway remains keyless of the cluster
  key); no agent token, edge, or in-flight cap changes; WD-4's negative leg stays green.
  *(block if violated)*
- **SEC-41 — Off by default.** `AIREOS_PAIRING_ENABLED` defaults to **off**, and `install.sh` writes
  it off. With pairing disabled the routes answer **404** (no oracle, per the ADR-0065/0066
  precedent) and the QR affordance is hidden by capability, not by CSS.

## 5. Pairing mechanism & audit (must-pass)

- **GOV-12 — The pairing secret is single-use and short-lived.** 32 bytes of entropy, **hashed at
  rest** (the plaintext is returned exactly once and never stored), `expires_at = now + 120s`, and
  **consumed in the same transaction** as the redeem. A failed-attempt cap consumes the request.
  *(block if violated)*
- **GOV-13 — The secret never reaches the server in a URL.** It rides the **URL fragment**, which
  browsers do not transmit; the SPA reads it in JS and posts it deliberately. A live assertion
  confirms the secret appears in **no** access log line and **no** `Referer`. *(block if violated)*
- **GOV-14 — Pairing is a consent-bearing act with an operator-visible record.** The desktop cockpit
  **lists** live paired sessions (label, created, expires) and can revoke any of them. Logout from the
  paired session revokes its own row.
- **AUD-32 — Three events, chained.** `pairing.requested`, `pairing.redeemed`, `pairing.revoked` —
  each chained in the same transaction as the state change it records, actor = the operator, edge
  `human-agent`, target `pairing:<id>` / `paired-session:<id>`.
- **AUD-33 — No lifecycle noise is manufactured.** There is **no `pairing.expired` event** and **no
  expiry-sweep event**. An unredeemed request that lapses chains nothing. *(block if violated —
  ADR-0067 §D3 conformance: a reaper chaining one event per lapse is exactly the content-free ticker
  volume v0.11 was spent eliminating.)*
- **AUD-34 — An approval from a paired session is attributable as such.** The `invocation.approved` /
  `invocation.denied` events carry enough provenance to distinguish a desk approval from a paired-
  device approval, without leaking the pairing secret or the raw session id into the record.

## 6. Contract & codegen (must-pass)

- **VER-2 — Zero codegen drift.** `task codegen` is byte-deterministic (prove: copy, re-run, diff
  empty) across `services/{api,audit-service}/internal/server/gen.go` and
  `packages/shared-types/src/generated/openapi.ts`.
- **CON-3 — Fragment discipline, with the T-106 lesson applied.** The new routes and parameters are
  **new named components**. **`LimitParam`, `CursorParam` and `PageMeta` are not edited** — `PageMeta`
  is referenced by seven operations, and v0.11's T-106 established that the shared-component trap
  exists in **schema** form, not only in parameter form. *(block if violated)*
- **CON-4 — Additive only.** No existing operation, parameter, schema, or response shape is removed or
  narrowed. The `/v1/auth/me` profile field is additive. **This is the last growth of the API surface
  before the E-06 freeze.**

## 7. Frontend (must-pass)

- **FE-36 — `Button` exists and has states.** `packages/ui` exports a `Button` with variants
  `default` / `primary` / `destructive` / `ghost` and **hover, active, `focus-visible`, and disabled**
  states. Tokens come from the existing Tailwind theme; **no new design token is minted.**
- **FE-37 — The affordance defect closes across the product.** Every `<button>` in `apps/web` that
  presents as a button uses the component. The existing link-styled idiom is preserved as `ghost` so
  the migration is **not also a visual redesign**. *(As-built: 48 buttons across 9 routes, none with a
  hover or active state.)*
- **FE-38 — The approval surface is usable on a phone.** The paired session's routes render and
  function at a 375px viewport: an operator can read a held invocation's command, approve, and deny
  without horizontal scrolling. **A Playwright assertion runs at a mobile viewport** — the smoke suite
  gains a mobile project alongside `Desktop Chrome`.
- **FE-39 — The QR is rendered from vendored code.** No npm QR dependency; the encoder is vendored
  into `packages/ui` with its provenance and licence recorded. *(ADR-0068 §D7)*
- **FE-40 — Consent copy is byte-unchanged.** If E-05b ships, all six migrated sites
  (`Memories.tsx` redact + share, `Runs.tsx` plan approve, `Workstreams.tsx` share + context-source
  register + remove) carry **identical copy** to their `window.confirm` predecessors. Only the
  presentation changes. *(block if violated — changing a consent gate's words while restyling it
  would make the re-verification meaningless.)*
- **FE-41 — The dialog is accessible.** `role="alertdialog"`, `aria-labelledby` / `aria-describedby`,
  focus trap, Escape and backdrop-click cancel, and **initial focus on the safe action** for
  destructive confirms.
- **FE-42 — Browser-rendered evidence.** Per the project DoD, every `packages/ui` / `apps/web`
  rendering change ships with browser-rendered evidence (a screenshot or a passing Playwright
  assertion against the rendered DOM). **jsdom unit tests do not satisfy this.** *(The consent
  surfaces are the specific reason: the Claude Desktop Browser pane auto-dismisses `window.confirm`,
  so today these six gates are untestable in-pane — E-05b makes them testable, which is a gate
  improvement, not polish.)*
- **FE-43 — Design-system preflight.** No ad-hoc component; existing tokens, components, variants and
  accessibility rules are identified before any new UI is written
  (`../agency-kit/ai/core/design-system-governance.md`).

## 8. Onboarding (must-pass)

- **ONB-1 — The checklist derives from live state.** First-run status is computed from real
  conditions (is there a resource? a connector credential? has a governed action completed?), **not**
  from a stored flag or a new column. **No migration is added for onboarding.** *(Derived state cannot
  go stale and cannot disagree with reality.)*
- **ONB-2 — Dismissal is per-browser, not server state.** Hiding the panel uses `localStorage`; the
  server records nothing about whether an operator has "finished onboarding".
- **ONB-3 — The demo path reaches a real governed action.** The seeded demo target is a **loopback
  resource — the installed host SSHing to itself** — and the demo action traverses the **real**
  policy → approval → connector → broker chain, chaining real audit events. *(An air-gapped
  single-host install cannot conjure a second machine; a demo that requires one is a prerequisite, not
  a demo.)*
- **ONB-4 — The demo creates nothing privileged.** The loopback resource is created through the
  existing operator-governed path with no new capability, no policy exemption, and no bypass. It is
  **removable** through the existing surface. *(block if violated)*
- **ONB-5 — Quickstart reaches a governed action without reading source.** `docs/` gains a quickstart
  that takes an operator from an installed stack to a completed governed action using only documented
  commands and the cockpit.
- **ONB-6 — Reference MCP client (S-16) — deferred/cut (T-119, VER-10).** A minimal MCP client that
  exercises the agent plane without the reader writing one. **Cut by recorded CEO decision**: shipping a
  *supported* client artifact immediately before the E-06 API freeze creates a compatibility obligation
  the freeze would then have to honour. See §14 for the promotion trigger.

## 9. Offline install & operability (must-pass)

- **OI-27 — The install-wiring diff is enumerated, not zero.** `git diff v0.11.0 HEAD -- install.sh
  systemd/ Caddyfile` is **non-empty by design**, and its entire content is: two env vars
  (`AIREOS_DEPLOYMENT_PROFILE`, `AIREOS_PAIRING_ENABLED`) and the OI-22 assertion. **No new systemd
  unit, no new port, no new key material, no Caddyfile change.** Anything else in that diff is a
  finding. *(block if violated — this replaces the zero-diff criterion that held v0.9–v0.11, which
  cannot hold in a release that changes install-time configuration.)*
- **OI-28 — One migration, on `services/api` only.** Migration **0016** adds `pairing_requests` and
  `paired_sessions`. `audit-service`'s forward-only schema is **untouched**. No other service gains a
  migration. *(block if violated)*
- **OI-29 — Bundle budget holds.** The offline bundle rebuilt from HEAD stays within the OI-4 budget
  (v0.11.0 baseline: 116 MB / 42 MB).
- **OI-30 — No new dependency.** `task licenses` shows **zero** new third-party dependency —
  frontend or backend. The QR encoder and the dialog are vendored with recorded provenance.
  *(block if violated)*
- **OI-31 — Upgrade from v0.11.0 is clean.** An existing v0.11.0 install upgraded by re-running
  `install.sh` acquires the profile (prompted or env-supplied) and pairing-off, applies 0016, and
  keeps every existing key, operator, and row. *(ADR-0051 idempotence.)*

## 10. Performance & resource safety (must-pass)

- **PERF-12 — The liveness check is bounded and indexed.** The per-request paired-session read is a
  single indexed primary-key lookup. **A desktop session takes no new read** — a token with no paired
  `jti` skips the check entirely, so the existing operator plane's per-request cost is unchanged.
- **PERF-13 — Expired rows do not accumulate unboundedly.** Consumed and expired `pairing_requests`
  are cleaned up on a bounded schedule **without chaining an audit event** (AUD-33). The cleanup is
  best-effort: failing to clean up never fails a request.

## 12. Verification & gates (VER)

- **VER-2** — codegen drift zero (§6).
- **VER-6 — G1 (live cross-boundary test).** Every ticket names the live test that proves its claim
  before sign-off; a mocked boundary does not satisfy it. **SEC-34** (revoked and expired sessions
  refused), **SEC-35** (out-of-scope actions refused), **GOV-12** (single-use redeem under a
  concurrent second attempt), **OI-22** (the installer refusal), **ONB-3** (the demo action reaches a
  real governed terminal state), and **FE-38** (the mobile-viewport approval) are the release's named
  live tests.
- **VER-7 — G2 (ADR divergence).** ADR-0068 records **one declared divergence** (ADR-0046's stateless
  TTL tiers). ADR-0046 is **not edited**. Any further Accepted-ADR contradiction found during
  implementation is flagged at decision time → conform or file a **new** ADR.
- **VER-8 — Diff budget.** ≤12 files / ≤500 LoC per ticket unless explicitly approved (generated
  `gen.go`/`openapi.ts` and SQL count but are mechanical).
- **VER-9 — Commander review gate.** Every implementer diff is Commander-reviewed against G1/G2 before
  `main` is fast-forwarded; **only the Commander advances `main`**.
- **VER-10 — Drop decisions are explicit.** If a droppable item (ONB-6, then E-05b) is cut, it is cut
  **by a recorded CEO decision**, the affected criteria flip to *deferred* with a trigger in §14, and
  the release notes say what was cut and why. A silent drop is a release-criteria violation.

## 14. Deferred (with promotion triggers)

| Item | Trigger that promotes it |
|---|---|
| **Generalized session revocation** (making desktop `logout` real for every operator session) | The natural sequel to SEC-34, deliberately out of v0.12: it would change the auth posture of every existing session in the release before an API freeze. Trigger: the **E-06 security-audit capstone**, or the multi-operator work (E-14/G14). Minted as a v1.x backlog row at DOC-24. |
| **`vpn-first` / `dmz-first` proven end-to-end** | A customer deployment on that topology. Documented + assertion-tested only (OI-25). |
| **Adopting NetBird / OpenZiti / Pangolin / Headscale** | **Declined for Beta-1**, not deferred pending analysis. They remain Tier-1 watch items under the standing decision filter; adoption would need its own ADR. |
| **Mobile beyond the approval surface** (terminal, Runs, charters on a phone) | **Rejected, not deferred** (ADR-0068 §D5). A future need requires arguing past the `approvals@1` narrowing. |
| **Radix UI adoption in `packages/ui`** | A component whose accessibility surface genuinely exceeds a hand-rolled implementation (a combobox or date picker would qualify; a confirm dialog does not). |
| **Push notification / out-of-band alerting to the paired device** | The obvious mobile follow-on and a SaaS-dependency trap on an air-gapped product. Not scoped. |

## 15. Ticket ladder (indicative; each JIT-authored with its own consult)

**Ordering rationale (ADR-0068 §D9/consult D8).** E-03 first because it changes `install.sh`, which
every later epic's verification rides on — doing it first means E-02 and E-04 are verified on the
profile-aware installer rather than retrofitted. E-02 second because it is the long pole (ADR,
migration, new middleware, WD-11) and a slip must be visible early. E-05a third because it unblocks
E-05b and lands the design-system decision **before** onboarding builds UI on it. E-04 fourth because
it *consumes* everything above and should document the real thing once. E-05b last, so dropping it
costs nothing already built.

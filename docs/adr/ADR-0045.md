# ADR-0045: Event bus at P0 — no broker; Postgres transactional outbox with sync HTTP ingest into `audit-service`; NATS JetStream held as the P1 reserve pick

## Status
Accepted — 2026-05-17.

## Context

ADR-0041 established Go as the primary backend language with single-static-binary deploy, a tight supply-chain surface, and a capability-edge permission model. ADR-0042 established Go workspaces + pnpm workspaces + Taskfile as the monorepo tooling. ADR-0043 established `go-chi/chi` v5 on `net/http` as the HTTP framework with `oapi-codegen` for schema-first server stubs and `packages/go/middleware/` as the shared-infra module shape. ADR-0044 established `golang-migrate/migrate` v4 in library mode, embedded per service via `embed.FS`, with a shared runner in `packages/go/migrate/`; Postgres is the assumed relational store.

This ADR picks the event-bus strategy for P0 and explicitly answers the open question in `docs/deep-dive/30-open-questions-and-research-backlog.md` *"PostgreSQL event table vs dedicated event store"*.

The decisive constraints are inherited:

1. **Self-hosted / offline-first** (ADR-0001). Any broker daemon must mirror cleanly into the offline installer. SaaS-hosted brokers are out.
2. **Single static binary per service + tight supply chain** (ADR-0041). Every broker adds an installer artifact, a release-guard surface, and a security-review surface.
3. **Capability-edge model** (`docs/security/agent-permission-model.md`). Every cross-service interaction is a capability edge. The `audit-service` writes are append-only and chained-hash; its ingest path is the chain authority for the whole product.
4. **P0 ship velocity** (ADR-0041, ADR-0042). Bringing up a broker daemon is a ticket; doing without one ships faster.
5. **Diff budget ≤12 files / ≤500 LoC per ticket** (`CLAUDE.md`).

Inventory of P0 cross-service flows by shape:

| Flow | Shape | Notes |
|---|---|---|
| `api` → `policy-service` (allow?) | sync RPC | command, not event |
| `api` → `connector-service` (credential lease) | sync RPC | command, not event |
| `api` → `audit-service` (evidence) | **event, fan-in** | chained-hash sink |
| `session-broker` → `audit-service` (lifecycle) | **event, fan-in** | chained-hash sink |
| `policy-service` → `audit-service` (decisions) | **event, fan-in** | chained-hash sink |
| `connector-service` → `audit-service` (egress decisions) | **event, fan-in** | chained-hash sink |
| Approvals to humans | poll / UI | not bus-shaped at P0 |

P0 has **one** event-shaped flow: producers fan-in to `audit-service`. There is no P0 pub/sub, no multi-subscriber fan-out, no stream replay, no time-travel debugging requirement. Every other cross-service call is RPC.

The decisive sub-questions for this ADR are therefore not "NATS vs Redis vs Kafka." They are:

1. Does P0 actually need a separate event bus at all, or can the vertical slice ship with HTTP-only inter-service calls plus a durable producer-side outbox?
2. Is `audit-service` ingest synchronous HTTP append-only, or is `audit-service` a subscriber on an event bus?
3. If we adopt durable handoff, transactional outbox in the producer or direct broker publish after commit?
4. If/when a broker is adopted, one broker for the cluster or per-service brokers?
5. Where does the shared client code live in `packages/go/*`?

## Decision

- **No dedicated event bus at P0.** Cross-service commands stay over HTTP. The single event-shaped flow — evidence fan-in to `audit-service` — is handled by the transactional outbox pattern with sync HTTP append-only ingest.
- **`audit-service` ingest is sync HTTP append-only.** A chi handler at `POST /v1/events` (instrumented by `packages/go/middleware/` per ADR-0043) accepts evidence packets, dedupes by `idempotency_key`, extends the chained-hash, and returns 200 only after commit. `audit-service` is the chain authority and is **not** a bus subscriber.
- **Every producer service writes to a local `outbox` table** in its own Postgres database **inside the same transaction** as its state change. This eliminates the dual-write problem by construction.
- **A relay loop drains the outbox** and POSTs each row to `audit-service` with the `idempotency_key`, marking the row delivered on 200. The relay uses Postgres `LISTEN/NOTIFY` to wake promptly instead of busy-polling, with a fallback periodic sweep for missed notifications. The relay runs as an in-process goroutine started from `main.go` and is also exposed as a `<service> outbox relay` subcommand for operator control — same precedent as the `migrate` subcommand from ADR-0044.
- **Shared infrastructure module: `packages/go/outbox/`** under `go.work`. Exposes `Writer.Enqueue(ctx, tx, event)` and `Relay.Run(ctx, cfg)`. Same shape as `packages/go/middleware/` (ADR-0043) and `packages/go/migrate/` (ADR-0044). The `audit-service` HTTP client is a small typed wrapper, ideally generated from `docs/api-contracts/openapi.v3.fragment.yaml` by `oapi-codegen` (client mode).
- **Outbox schema is per service**, governed by that service's own migrations under ADR-0044. A canonical outbox migration template ships alongside `packages/go/outbox/` for new services to copy.
- **Delivery semantics: at-least-once.** `audit-service` deduplicates by `idempotency_key` (UUID v7 generated when the row is enqueued). Producers are not required to wait for the relay to confirm before returning to their caller; the chained-hash extension at `audit-service` is the integrity boundary.
- **No boot-time draining gate.** Services start serving HTTP traffic immediately; the relay starts in parallel. An unhealthy `audit-service` does not block the producer's startup, but does eventually surface as monotonically growing outbox lag (exported as a metric).
- **No `LISTEN/NOTIFY`-as-bus.** `LISTEN/NOTIFY` is used only as a wakeup hint for the outbox relay; it is not the transport. The transport is HTTP. This avoids relying on LISTEN/NOTIFY's transient, no-replay semantics for integrity-bearing events.

`pressly/goose`-style direct-publish, NATS Core, NATS JetStream at P0, Redis Streams, Kafka/Redpanda, and pure `LISTEN/NOTIFY`-as-bus are rejected at P0 under defined review triggers below. **NATS JetStream is held as the named P1 reserve pick** for the day a real fan-out flow lands.

## Alternatives considered

### A. Postgres `LISTEN/NOTIFY` as the event bus
Rejected.
- Pros: zero new infrastructure; reuses the Postgres instance ADR-0044 already commits to.
- Cons: `LISTEN/NOTIFY` is transient — payload is delivered only to currently-connected subscribers; no persistence, no replay, no consumer groups. A disconnected subscriber misses events forever. For integrity-bearing audit evidence that is a complete loss-of-data failure mode. Payload size capped at 8000 bytes (default `NAMEDATALEN`-bounded), which is on the order of one evidence packet header.
- Decisive: incompatible with at-least-once delivery for the chain authority. Kept in scope as a wakeup hint for the outbox relay only, never as the transport.

### B. Postgres + transactional outbox (adopted)
See *Decision*. Net-of-stdlib supply-chain delta: zero new runtime dependencies — `pgx`'s `LISTEN/NOTIFY` is already part of any Postgres driver the services will use under ADR-0044. Same Postgres instance, same migration tool, same backup/restore story.

The outbox pattern is the textbook answer to the dual-write problem and is the only shape that:
- Holds the chained-hash invariant under producer crashes between "state changed" and "evidence emitted."
- Survives `audit-service` outages without losing evidence.
- Lets the chain authority remain the only thing that knows `prev_hash`.
- Ships with no new daemon.

### C. NATS Core
Rejected at P0.
- Pros: single small Go binary broker; ergonomic pub/sub; first-class Go client; trivial offline install.
- Cons: no persistence. Subscribers that are down miss messages forever. Same loss-of-evidence failure mode as `LISTEN/NOTIFY`-as-bus. NATS Core's design assumption is "subscribers are present and connected"; integrity-bearing audit fan-in violates that assumption.
- Decisive: at-least-once delivery requires JetStream, not Core.

### D. NATS JetStream
Rejected at P0; **held as the named P1 reserve pick.**
- Pros: single Go binary broker; persistent streams with at-least-once + exactly-once (consumer-side dedup) modes; consumer groups; KV + object stores in the same daemon; strong Go client; clean offline install; clusterable.
- Cons:
  - One more daemon to babysit in restricted-network deploys, with its own auth surface, persistence directory, backup/restore procedure, and supply-chain surface.
  - At P0 there is one fan-in flow and one consumer (`audit-service`). The broker adds a network hop, an auth boundary, and a "trust-the-broker" leap between the producer and the chain authority that the chained-hash design specifically does not want.
  - The relay-in-producer code that the outbox pattern needs is ~80 LoC and shares no logic with the JetStream client we would otherwise import. Buying JetStream now does not delete that code.
- Decisive: premature for P0 — pays operational tax for zero P0 benefit. Adopt the day a real fan-out flow lands. See *Review triggers*.

### E. Redis Streams
Rejected.
- Pros: durable streams with consumer groups; widely deployed.
- Cons: introduces Redis as a new daemon when the project does not already need it (Postgres covers state + outbox). Redis adds a separate persistence story (RDB/AOF) with its own backup/restore semantics, on top of Postgres's. The historical justification for adding Redis is caching or session storage, neither of which is on the P0 wedge.
- Decisive: adds a daemon for an event-bus role that JetStream would fill better when the time comes. Not held in reserve.

### F. Kafka / Redpanda
Rejected — hard out for P0.
- Pros: industry-standard log; strongest replay and time-travel; mature tooling.
- Cons: operational burden is wildly disproportionate to a one-flow fan-in. Kafka needs ZooKeeper or KRaft and a non-trivial broker config; Redpanda is single-binary but still a meaningful daemon with cluster-aware operations. Supply-chain surface is large. Offline install is workable but expensive.
- Decisive: overkill by 1-2 orders of magnitude. If event sourcing or stream replay ever becomes a product requirement (it is not on the P0 wedge), revisit then. Even then, JetStream covers most needs; Kafka/Redpanda only enters if log-as-store semantics become load-bearing.

### G. In-process channels only — no cross-process event bus at P0 (the "do nothing" option)
Rejected as stated; the **adopted decision is G′**, a strict superset: HTTP-only inter-service calls, plus a Postgres outbox in the producer for durable evidence handoff.
- Pros of pure G: zero new code, zero new tables.
- Cons of pure G: re-introduces the dual-write problem the outbox is designed to eliminate. A producer crash between "tx committed" and "POST /v1/events succeeded" loses evidence. For integrity-bearing audit data that is unacceptable.
- Decisive: outbox is the smallest delta that preserves the chained-hash invariant under producer crashes. ~80 LoC of relay code is worth it.

### H. Direct HTTP publish to `audit-service` after commit, no outbox
Rejected — same failure mode as G.
- Producer commits state in tx, then POSTs to `audit-service`. If the producer crashes between commit and POST (or the POST fails permanently), evidence is lost.
- Decisive: dual-write. The outbox eliminates this by colocating the evidence enqueue inside the producer's tx.

## Decisive sub-questions — answers

### 1. Does P0 need an event bus at all? — No.
One fan-in flow (producers → `audit-service`) does not justify a broker. The right tool is a transactional outbox + sync HTTP ingest. Net-of-stdlib supply-chain delta: zero new runtime daemons, zero new client libraries.

### 2. `audit-service` ingest semantics — Sync HTTP append-only POST.
`audit-service` is the chain authority for the chained-hash evidence chain. It serializes writes, computes `prev_hash` in-process, and is the only thing that can preserve integrity. Putting a broker between producers and the chain authority does not change that — the chain authority is the choke point either way — and adds a "trust-the-broker" leap that the integrity model specifically wants to avoid. The ingest endpoint is instrumented by the shared `packages/go/middleware/` chain from ADR-0043 like any other capability-edge HTTP boundary.

### 3. Transactional outbox vs direct publish — Outbox.
The dual-write problem is real. Producer commits state in tx, then publishes — if the producer crashes between commit and publish, evidence is lost. The outbox eliminates this by enqueueing the evidence row inside the same tx as the state change. Cost: one new table per service, ~80 LoC of relay code in a shared module, one `LISTEN/NOTIFY` wakeup hint.

### 4. One broker or per-service brokers — N/A at P0.
When NATS JetStream is adopted at P1, **one broker for the cluster**, instrumented by capability-edge auth, with subject namespacing per producer service.

### 5. Where does the client code live — `packages/go/outbox/` at P0.
Outbox writer + relay live in `packages/go/outbox/`. The `audit-service` HTTP client lives either in a small typed wrapper or as `oapi-codegen` client output. When JetStream lands at P1, `packages/go/events/` becomes the pub/sub client package; `packages/go/outbox/` continues to live alongside it as the durable-handoff layer.

## Consequences

### Positive

- **No new daemon in the P0 offline installer.** Same Postgres ADR-0044 already commits to. One fewer thing to mirror, vet, authenticate, back up, and babysit.
- **Chained-hash integrity is preserved by construction.** Evidence row and state change commit in the same tx. The chain authority is the only thing that extends the hash, in-process, with no broker between producer and chain.
- **At-least-once with idempotent dedup at the sink.** `idempotency_key` (UUID v7) generated at outbox enqueue. `audit-service` dedupes on insert. Producer crashes between enqueue and POST are recovered by the relay's retry loop.
- **Supply-chain delta is zero new runtime daemons.** `pgx`'s `LISTEN/NOTIFY` is already in scope from ADR-0044.
- **The shared `packages/go/outbox/` module follows the established `packages/go/middleware/` (ADR-0043) and `packages/go/migrate/` (ADR-0044) shape.** Operators and contributors do not learn a new infrastructure pattern; same shape, third application.
- **The `<service> outbox relay` subcommand mirrors `<service> migrate` from ADR-0044.** Operators can run the relay out-of-process if a service's in-process relay needs to be paused for any reason.
- **Closes the deep-dive 30 open question** *"PostgreSQL event table vs dedicated event store"* in favor of Postgres event/outbox tables at P0, dedicated event store deferred (JetStream named reserve).

### Negative

- **No fan-out at P0.** If a P1 module needs multi-subscriber pub/sub (workstream engine, MCP gateway telemetry), the outbox does not give it. Mitigation: that day is exactly when JetStream is adopted, per the *Review triggers* below.
- **Relay lag is a real operational signal.** A degraded `audit-service` causes monotonically growing outbox row counts in every producer. Mitigation: outbox depth is exported as a metric; alert thresholds documented in the operator runbook (deferred to the first stateful-service ticket).
- **`LISTEN/NOTIFY` wakeup is not strictly necessary** but materially reduces evidence latency under load. If a Postgres deployment disables `LISTEN/NOTIFY` for any reason, the relay falls back to periodic sweeps. Mitigation: documented in `packages/go/outbox/README.md`.
- **Two evidence-shape sources of truth eventually.** When JetStream lands, some flows will be outbox→HTTP and some flows will be JetStream pub/sub. Mitigation: outbox→HTTP remains the canonical path for integrity-bearing fan-in into `audit-service` even after JetStream lands; JetStream serves multi-subscriber flows that are not the audit fan-in. Documented in the ADR that adopts JetStream.
- **No exactly-once illusion.** Producers cannot assume the relay has flushed before returning to their caller; `audit-service` is the integrity boundary, not the producer. Mitigation: explicit in the model — at-least-once + idempotent sink is the contract.

### Held in reserve

- **NATS JetStream** — adopt as the cluster's broker the day **any one** of these fires:
  - A real fan-out flow lands (workstream engine, MCP gateway tool-call telemetry, or any flow with ≥2 distinct subscribers).
  - Outbox relay lag exceeds a defined SLO (e.g., p99 > 60s under non-pathological load) across two customer environments.
  - A third subscriber on any single event class appears.
- **Postgres LISTEN/NOTIFY-as-bus** — not held in reserve as a real broker. Used at P0 only as a wakeup hint for the outbox relay.
- **NATS Core, Redis Streams, Kafka, Redpanda** — not held in reserve. If a broker is needed, JetStream is the destination.

## Verification

This ADR is verified once the following hold:

1. `packages/go/outbox/` exists as a Go module under `go.work` and exports a `Writer` (with an `Enqueue(ctx, tx, event)` method that requires a `*sql.Tx` or `pgx.Tx`) and a `Relay` (with a `Run(ctx, cfg)` method).
2. At least one stateful producer service (e.g., `services/policy-service` or `services/connector-service`) imports `packages/go/outbox/`, owns an `outbox` table created via its own migrations under ADR-0044, and writes evidence rows inside its state-change transaction.
3. `services/audit-service` exposes `POST /v1/events` over chi (per ADR-0043), dedupes by `idempotency_key`, extends the chained-hash in the same transaction as the row insert, and the integrity test from ADR-0041 §Verification passes under concurrent relay traffic.
4. Each producer service exposes `<service> outbox relay` as a subcommand and starts the relay as an in-process goroutine on `main.go` boot.
5. The deploy artifact remains a single static binary per service. No event-bus daemon ships in the offline installer for the P0 cut.
6. No service uses `LISTEN/NOTIFY` as a transport for integrity-bearing data; it is used only as a wakeup hint, with a periodic-sweep fallback documented.
7. Outbox depth is exported as a metric (deferred to the metrics ticket; documented here as a verification gap at P0 if metrics scaffolding does not land in the same milestone).

Known verification gap at P0:

- Outbox-depth alerting thresholds are documented but not yet wired into a runbook. P1 ticket.
- No CI lint enforces that producer services use the outbox for `audit-service` writes instead of direct HTTP POSTs. The rule is documented and review-enforced at P0; lint enforcement is a P1 ticket.

## Review triggers

Re-open this ADR if any of these become true:

- A real fan-out flow lands (≥2 distinct subscribers on one event class) → adopt **NATS JetStream**.
- Outbox relay lag exceeds an agreed SLO (p99 > 60s under non-pathological load) across two customer environments → adopt **NATS JetStream**.
- A `pgx` / Postgres `LISTEN/NOTIFY` supply-chain or correctness incident materially affects the relay wakeup path → re-evaluate the wakeup hint (the periodic-sweep fallback already covers correctness; the question becomes latency).
- A regulatory regime requires stream replay / time-travel semantics for evidence → revisit the chain-authority-only model and consider log-as-store options (JetStream first; Kafka/Redpanda only if log-as-store becomes load-bearing).
- The chained-hash integrity model is replaced or supplemented (e.g., a Merkle-tree variant) → revisit whether sync HTTP ingest remains the right shape.

## Output contract (per kit specialist-output format)

- **Scope**: event-bus strategy for P0 across the five named Go services; consumed by every stateful-service-implementation ticket from T-002 onward; explicitly answers the deep-dive 30 open question.
- **Findings**: P0 has one event-shaped flow (evidence fan-in to `audit-service`) and no fan-out. Chained-hash integrity makes `audit-service` the unavoidable serialization point regardless of transport; a broker between producer and chain authority adds latency and a trust leap without changing the bottleneck. Dual-write between producer state and audit log is the real hazard; the transactional outbox is the textbook fix. Offline-install + supply-chain + P0 velocity together rule out every broker at P0. JetStream is the right *eventual* broker when fan-out actually appears.

# ADR-0043: Go API framework — `go-chi/chi` on top of `net/http`, with `oapi-codegen` for schema-first server stubs

## Status
Accepted — 2026-05-17.

## Context

ADR-0041 established Go as the primary backend language and named `net/http` (stdlib) as the baseline with `chi`, `fiber`, and `echo` as the candidate third-party routers. ADR-0042 established Go workspaces + pnpm workspaces + Taskfile as the monorepo tooling; the API framework chosen here will live inside `services/*` Go modules under `go.work`.

P0 ships five Go services: `api`, `session-broker`, `audit-service`, `policy-service`, `connector-service`. Every one of them is a *capability-edge*: per `docs/security/agent-permission-model.md`, every cross-actor HTTP boundary must be instrumented for audit logging, permission gates, egress scope enforcement (`docs/security/egress-policy.md`), and approval workflows. The framework choice has to make that instrumentation *shared* across all five services — five copies of subtly-different audit middleware is a security regression dressed as DRY.

The product also runs schema-first: `docs/api-contracts/openapi.v3.fragment.yaml` is the canonical contract, and ADR-0041 named `oapi-codegen` as the verification-target codegen tool. The framework must serve generated server stubs without fighting the router. And every constraint from ADR-0001 (offline-first, no SaaS runtime), ADR-0041 (single static binary, tight supply chain), and ADR-0042 (mirror-trivially into a restricted-network installer) still applies.

The decisive sub-question is therefore not "which router has the fastest benchmark" — it is "which framework lets one capability-edge middleware library work uniformly across five Go services, with first-class `oapi-codegen` support, while staying `net/http`-compatible so future stdlib-only services can share the same middleware."

## Decision

- **HTTP router:** [`go-chi/chi`](https://github.com/go-chi/chi) v5. Mounted on top of `net/http`. One direct dependency: `github.com/go-chi/chi/v5`.
- **Server-stub codegen:** `oapi-codegen` configured with `generate: chi-server` against `docs/api-contracts/openapi.v3.fragment.yaml`. Generated code is committed (not regenerated at runtime). Generator invocation lives in `Taskfile.yml` (`task codegen`).
- **Middleware contract:** all capability-edge middleware (audit, permission, egress scope, approval, rate-limit) is written as `func(http.Handler) http.Handler` and lives in `packages/go/middleware/` (a shared Go module under `go.work`). Every service mounts the same chain.
- **Per-service shape:** each `services/*` Go module exposes one `func New(cfg Config) http.Handler` that returns a `chi.Mux`. The `main.go` binds it to `http.Server`. No custom router types leak across module boundaries.
- **No custom `Context` type.** Handlers take `http.ResponseWriter, *http.Request`. Per-request state rides on `context.Context` via typed keys. This keeps shared middleware framework-agnostic and audit-readable.
- **HTTP/2 + WebSockets:** served via stdlib `http.Server` (HTTP/2 by default on TLS) and `nhooyr.io/websocket` (or `gorilla/websocket` if the audit reviewer prefers the more-deployed option) for the session broker. Both are `net/http`-compatible; neither conflicts with chi.

`fiber` is rejected. `echo`, `gin`, `huma`, and pure stdlib `ServeMux` are held in reserve under defined review triggers.

## Alternatives considered

### A. `net/http` stdlib + `http.ServeMux` (Go 1.22+ pattern matching)
Rejected as the P0 router.
- Pros: zero third-party deps; smallest possible supply-chain surface; `net/http` is the lingua franca for middleware; `oapi-codegen` has a `stdlib` generator.
- Cons: no first-class route groups or sub-router mounting (manual `http.StripPrefix` + nested muxes per service segment), no middleware-composition sugar, no per-route middleware. Across five services the boilerplate cost is real, and each service hand-rolls a slightly different chain helper — exactly the divergence the capability-edge model is trying to prevent.
- Decisive: the win (one fewer dep) is dwarfed by the P0 cost of writing route-grouping and middleware-composition helpers ourselves for five services. Held in reserve for a future hardened module that wants zero non-stdlib deps for one specific service.

### B. `net/http` + `go-chi/chi`
**Adopted.** See *Decision*.
- Net-of-stdlib supply-chain delta: one small, MIT-licensed module (~3k LoC), zero non-stdlib runtime deps.
- `chi.Router` is an `http.Handler`. Middleware signature is `func(http.Handler) http.Handler`. Sub-routers and route groups are first-class. Per-route middleware is first-class.
- `oapi-codegen`'s chi backend is the most-travelled path; the generator project itself ships chi examples and tests against chi as the reference.
- Active maintenance; v5 has been stable since 2022; no breaking-change cadence problems.

### C. `labstack/echo`
Rejected.
- Pros: large middleware ecosystem; ergonomic; good `oapi-codegen` support.
- Cons: custom `echo.Context` and `echo.MiddlewareFunc` signatures. Capability-edge middleware bound to Echo's API does not compose with stdlib `http.Handler` middleware. Five services × Echo's context type = the shared `packages/go/middleware/` library is Echo-locked, and any future stdlib-only service has to duplicate audit/permission code. "Batteries included" is a larger supply-chain surface than chi for no net benefit at this scope.
- Decisive: framework-lock on the audit-edge middleware.

### D. `gin-gonic/gin`
Rejected.
- Pros: most-deployed Go web framework; high performance; `oapi-codegen` support.
- Cons: same custom-context lock-in as Echo. Larger transitive dependency tree (binding/validator libraries). Slower historical response on security/disclosure relative to chi and Echo. The "most popular" tiebreaker doesn't override the audit-edge composability constraint.
- Decisive: same framework-lock concern as Echo, plus a larger dep tree.

### E. `gofiber/fiber`
Rejected — hard out.
- Pros: very high raw throughput on synthetic benchmarks (fasthttp underneath); ergonomic API.
- Cons:
  - **Not `net/http`-compatible.** Built on `fasthttp`, which is a separate HTTP/1.1 stack with its own `Context`, its own middleware ecosystem, and no shared surface with stdlib. Every capability-edge middleware would have to exist in two flavors, or the project commits to fiber-only forever — including the session-broker.
  - **No HTTP/2 server support in fasthttp.** The session-broker hot path is exactly where long-lived multiplexed streaming matters most; choosing a stack that forecloses HTTP/2 there is a strategic miss.
  - `oapi-codegen` has no first-class fiber generator. Existing community workarounds are second-class and project-maintained outside the codegen tool.
  - Larger supply-chain surface (fasthttp + fiber's middleware galaxy).
- Decisive: breaks `net/http` compatibility AND the streaming story AND the schema-first codegen path.

### F. `huma`
Rejected for P0; held in reserve.
- Pros: schema-from-Go-types is genuinely good ergonomics at scale; runs on top of chi/stdlib/gin/fiber so it does not foreclose on the router choice; small, well-engineered.
- Cons: inverts the schema-first direction. `docs/api-contracts/openapi.v3.fragment.yaml` is the canonical contract; huma's pitch is to generate the OpenAPI *from* Go code. Adopting huma at P0 means either (a) accepting two sources of truth (the YAML and huma's generated spec) or (b) abandoning the YAML as canonical — neither acceptable mid-flight.
- Decisive: schema-direction conflict. Re-evaluated if the API surface grows past ~50 endpoints and type-first generation becomes a net win.

## Consequences

### Positive

- One shared `packages/go/middleware/` library serves all five P0 services with a single `func(http.Handler) http.Handler` signature — capability-edge audit, permission, egress, and approval gates are written once.
- `oapi-codegen --generate chi-server` is the most-travelled codegen path. CI invocation is a single Taskfile target; generated code is reviewable as a normal diff.
- Supply-chain delta vs. stdlib is one small MIT module. Mirror-trivial for offline install (`go mod download` populates the module cache, tarball ships with the installer per ADR-0042).
- No custom `Context` type means handlers, middleware, and tests stay portable. Future stdlib-only services (e.g., a hardened module per ADR-0041's reserve clause) share the same middleware library unchanged.
- `chi.Router` IS an `http.Handler`. Composition with stdlib (`http.StripPrefix`, `http.TimeoutHandler`, `http.Server`) and with stdlib-compatible WebSocket libraries is frictionless.
- HTTP/2 comes for free from `http.Server` over TLS; WebSocket libraries layer cleanly on the same listener.

### Negative

- Chi is effectively maintained by a small team. If the project becomes unmaintained or ships a breaking v6, the swap-out cost is real (mitigated: chi-flavored middleware is `net/http`-shaped, so the cost is router-only, not middleware-rewrite; `oapi-codegen` ships a stdlib generator as fallback).
- Codegen is bound to chi via `oapi-codegen.yaml`. Swapping is a one-line generator flag change for the stubs; handler signatures remain stable because they use stdlib types.
- Chi's per-route middleware ergonomics are powerful enough to encourage divergence between services if unreviewed. Mitigation: the canonical middleware chain is constructed by a single helper in `packages/go/middleware/`, and Permission Model Reviewer gates any service that deviates.

### Held in reserve

- **Pure `net/http` stdlib (`ServeMux`)** — adopt for a specific hardened module if ADR-0041's reserve clause fires and that module needs zero non-stdlib runtime deps.
- **`huma` on top of chi** — re-evaluate when the API surface grows past ~50 endpoints AND a clear net win from type-first OpenAPI generation appears.
- **`echo`, `gin`, `fiber`** — re-evaluate only if chi's maintenance posture deteriorates materially or if `oapi-codegen`'s chi backend regresses.

## Verification

This ADR is verified once the following hold:

1. `services/api/go.mod` declares `github.com/go-chi/chi/v5` as the sole router dependency.
2. `oapi-codegen` is wired via `Taskfile.yml` (`task codegen`) and produces a chi-server stub matching `docs/api-contracts/openapi.v3.fragment.yaml` that compiles cleanly inside `services/api`.
3. `packages/go/middleware/` exists as a Go module under `go.work` and exports at least one `func(http.Handler) http.Handler` (e.g., `RequireCapability`) that is consumed identically by `services/api`, `services/session-broker`, `services/audit-service`, `services/policy-service`, and `services/connector-service`.
4. No service imports a non-stdlib HTTP router other than `chi/v5`. No service defines a custom request-context type at the handler signature level.
5. `services/session-broker` serves at least one HTTP/2 endpoint and one WebSocket endpoint via stdlib `http.Server` + a `net/http`-compatible WebSocket library, with the same audit middleware chain applied.
6. Static analysis (`go vet`, `staticcheck`) and the kit's permission-model reviewer pass with the canonical middleware chain mounted.

## Review triggers

Re-open this ADR if any of these become true:

- `go-chi/chi` maintenance posture deteriorates materially (>12 months without release while issues accumulate, or a unilateral v6 with breaking changes).
- `oapi-codegen`'s chi generator regresses or is deprecated.
- The API surface grows past ~50 endpoints AND a concrete proposal for `huma` shows a measurable ergonomics win net of the schema-direction trade-off.
- A specific service needs zero non-stdlib runtime deps (hardened-module reserve clause from ADR-0041) — propose a per-service exception, not a wholesale swap.
- A supply-chain incident materially affects `chi`, `oapi-codegen`, or the chosen WebSocket library.

## Output contract (per kit specialist-output format)

- **Scope**: HTTP framework for all P0+ Go services; consumed by every service-implementation ticket from T-002 onward.
- **Findings**: capability-edge middleware composability across five services + schema-first `oapi-codegen` fit + `net/http` compatibility for streaming are the decisive axes. `chi` wins on all three. `fiber` loses hardest (breaks `net/http`, no HTTP/2 in fasthttp, no first-class codegen). `echo`/`gin` lose on framework-locked middleware. Pure stdlib loses on P0 velocity for route-grouping + middleware-composition boilerplate across five services. `huma` loses on schema direction.
- **Evidence**: `docs/api-contracts/openapi.v3.fragment.yaml` (canonical schema), `docs/security/agent-permission-model.md` (capability edges), `docs/security/egress-policy.md` (egress gates as middleware), ADR-0001 (offline-first), ADR-0041 (language + baseline candidates), ADR-0042 (monorepo + Taskfile orchestration).
- **Risks**: chi single-maintainer surface (LOW, mitigated by stdlib-compatible signatures making rollback cheap); codegen bound to one generator backend (LOW, one-flag swap); middleware divergence across services (LOW, mitigated by shared `packages/go/middleware/` and Permission Model Reviewer gate).
- **Recommendation**: `go-chi/chi` v5 on `net/http`, with `oapi-codegen` `chi-server` for stubs and a shared `packages/go/middleware/` module for capability-edge enforcement.
- **Confidence**: HIGH for chi as router; HIGH for `oapi-codegen` chi-server as codegen; MEDIUM-HIGH for the WebSocket library choice (final pick deferred to the session-broker service ticket); RESERVED for the "no huma at P0" call (explicit review triggers documented).
- **Hand-off notes**: T-002 (skeleton commit) does not need to land chi yet — the first service-implementation ticket should add `github.com/go-chi/chi/v5` to its `go.mod`, scaffold `packages/go/middleware/`, and wire `task codegen` to `oapi-codegen.yaml` configured with `generate: chi-server`.

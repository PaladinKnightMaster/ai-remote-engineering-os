# ADR-0010: Integrate existing Git forges before building native forge

## Status

Accepted — 2026-08-27 (CEO ruling, ecosystem-architecture session). **Draft for 15 months; resolved
against ADR-0073 §2, and it was the most load-bearing of the three unresolved Drafts.**

## Context

This project must balance remote execution, AI agency, restricted-network deployment, security, mobile UX and future engineering-OS ambitions.

## Decision

Gitea/Forgejo/GitLab/GitHub Enterprise integrations are safer than cloning GitHub/GitLab early.

## Consequences

- The decision becomes part of the implementation baseline.
- Changes require a follow-up ADR.
- Related requirements, tests and documentation must stay aligned.

## Resolution — 2026-08-27

**Drafted 2026-05, left unresolved for fifteen months — and that was the actual risk**, not the
decision itself.

**Accepted.** It is the same rule, in the same family, as two ADRs that were Accepted at the time:
**ADR-0004** (*"use existing remote desktop tools before building custom"*) and **ADR-0015**
(*"agent runtimes behind adapters rather than hard dependencies"*). Integrate before cloning is a
single posture applied to three surfaces — remote desktop, agent runtime, git forge — and there is no
reason on record why the forge instance alone should have stayed Draft.

**Under ADR-0073 §2 a git forge is a substrate:** governed at its seam, operator-provided by default,
never merged into the core. Shipping a native forge would be a §3 escalation requiring a measured
feasibility finding and its own ADR.

**Why leaving this Draft was the risk.** ADR-0073 §Consequences records that **ADR-0015 is the only
thing holding the line against shipping a first-party harness**, and names as a negative that its
sibling forge decision was unratified. Accepting this ADR closes that gap: the integrate-before-clone
posture is now ratified on all three surfaces rather than two.

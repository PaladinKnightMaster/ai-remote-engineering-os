# ADR-0044: DB migration tool — `golang-migrate/migrate` in library mode, embedded per service, pure-SQL files

## Status
Accepted — 2026-05-17.

## Context

ADR-0041 established Go as the primary backend language with single-static-binary deploy, a tight supply-chain surface, and a capability-edge permission model. ADR-0042 established Go workspaces + pnpm workspaces + Taskfile as the monorepo tooling and named Taskfile targets (`task lint`, `task test`, `task build`, `task offline-bundle`) as the canonical orchestration surface. ADR-0043 established `go-chi/chi` v5 on `net/http` as the HTTP framework with `oapi-codegen` for schema-first server stubs and `packages/go/middleware/` as the *shared infrastructure module* shape for code consumed identically by every service.

This ADR picks the database-schema migration tool for P0. The decisive constraints are all inherited:

1. **Single static binary per service** (ADR-0041). Any tool that requires a second binary in the deploy artifact increases the offline-installer surface.
2. **Offline / restricted-network deploy** (ADR-0001). The tool itself, its module sources, and any runtime artifacts must mirror cleanly into a Go module cache and a pnpm content-addressed store. No fetching during install.
3. **Capability-edge model** (`docs/security/agent-permission-model.md`). `audit-service` enforces append-only writes and a chained-hash evidence chain; a migration that drops or rewrites audit rows would forge integrity. Migration tooling itself is a capability edge — privileged DDL run by an operator — and must be auditable.
4. **P0 ship velocity** (ADR-0041, ADR-0042). Five Go services (`api`, `session-broker`, `audit-service`, `policy-service`, `connector-service`) need a migration story they can adopt the same day.
5. **Diff budget ≤12 files / ≤500 LoC per ticket** (`CLAUDE.md`). Hand-rolled plumbing is expensive in this budget.

Postgres is the assumed relational store per `docs/deep-dive/09-offline-self-hosting-deployment.md` and `docs/deep-dive/20-memory-context-architecture.md`. This ADR does not relitigate the DB engine; if that needs formalizing, a separate ADR can do so without changing the tool selection below.

The decisive sub-questions for this ADR are not "which tool has the best schema diff" — they are:

1. Do migrations ship **embedded** in each service binary or as an **external** tool binary?
2. Does each stateful service own its **own** migrations directory, or is there a **shared** migrations tree?
3. **Forward-only vs up/down** — what is the rollback story for `audit-service` specifically?
4. **Atlas's declarative mode** — is schema-as-code the right abstraction at P0?

## Decision

- **Tool:** [`golang-migrate/migrate`](https://github.com/golang-migrate/migrate) v4 in **library mode** (not the CLI binary). Import path: `github.com/golang-migrate/migrate/v4`, with the `postgres` database driver and the `iofs` source driver.
- **Embedding:** each `services/<name>` Go module embeds its own SQL migrations via `//go:embed migrations/*.sql` and an `embed.FS` handed to `iofs.New(...)`. No external CLI binary ships in the deploy artifact.
- **Per-service ownership:** each stateful service owns `services/<name>/migrations/` containing pure-SQL files named `NNNN_<slug>.up.sql` / `NNNN_<slug>.down.sql`. Sequence numbers are zero-padded four digits, starting at `0001`. No service applies another service's migrations. `services/api` is assumed stateless at P0; if that changes, an ADR addendum is not required, but the service owns its own migrations directory like any other.
- **Shared runner:** a new Go module `packages/go/migrate/` under `go.work` exposes the migration runner — same shape as `packages/go/middleware/` from ADR-0043. It provides:
  - A `Runner` type taking an `embed.FS`, a service name, and a DB DSN.
  - Subcommand wiring so every service's `main.go` exposes `<service> migrate up|down|version|force <v>` uniformly.
  - An audit-emission hook so migrations against `audit-service` (and any other service that wants it) write a structured event into the chained-hash audit log on apply.
- **Invocation surface:** Taskfile target `task migrate -- <service> <action>` wraps the per-service subcommand. Migrations run as a **deliberate operator action via the service subcommand**, not on service boot.
- **File format:** pure SQL. No Go-coded migrations. Data transforms that cannot be expressed in SQL are deferred to an out-of-band data-tools playbook; if that pattern becomes load-bearing, a follow-up ADR may revisit (see *Review triggers*).
- **Forward-only policy for `audit-service`:** the integrity invariant from `docs/security/agent-permission-model.md` (append-only + chained-hash) means destructive `DOWN` migrations would forge integrity. `audit-service` migrations follow this rule:
  - `DOWN` files may exist for *structural-only* rollbacks (drop an added index, drop a newly-added column that has never received writes in production).
  - `DOWN` files MUST NOT drop, rewrite, truncate, or alter the `events` table or any table participating in the chained-hash evidence chain.
  - This rule is documented in `services/audit-service/migrations/README.md` and enforced by a migration linter (deferred to P1; documented here as a verification gap at P0 — see *Verification*).
- **Up/down enabled for other services:** `policy-service`, `connector-service`, `session-broker` (if persistent) ship standard `up.sql` / `down.sql` pairs.

`pressly/goose`, `amacneil/dbmate`, `ariga.io/atlas`, and a hand-rolled stdlib runner are rejected at P0 under defined review triggers below.

## Alternatives considered

### A. `golang-migrate/migrate` in library mode (adopted)

See *Decision*. Net-of-stdlib supply-chain delta: one MIT-licensed module (`github.com/golang-migrate/migrate/v4`) plus its `postgres` and `iofs` sub-drivers. The Postgres driver uses `database/sql`-compatible connectivity, so the project's DB driver choice (e.g., `pgx`'s `stdlib` adapter) is not foreclosed.

Library mode + `iofs` source driver gives us:

- Migrations are part of the service binary. The single-static-binary deploy story from ADR-0041 holds.
- `pg_advisory_lock` handling is built in; concurrent invocation from two replicas degrades safely.
- The runner is callable from the service's own audit pipeline — migration application can emit a chained-hash event into `audit-service` from inside the same process boundary.
- The CLI is not shipped to operators; the *service subcommand* is the audited entry point.

### B. `pressly/goose`

Rejected at P0; held in reserve.

- Pros: Go-native; first-class `embed.FS`; mature; supports both SQL files and Go-coded migrations.
- Cons: Go-coded migrations are the differentiator and the precise feature we do not want — they introduce a code-execution surface at schema-apply time, which inflates the audit review for `audit-service` migrations and weakens the "pure DDL/DML, reviewable as text" property of the SQL-file discipline. Without that differentiator, goose is feature-parity with golang-migrate but with a smaller community.
- Decisive: extra code-execution surface for zero P0 benefit. Re-evaluated if data-transform migrations become genuinely necessary in P1+.

### C. `amacneil/dbmate`

Rejected.

- Pros: single static binary, language-agnostic, simple SQL-file model.
- Cons:
  - No library mode. Migrations cannot be embedded into the service binary — a second binary ships in the offline installer for every service that needs migrations.
  - "Language-agnostic" is a weak value-add in a Go-primary repo; we'd be paying a deploy-surface cost to support a generality we do not consume.
  - External tool cannot emit into the in-process audit chain without bespoke plumbing.
- Decisive: breaks the single-static-binary deploy story for no compensating benefit.

### D. `ariga.io/atlas`

Rejected at P0; held in reserve.

- Pros: schema-as-code with a planner-driven diff is genuinely powerful at scale; reverse-engineering of existing schemas is best-in-class; both declarative HCL and versioned-imperative modes available.
- Cons:
  - **Novelty cost.** Declarative schema-diff is a different mental model than "numbered SQL files" — onboarding tax during P0 push.
  - **Planner ↔ append-only invariant.** Atlas's declarative planner can propose destructive DDL when reconciling a target schema with the current state. For `audit-service` this is exactly the failure mode the integrity invariant must prevent. Operating Atlas in versioned-imperative mode for that service neutralizes its differentiator.
  - **Cloud-feature footgun.** Atlas's hosted features must be carefully disabled for the offline-deploy posture, similar to the Turborepo remote-cache footgun called out in ADR-0042. A release-guard hazard if a future contributor toggles it back on.
- Decisive: novelty + integrity-invariant conflict at P0. Re-evaluated under the *Review triggers* below.

### E. Hand-rolled stdlib runner (`database/sql` + numbered SQL files + a small Go program)

Rejected.

- Pros: zero non-stdlib runtime dependency for the migration path.
- Cons: reimplements the `schema_migrations` table, advisory locking, dirty-state recovery, sequence enforcement, and source loading — all already-solved problems in golang-migrate. Several hundred LoC of plumbing, pressuring the diff budget, with subtle correctness bugs likely on the first pass.
- Decisive: cost-benefit fails versus a single small dependency that is already audited by the broader Go community.

### F. `sqlc` paired with one of A–E

Out of scope as a *migration* tool — `sqlc` is a query codegen tool. Worth noting as a possible P1+ companion to provide typed queries on top of whatever migration tool ships schemas. Does not change this ADR.

## Decisive sub-questions — answers

### 1. Embedded vs external — Embedded.

Migrations ship inside the service binary via `embed.FS` + golang-migrate's `iofs` source driver. The service exposes a `migrate` subcommand (`audit-service migrate up`, etc.). Rationale:

- Honors single-binary deploy from ADR-0041.
- Honors offline posture from ADR-0001 — migrations are already in the deployed artifact, not fetched.
- Migration application is a capability-edge event — the in-process subcommand can write an audit event into the chained-hash log. An external CLI cannot do this natively.
- **Migrations do NOT run on boot.** Boot-time auto-migration is tempting and golang-migrate's advisory-lock handling would make it safe; we reject it on principle. Schema changes are deliberate operator actions, gated to a `migrate up` invocation, so that a multi-replica deploy never silently mutates schema and so that the audit trail records an explicit "operator X applied migration N" event distinct from "service started."

### 2. Per-service vs shared — Per-service.

Each stateful service owns `services/<name>/migrations/`. Service boundaries are capability-edge boundaries; schema boundaries match them. The shared `packages/go/migrate/` module is *infrastructure code* (runner, subcommand wiring, audit hook) — not a shared schema. Same pattern as `packages/go/middleware/` in ADR-0043.

If two services genuinely need to share a table (not expected at P0), the table belongs to whichever service owns its capability edge; the other service reads via that service's API, not the database. This rule is doctrinal, not enforced by tooling at P0.

### 3. Forward-only vs up/down — Mixed, by service policy.

- **`audit-service`: forward-only by policy** (rule documented in this ADR and in the service's `migrations/README.md`). `DOWN` files are permitted only for structural-only reversals; destructive DDL on integrity-bearing tables is forbidden.
- **All other services: standard up/down pairs.** `policy-service`, `connector-service`, `session-broker` (if persistent) ship `NNNN_<slug>.up.sql` and `NNNN_<slug>.down.sql`.

A CI lint to enforce the audit-service rule is deferred to P1 and documented as a verification gap at P0.

### 4. Atlas declarative mode at P0 — No.

Held in reserve. Adopt only when both of the following are true: (a) schemas have stabilized enough that a diff-driven workflow is a concrete net win, AND (b) the planner can be operated against `audit-service` without ever proposing destructive DDL (typically via versioned-imperative mode for that one service while declarative mode runs against others). Until then, golang-migrate carries the load.

## Consequences

### Positive

- One shared `packages/go/migrate/` library serves every stateful service with a uniform subcommand surface (`<service> migrate up|down|version|force`). Operators learn it once.
- The deploy artifact remains a single static binary per service — no migration CLI ships alongside.
- Offline posture is straightforward: `go mod download` populates `github.com/golang-migrate/migrate/v4` and its drivers into the module cache; the same `task offline-bundle` mechanism from ADR-0042 covers it. No new offline-install surface.
- Supply-chain delta is one well-known MIT module plus two sub-drivers (`postgres`, `iofs`). Within the budget set by ADR-0041 / ADR-0042.
- Migration application against `audit-service` can emit an audit event in-process — the operator action is itself evidence in the chained-hash log.
- Pure-SQL discipline keeps migration review as plain text. Reviewers do not need to reason about Go code that runs at schema-apply time.
- The `chi.Router IS http.Handler` composability pattern from ADR-0043 is preserved here at the infrastructure layer: the `packages/go/migrate/` module exposes a small surface that does not leak across service boundaries.

### Negative

- `audit-service`'s forward-only policy is documented but not lint-enforced at P0. A contributor could land a destructive `DOWN` file against an integrity-bearing table; review and the service-level `README.md` are the only guards. Mitigation: P1 ticket for a migration linter; documented as a verification gap.
- golang-migrate's CLI is not part of the operator surface, which means recovering from a `dirty` state requires the service's own `migrate force <v>` subcommand. This is the correct posture but it is one more thing operators must learn.
- Future data-transform migrations that cannot be expressed in SQL will require either an out-of-band data-tools job or a re-evaluation of pure-SQL discipline (see goose in *Held in reserve*).
- Pinning to golang-migrate v4 means any v5 breaking change is a deferred-cost item. Mitigation: drivers are pluggable and the public API surface we consume is small (`Up`, `Down`, `Migrate`, `Force`, `Version`).

### Held in reserve

- **`pressly/goose`** — adopt if data-transform migrations that cannot be expressed in pure SQL become recurring (more than two cases in one quarter), to gain its Go-coded migration path.
- **`ariga.io/atlas`** — adopt when schemas have stabilized, the team has bandwidth for the model shift, AND a concrete proposal explains how the integrity invariant on `audit-service` is preserved under the declarative planner.
- **`amacneil/dbmate`** — not held in reserve. The "external binary" model is a regression against single-binary deploy.
- **Hand-rolled stdlib runner** — held in reserve only for a future hardened module per ADR-0041's reserve clause, paired with a similar zero-non-stdlib exception.

## Verification

This ADR is verified once the following hold:

1. `packages/go/migrate/` exists as a Go module under `go.work` and exports a `Runner` type plus a subcommand registrar consumed identically by every stateful `services/*` module.
2. At least one stateful service (e.g., `services/audit-service`) declares `github.com/golang-migrate/migrate/v4` in its `go.mod`, embeds `migrations/*.sql` via `//go:embed`, and exposes `<service> migrate up|down|version|force` as subcommands.
3. `task migrate -- <service> <action>` is wired in `Taskfile.yml` and dispatches to the service subcommand.
4. The deploy artifact for any stateful service remains a single static binary; no second migration-tool binary appears in the offline installer for the migration path.
5. `services/audit-service/migrations/README.md` documents the forward-only / no-destructive-DDL policy and references this ADR.
6. Applying a migration against `audit-service` writes a structured audit event into the chained-hash log via the runner's audit hook (verifiable from `audit-service`'s own evidence-chain integrity test under ADR-0041's verification target).

Known verification gap at P0:

- No CI lint enforces the `audit-service` forward-only / no-destructive-DDL rule. The rule is documented and review-enforced at P0; lint enforcement is a P1 ticket.

## Review triggers

Re-open this ADR if any of these become true:

- A `golang-migrate/migrate` supply-chain incident materially affects trust posture, or v4 enters unmaintained status.
- Recurring data-transform migrations (>2 in one quarter) cannot be expressed in pure SQL — re-evaluate `pressly/goose`.
- Schemas have stabilized AND a concrete Atlas proposal shows a measurable net win that preserves the `audit-service` integrity invariant — re-evaluate Atlas.
- The "no boot-time auto-migration" rule proves operationally onerous across two or more customer environments — revisit the run-on-boot policy specifically (golang-migrate's advisory-lock handling would still make it safe).
- A new stateful service requires a database engine other than Postgres — re-evaluate the `postgres` driver pin (the rest of this ADR is engine-agnostic).

- **Findings**: single-binary deploy + offline posture + audit-edge auditability + P0 velocity are the decisive axes. Hand-rolled loses on cost-benefit vs one small dep.
- **Evidence**: `docs/security/agent-permission-model.md` (capability edges, append-only + chained-hash invariant), `docs/deep-dive/09-offline-self-hosting-deployment.md` (Postgres as assumed engine), `docs/deep-dive/20-memory-context-architecture.md` (relational metadata in Postgres), ADR-0001 (offline-first), ADR-0041 (single static binary, tight supply chain), ADR-0042 (Taskfile orchestration), ADR-0043 (shared-infra `packages/go/*` pattern).
- **Risks**: forward-only rule for `audit-service` is documented-not-enforced at P0 (MEDIUM, mitigated by P1 lint ticket); golang-migrate v5 breakage cost (LOW, small public-API surface consumed); pure-SQL discipline forecloses Go-coded data transforms (LOW at P0, MEDIUM if it becomes recurring — explicit review trigger).

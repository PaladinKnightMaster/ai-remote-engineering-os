# ADR-0048: Cockpit session lifecycle — in-process Go SSH for terminal, services/api for control plane, per-input-line audit, pgcrypto for target secrets

## Status

**Accepted** — 2026-05-28. Promoted from Proposed after the
`spike/xterm-ssh-pty` branch landed numerical confirmations for every
§Verification item; spike findings are folded into the verification
table below and the throwaway branch was deleted. Full spike post-
mortem lives in `docs/spike/xterm-ssh-pty-findings.md`.

## Context

The v0.1.0 wedge demo (per `docs/evaluation/v0.1.0-release-criteria.md`
§WD-1) requires an operator end-to-end path: pick a resource → start a
remote session → operate a terminal → audit timeline reflects every
operator-attributable action. ADR-0047 settled the frontend stack
(Vite + React + xterm.js for terminals; Guacamole for GUI) and split
`<RemoteSessionView>` (GUI, deferred) from `<TerminalView>` (terminal,
in v0.1.0 scope). ADR-0046 settled capability-edge auth. ADR-0045
settled audit-chain integrity.

What was **not** settled: the actual cockpit session shape — how the
WebSocket terminal data plane connects to a target SSH server, where
session state lives, how target credentials are stored, how
operator-attributable actions become discrete chain events, and how
the session lifecycle (open / close / terminate / TTL / reconnect)
is governed.

The v0.1.0 criteria's `§11 Open Questions` listed OQ-1 (terminal
transport) and OQ-2 (session lifecycle owner) as the surface
questions, but the war-room consult on 2026-05-27 surfaced 6 more
load-bearing decisions (cast files, per-command audit, target
credentials, recovery, TTL, scope) that all need single answers
before the SSH end-to-end vertical slice can be authored.

This ADR consolidates the consult's answers. It is the binding spec
for that vertical slice.

## Decision

The eight answers, in one ADR:

### 1. Terminal transport: in-process Go SSH via `session-broker`

- `<TerminalView>` in `apps/web` mounts `xterm.js` and opens a WebSocket
  to `services/session-broker` at `/v1/sessions/{id}/stream`.
- `services/session-broker` opens an SSH connection to the target
  resource using `golang.org/x/crypto/ssh` (stdlib-adjacent, no new
  third-party SSH client) and pipes PTY bytes bidirectionally over the
  WebSocket.
- **`guacd` is NOT in the terminal path.** Guacamole only lands when
  RDP/VNC GUI sessions become load-bearing (deferred to a feature
  ticket per §Held in reserve).

### 2. Session lifecycle ownership: `services/api`

- `services/api` owns the REST control plane for sessions:
  - `POST   /v1/sessions`         — start a session against a resource
  - `GET    /v1/sessions/{id}`    — fetch session metadata
  - `GET    /v1/sessions`         — list (operator-scoped)
  - `POST   /v1/sessions/{id}/end` — end a session
- `services/session-broker` owns ONLY the WebSocket data plane.
- The two services communicate via shared Postgres (`sessions` table
  owned by `services/api`'s schema). No direct service-to-service RPC
  is required at v0.1.0.

### 3. `sessions` table schema (in `services/api`'s Postgres)

```sql
CREATE TABLE sessions (
    id              UUID PRIMARY KEY,                  -- UUID v7, server-assigned
    resource_id     TEXT NOT NULL REFERENCES resources(id),
    operator_id     TEXT NOT NULL,                     -- bearer's subject
    mode            TEXT NOT NULL,                     -- 'terminal' at v0.1.0
    status          TEXT NOT NULL,                     -- pending|active|closed|terminated
    started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    ended_at        TIMESTAMPTZ,
    closed_reason   TEXT,                              -- idle|operator|broker_crash|ttl
    cast_path       TEXT,                              -- path to asciinema cast file (NULL until close)
    cast_sha256     CHAR(64),                          -- SHA256 of cast file at close
    CONSTRAINT sessions_mode_chk   CHECK (mode IN ('terminal')),
    CONSTRAINT sessions_status_chk CHECK (status IN ('pending','active','closed','terminated'))
);
```

### 4. Authentication of the WebSocket upgrade

- The browser sends the existing `aireos_session` HttpOnly cookie on
  the WS upgrade (browsers send cookies on the underlying HTTP request
  by spec).
- `services/session-broker`'s `RequireCapability` middleware (the same
  one used by REST routes per ADR-0046) verifies the bearer.
- No new auth path; the cookie-based posture from ADR-0047 T-007b
  flows through.

### 5. Authorization (this operator for this session)

- The WS path embeds the session ID: `/v1/sessions/{id}/stream`.
- `session-broker` SELECTs the `sessions` row by `id`, asserts
  `sessions.operator_id == bearer.sub`.
- **No cross-operator scope at v0.1.0.** "Shadow another operator's
  session" requires capability scope `{ resource: "session:<id>" }`
  which is held in reserve.

### 6. Audit granularity: per-input-line + cast file

- session-broker buffers PTY input bytes per session.
- On every `\r` (Enter), session-broker emits a chained-hash audit
  event `terminal.input.line` with `{ session_id, line }` and resets
  the buffer.
  - **Shell-agnostic.** No PS1 / prompt parsing. The byte boundary
    is the operator's Enter — well-defined for every shell, paste,
    heredoc, and multi-line continuation.
  - Multi-line commands via backslash continuation: each line
    becomes its own event (which is what was sent).
  - Heredoc body lines: each becomes its own event.
  - Pasted multi-command: one event per embedded `\r`.
- Output bytes (target → operator) are **not** chain-audited (target-
  side, not operator-attributable). They land in the cast file.
- Lifecycle events emit: `session.open`, `session.close`, `session.terminated`.
- Forensic cast: every session writes a full asciinema-format
  recording (input + output, timestamped) to
  `/var/lib/aireos/sessions/<id>.cast`. On `session.close`, the file
  is hashed (SHA256) and the hash recorded in the close event +
  `sessions.cast_sha256`. The chain therefore points at the
  immutable forensic blob for post-hoc analysis.

**Volume estimate:** ~30-100 `terminal.input.line` events per active
session-hour. Well within audit-service's chained-hash throughput
budget (Postgres sustains thousands of chain inserts per second under
the T-004b trigger). The earlier "per-keystroke audit blows throughput"
fear was misframed — per-line is the correct atom and the volume is
modest.

**Semantic clarifications (added by spike review pass):**

- *Backspace mid-line records two different things in two surfaces.*
  Operator typing `helo\bllo<Enter>` produces ONE chain event
  carrying the raw bytes `helo\bllo` (what the operator actually
  sent on the wire — the operator-attributable atom). The cast file
  separately records the rendered terminal state, which is whatever
  the shell did in response to the backspace (in bash:
  `[K` ANSI erase-to-EOL followed by re-rendering). Investigators
  get both: intent (chain) + result (cast file). This is by design;
  the chain audits attribution, the cast preserves visual ground
  truth. The SSH slice ticket must NOT "normalize" backspaces out of
  the chain event — the operator-attributable atom is the raw byte
  sequence.

- *Cast file event payloads MUST NOT use Go's default
  `string([]byte)` → JSON path.* PTY streams carry 8-bit bytes
  (terminal escape sequences, locale output, partial UTF-8 multi-byte
  chars split across WS frames). `json.Marshal` on a string with
  invalid UTF-8 silently replaces bad bytes with U+FFFD — data loss
  with no error. The spike validated a byte-by-byte JSON literal
  builder (`safeJSONStringFromBytes` pattern): ASCII printable passes
  through; control bytes get `\u00XX`; bytes ≥ 0x80 get `\u00XX`
  (round-trips losslessly through asciinema players for U+0080–U+00FF).
  The SSH slice ticket inherits this pattern.

### 7. Target credentials: pgcrypto-encrypted columns at v0.1.0

- `resources` table grows a `connection_secret` `BYTEA` column at the
  next migration (`0002`). The column stores
  `pgp_sym_encrypt(secret_plaintext, AIREOS_RESOURCE_SECRET_KEY)`
  where the key is a separate env var from `AIREOS_PASETO_KEY`
  (authority separation: PASETO key signs tokens; resource secret key
  unwraps target credentials).
- For SSH-typed resources: operator pre-provisions a service-account
  on the target host; the encrypted column stores its private key
  (and optionally a passphrase).
- `services/api` decrypts at session-open time and hands the
  decrypted credential to `services/session-broker` over the
  service-to-service token-gated channel (ADR-0046 §service-tokens).
  The decrypted form lives only in session-broker's process memory
  for the lifetime of the SSH connection.
- **Postgres extension `pgcrypto` ships with the standard `postgres:16`
  image** — no offline-bundle delta.

**This is a known security debt at v0.1.0.** `services/api`'s database
holds material that, if compromised, gives access to every target
resource. The architecturally-correct destination is
`services/connector-service` (per ADR-0046 §Hand-off + the
egress-policy doctrine). Promotion trigger documented in v0.1.0
criteria §10 as: *"first egress-policy ticket OR first non-SSH
resource type OR a customer security audit flags `services/api`
secret access."*

### 8. Session TTL + reconnect + crash recovery

- **Hard TTL**: session is automatically terminated when the parent
  operator session expires (8h per ADR-0046).
- **Soft idle timeout**: 30 minutes without PTY input → session
  `closed` with `reason: idle`.
- **Reconnect**: operator's `useWebSocketChannel` hook reconnects via
  exponential backoff (per ADR-0047 §useWebSocketChannel skeleton).
  The `sessions` row stays `active` during the brief disconnect
  window; broker re-attaches.
- **session-broker crash**: SSH connections die with the process.
  Operator's WS reconnects; broker opens a *new* SSH connection to
  the same target on the same `sessions` row. Operator sees a brief
  blank terminal followed by a fresh prompt. Acceptable at v0.1.0;
  the criteria notes "session resumption-at-state" as held in reserve.
- **`services/api` crash mid-session**: irrelevant to the data plane
  (broker has the SSH connection); session metadata is in Postgres
  (durable).

## Alternatives considered

### A. `guacd` for terminal sessions

Rejected. Guacamole was designed for GUI gateway protocols (RDP/VNC);
its SSH support is a coincidence of Guacamole's protocol multiplexer.
Using guacd for terminal in v0.1.0 would:
- Add a C daemon to the offline bundle (~50 MB; X11 deps)
- Add a CVE feed to the security-review surface
- Require an audit-translation layer (Guacamole's audit format is
  not chained-hash)
- Couple the cockpit's lightest session type to its heaviest
  dependency.

In-process Go SSH avoids all four. Guacamole lands when the FIRST
RDP/VNC resource type ships — a feature ticket post-v0.1.0.

### B. New `services/session-manager` for session control plane

Rejected. `services/api` already gates `/v1/resources` with
`RequireCapability`, emits audit events via the outbox, and is the
canonical operator REST surface. Adding `/v1/sessions` reuses
everything; a new service would duplicate auth wiring, audit wiring,
and bundle real estate. The "single-responsibility" lure (sessions
should have their own service) doesn't pay for itself at v0.1.0 with
a single resource type.

If a future feature splits session state to a per-service auth domain
(unlikely), this ADR can be re-opened. Until then: monolithic
`services/api` for control plane.

### C. Per-keystroke audit chain writes

Rejected. ~100 events/sec under bursty typing. Chain trigger is O(1)
but row-count grows quickly; querying a session's commands becomes
"reconstruct from byte stream." Per-input-line is the right atom:
*operator-attributable* boundaries are Enters, not keystrokes.

### D. Shell-prompt parsing for per-command audit

Rejected. Different shells, customizable PS1, multi-line continuation,
heredoc, paste — robust prompt parsing requires either a hooked shell
on the target (out of scope; target hosts are operator-provided) or a
PAM-based command logger. Both are real future options; neither is
P0-implementable.

Per-input-line is shell-agnostic and adversarial-input-safe.

### E. `services/connector-service` for target credentials at v0.1.0

Rejected at v0.1.0 (held in reserve). `connector-service` is the
architecturally-correct destination for secrets + egress policy +
per-ticket leases. Building it now is 2-3 weeks of work on its own —
substantial scope inflation on the v0.1.0 wedge. pgcrypto-encrypted
columns are the smallest path to a demoable session, with explicit
debt and promotion trigger.

### F. Cast file only, no per-command chain events

Rejected. A cast file blob with a SHA256 in the chain technically
maintains integrity but defeats *queryability*. An investigator
asking "what command did `operator:admin` run at 14:23:07?" should
get a one-row Postgres answer, not a `grep` over an 80 MB file. The
chain's whole value proposition is queryable evidence; per-input-line
events make that real.

## Consequences

### Positive

- **One schema, two consumers** preserved: `/v1/sessions` is added to
  the same OpenAPI fragment that drove Go + TS codegen since T-009.
- **Audit chain becomes queryable for operator actions.** Per-input-line
  events index by `session_id`, `operator_id`, timestamp.
- **Forensic record decoupled from chain throughput.** Cast files
  carry the full byte stream; the chain carries the semantic
  attribution. Both are immutable post-close (cast file hashed into
  chain).
- **No new daemon in the offline bundle.** Go SSH client is stdlib-
  adjacent; cast files are plain disk; pgcrypto is in standard
  postgres image.
- **Capability-edge model preserved.** Every cross-edge action
  (open, line, close, terminate) emits a chain event with the
  capability's `edge` field. The seven canonical edges from
  `docs/security/agent-permission-model.md` cover terminal sessions
  via `agent-remote-session`.

### Negative

- **Secrets in `services/api`'s Postgres** is a known security debt.
  Compromising `services/api` compromises every target. Mitigated by
  pgcrypto + key separation; remediated by `connector-service`
  adoption (held in reserve with explicit trigger).
- **Cast files on local disk** introduce a new operational concern
  (disk pressure, rotation policy, retention). At v0.1.0 with one
  operator, ~80 MB / 8h-session-day; budget-able. Operations runbook
  for rotation deferred to a release-prep ticket.
- **session-broker crash means SSH state loss.** Operator sees a fresh
  shell on reconnect — not a tmux-style preserved state. Acceptable at
  v0.1.0; tmux-as-stateful-bridge held in reserve.
- **No cross-operator session sharing.** "Shadow my session" is a
  natural follow-up but adds a capability scope shape and a UX surface.
  Held in reserve.

### Held in reserve

| Item | Promotion trigger |
|---|---|
| `guacd` + `<RemoteSessionView>` for RDP/VNC sessions | First RDP or VNC resource type ticket |
| `services/connector-service` for secrets + egress policy | First egress-policy ticket OR first non-SSH resource type OR a customer security audit |
| Cast-file UI replay component | v0.2.0 evidence-replay ticket |
| Cross-operator session sharing (scope `session:<id>`) | First "shadow operator" customer ask |
| tmux-backed session preservation across broker restart | Customer ask, or sustained ops complaint about reconnect UX |
| Per-shell-prompt command parsing | Probably never; per-input-line is the v1+ semantic |
| Auto-generated session recording redaction (PII / secret patterns) | First compliance ticket |

## Verification

### Spike-confirmed items (all PASS as of 2026-05-28)

The `spike/xterm-ssh-pty` branch (commits `8ce8f3a` Phase 1 +
`6438ec6` Phase 2 + `399e1ba` Phase 2 tightening) validated every
architecturally-load-bearing item. Full post-mortem in
`docs/spike/xterm-ssh-pty-findings.md`.

1. **End-to-end terminal session works.** ✓ PASS — 200+20 round-trips
   through SPA-equivalent driver → session-broker `/spike/ssh` →
   `golang.org/x/crypto/ssh` → containerized `linuxserver/openssh-server`
   on `docker-compose_default`. No WS-close errors, SSH dial failures,
   or PTY allocation failures across both phases.

2. **Keystroke→echo round-trip latency, p95 < 100ms localhost.** ✓ PASS
   — measured (200 samples, single-byte sends, 30ms gap):

   | min | p50 | p95 | p99 | max |
   |---|---|---|---|---|
   | 0.36ms | 0.54ms | **1.03ms** | 1.77ms | 3.11ms |

   ~97× headroom on the SLO. Real WAN deployment will be RTT-dominated
   (50-200ms typical); SLO still applies — re-measure on staging.

3. **Reconnect: ✓ PASS, with reframing.** The spike review pass
   surfaced that the original "5s p95" phrasing conflates server-side
   dial bound with client-side backoff. Replaced with three parts:

   - **Server-side reconnect bound** (WS dial + SSH dial + PTY alloc):
     measured 20-30ms on docker-compose_default; SLO p95 < 200ms.
   - **Client-side backoff window**: `useWebSocketChannel` default
     initial 500ms, exponential up to a 15s cap; verified by T-007c
     unit tests.
   - **First-failure recovery** (combined): p95 < 1s on localhost;
     subsequent failures intentionally exceed via backoff (cap 15s).

   Measured cold-dial distribution (20 samples, 200ms gap; dominated
   by a 500ms quiet-gap settle timer in the measurement tool — actual
   dial cost is 20-30ms):

   | min | p50 | p95 | p99 | max |
   |---|---|---|---|---|
   | 521ms | 522ms | **529ms** | 529ms | 535ms |

4. **Per-input-line audit emission correctness.** ✓ PASS — 6/6
   expected `input.line` log entries emitted across 5 deterministic
   scenarios:

   - Two-commands (`echo first-line\recho second-line\r`): ✓ both
   - Backspace mid-line (`helo\bllo\r`): ✓ — chain captures raw
     bytes (`helo\bllo`), NOT rendered text (`hello`). The cast file
     captures the rendered terminal state separately. Both are
     correct; investigators get both views.
   - Pasted multi-line (`a-line\rb-line\r` in one WS frame): ✓
     correctly split on embedded `\r`
   - Empty `\r\r\r`: ✓ zero events (line buffer empty)
   - Exit (`exit\r`): ✓

5. **Cast file format + replay.** ✓ PASS — `asciinema cat` on the
   produced file exits 0; full session renders correctly. SHA256 of
   closed file logged in the `cast.close` broker line (the anchor
   §SEC-11 records in the chain). 20 events (5 input / 15 output),
   timeline 0 → 3.522s, balanced byte counts.

### New verification items (added by spike review pass)

These items did not appear in the original Proposed §Verification
because the spike surfaced them only after running. They block the
**SSH end-to-end vertical slice ticket** sign-off (not this ADR's
acceptance):

6. **PTY resize signaling.** Browser `window.resize` event → SPA
   computes new cols/rows from xterm's `FitAddon` → sends a control
   message over WS → session-broker propagates via
   `ssh.Session.WindowChange(cols, rows)`. Spike hardcoded 80×24;
   production must handle resize without dropping the SSH session.

7. **Host key pinning per target resource.** Spike used
   `ssh.InsecureIgnoreHostKey()` for measurement. Production must
   replace with `ssh.FixedHostKey` or `known_hosts`-style verification
   bound to the `resources` row.

8. **Session idle timeout enforcement.** ADR-0048 §8 mandates 30min
   of input inactivity → session closes with `reason: idle`. Spike
   handler ran until the WS closed (no timeout). The SSH slice ticket
   wires a `time.AfterFunc` keyed on every input event.

9. **Large-output streaming without buffer-bloat.** Spike measured
   only single-byte echo; production must demonstrate sustained
   multi-MB output (e.g. `find /`) without session-broker OOMing or
   blocking on PTY reads. Suggested test: stream 100 MB of `/dev/urandom`
   through `cat` and confirm constant memory footprint at the broker.

### Implementation-confirmable items (block the SSH slice ticket sign-off)

6. `services/api` exposes the four `/v1/sessions` REST operations,
   gated by `RequireCapability` over edges
   `{ human-agent, agent-remote-session }`.
7. `sessions` migration adds the table + `pgcrypto`-encrypted
   `resources.connection_secret` column via the per-service
   forward-only migration runner (ADR-0044).
8. `services/session-broker`'s WS handler at `/v1/sessions/{id}/stream`
   verifies bearer (cookie path) + ownership (sessions.operator_id =
   bearer.sub) before opening the SSH connection.
9. `terminal.input.line` audit events appear in the chained-hash
   log under load (1 hour of bursty typing); chain integrity test
   from T-004b still passes.
10. Cast file's SHA256 in `session.close` audit event matches the
    on-disk file SHA256.

### Known verification gaps

- No CI lint enforces "the SSH client library `golang.org/x/crypto/ssh`
  is only imported from `services/session-broker/...`". Defense in
  depth; deferred to the post-v0.1.0 lint pass.
- No automated test asserts cast files cannot be tampered post-close.
  At-rest integrity relies on chain's SHA256 anchor; documented as
  expected behavior.

## Review triggers

Re-open this ADR if any of these become true:

- The first RDP/VNC resource type ticket lands → revisit terminal +
  GUI session boundary (`guacd` promotion).
- Operator count exceeds 1 OR cross-operator session sharing becomes
  required → revisit capability scope shape + session ownership rule.
- `services/connector-service` lands → migrate secrets off
  `services/api`'s Postgres in the same milestone.
- per-second chain insert load from terminal sessions exceeds 50% of
  audit-service throughput SLO → revisit audit granularity (per-line
  may need batching / coalescing).
- A target host requires interactive auth (challenge-response,
  hardware token) → reconsider the credential model — pgcrypto-stored
  static keys won't cover that case.
- A customer or compliance ask requires per-command (not per-line)
  audit attribution → re-evaluate the prompt-parsing alternative or
  PAM hook on target hosts.
- An xterm.js / `golang.org/x/crypto/ssh` supply-chain incident
  materially affects trust posture → re-evaluate that specific dep.

## Output contract (per kit specialist-output format)

- **Scope**: cockpit session lifecycle (control + data plane), target-
  credential storage, audit granularity for terminal sessions, session
  TTL + reconnect + crash recovery. Consumed by the SSH end-to-end
  vertical slice ticket and every subsequent cockpit-feature ticket.
- **Findings**: the war-room consult surfaced 8 load-bearing questions
  the criteria's OQ-1/OQ-2 didn't fully cover. The architectural
  answers cluster cleanly (services/api control plane,
  session-broker data plane, in-process Go SSH, per-input-line audit,
  pgcrypto interim for secrets). Two real disagreements were surfaced
  and resolved without averaging: per-command audit (resolved by
  reframing as per-input-line) and connector-service-now (resolved
  as documented debt with promotion trigger).
- **Evidence**: ADR-0046 (capability tokens + service-tokens),
  ADR-0047 (Vite + xterm.js + useWebSocketChannel),
  ADR-0045 (chained-hash outbox), ADR-0044 (forward-only migrations),
  docs/security/agent-permission-model.md (capability edges),
  docs/evaluation/v0.1.0-release-criteria.md §11 (open questions
  this ADR closes).
- **Risks**: secrets-in-services/api debt (MEDIUM, mitigated by
  pgcrypto + key separation + promotion trigger); cast file disk
  pressure (LOW); session-broker crash UX (LOW); per-input-line
  granularity misses sub-line forensics (LOW; mitigated by cast file).
- **Recommendation**: adopt this ADR as Proposed; run the
  `spike/xterm-ssh-pty` spike to confirm Verification items 1-5;
  promote to Accepted once spike findings land; author the SSH
  vertical slice ticket against the Accepted version.
- **Confidence**: HIGH for the architectural decisions (consult
  unanimity on the major axes); MEDIUM-HIGH for per-input-line
  audit (one specialist preferred richer schemes; this is the
  pragmatic v1); MEDIUM for pgcrypto target credentials (known
  debt acknowledged); MEDIUM for the latency / reconnect numbers
  (pending spike measurements).
- **Hand-off notes**: the SSH vertical slice ticket should split into
  4 slices analogous to T-007: (a) sessions schema + REST CRUD on
  services/api with pgcrypto column for resources.connection_secret;
  (b) session-broker SSH gateway + per-input-line audit emission;
  (c) apps/web `<TerminalView>` + session lifecycle UI + cast file
  serving from session-broker; (d) cast file persistence layout
  + audit linkage + cleanup policy. Each slice is its own consult.

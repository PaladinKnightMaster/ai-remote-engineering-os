# ADR-0046: Auth adapter at P0 — no IdP daemon; in-process `packages/go/auth/` issuing PASETO v4 capability tokens; Zitadel held as the P1 reserve pick

## Status
Accepted — 2026-05-18.

## Context

ADR-0041 established Go as the primary backend language with single-static-binary deploy, a tight supply-chain surface, and a capability-edge permission model. ADR-0042 established Go workspaces + pnpm workspaces + Taskfile as the monorepo tooling. ADR-0043 established `go-chi/chi` v5 on `net/http` as the HTTP framework with `oapi-codegen` for schema-first server stubs and `packages/go/middleware/` as the *shared-infra module* shape, with `RequireCapability` as the canonical capability-edge enforcement point. ADR-0044 established `golang-migrate/migrate` v4 in library mode with a shared runner in `packages/go/migrate/`. ADR-0045 established no broker at P0; a transactional outbox with sync HTTP ingest into `audit-service`; a shared runner in `packages/go/outbox/`; NATS JetStream named as the P1 reserve pick. ADR-0045 explicitly left service-to-service auth abstract: *"the relay's HTTP client to `audit-service` will plug into whichever auth model lands."* This ADR closes that.

This ADR also explicitly answers the question in `docs/deep-dive/30-open-questions-and-research-backlog.md` *"How to design short-lived capability tokens"* and closes the Identity-layer placeholder in `docs/deep-dive/09-offline-self-hosting-deployment.md` (which named **Keycloak or Authentik** as the candidates).

The decisive constraints are inherited:

1. **Self-hosted / offline-first** (ADR-0001). No SaaS-hosted IdPs (no Auth0, Okta, Clerk, WorkOS). Any IdP daemon must mirror cleanly into the offline installer.
2. **Single static binary per service + tight supply chain** (ADR-0041). Every IdP daemon adds an installer artifact, a release-guard surface, a CVE feed, and a security-review surface.
3. **Capability-edge model** (`docs/security/agent-permission-model.md`). Every cross-actor interaction is a typed edge (`human-agent`, `agent-agent`, `agent-tool`, `agent-workspace`, `agent-repo`, `agent-memory`, `agent-remote-session`). Tokens MUST encode a typed edge + scope, not stock OIDC `scope` strings.
4. **Just-in-time credentials and per-ticket egress scopes** (`docs/security/egress-policy.md`). Egress leases issued by `connector-service` are themselves capability tokens.
5. **P0 ship velocity** (ADR-0041, ADR-0042). Five Go services (`api`, `session-broker`, `audit-service`, `policy-service`, `connector-service`) must consume the same auth model the day they land.
6. **Diff budget ≤12 files / ≤500 LoC per ticket** (`CLAUDE.md`).

Inventory of P0 actors and edges:

| Actor | Edges crossed | Notes |
|---|---|---|
| Operator (human) | human-agent, human-tool | One bootstrap account at P0; no self-service signup |
| Agent (in cockpit session) | agent-tool, agent-workspace, agent-repo, agent-memory, agent-remote-session | Short-lived scoped tokens, issued per session |
| `services/*` (workload identity) | service-service | Internal RPCs (outbox relay → `audit-service`, `api` → `policy-service`, etc.) |
| `connector-service` | issues egress lease tokens | Per-ticket scopes per `egress-policy.md` |

P0 has **one operator user**, **zero customer-IdP federation requirements** (the demo and first-customer environments have no AD/Okta/SAML to federate against), and **one approval workflow** (`policy-service` decisions, ADR-0045 outbox).

The decisive sub-question for this ADR is therefore not "Keycloak vs Authentik vs Zitadel." It is the ADR-0045-shaped question: *"do we need a separate IdP daemon at P0 at all, or can the vertical slice ship with in-process token issuance that the same `packages/go/middleware/RequireCapability` already trusts?"*

## Decision

- **No dedicated IdP daemon at P0.** Cross-service and operator-facing auth are handled by a new shared infrastructure module, `packages/go/auth/`, that issues and verifies capability tokens in-process.
- **Token format: PASETO v4 local** (symmetric, authenticated encryption). Reference implementation: [`aidantwoods/go-paseto`](https://github.com/aidantwoods/go-paseto). PASETO over JWT to eliminate algorithm-confusion / `alg:none` failure modes and to avoid standing up JWKS rotation infrastructure at P0. Library mode only.
- **Claim payload is a typed `CapabilityToken` struct**, not stock OIDC `scope` strings. Fields:
  - `sub` — actor identifier (operator user ID, agent session ID, or service workload name).
  - `edge` — one of the seven capability edges from `docs/security/agent-permission-model.md`, extended with `service-service` for internal RPC.
  - `scope` — typed object: target resource + allowed operations + (optional) `lease_id` for egress leases.
  - `iat`, `exp`, `jti`, `aud` (service name), `iss` (cluster ID).
- **Token lifetimes:**
  - Agent session tokens: **5 minutes**, refreshable while the parent operator session is active; every refresh emits an audit event via the ADR-0045 outbox.
  - Operator session tokens: **8 hours**, sliding refresh.
  - Service workload tokens: **1 hour**, auto-refreshed in-process from the workload bootstrap key.
  - Egress lease tokens: **TTL = lease expiry per `connector-service`**, single-use enforced by `jti` recording in `policy-service`'s decisions table; one-shot capability tokens minted from approval workflows follow the same shape.
- **Service-to-service auth: signed PASETO service tokens with workload identity** (closes ADR-0045's hangover). Each service receives a workload bootstrap key at install time (`install.sh` material, mounted as a secret). The service mints its own service-token at startup (audience = target service) and refreshes hourly. The ADR-0045 outbox relay's HTTP call to `audit-service` carries `Authorization: Bearer <service-paseto>` with `edge: service-service`, verified by the same `RequireCapability` middleware that gates human and agent traffic. **Not mTLS at P0** — mTLS cert provisioning/rotation/revocation is deferred operational burden; held in reserve for a hardened-deploy profile.
- **Shared infrastructure module: `packages/go/auth/`** under `go.work`. Same shape as `packages/go/middleware/` (ADR-0043), `packages/go/migrate/` (ADR-0044), and `packages/go/outbox/` (ADR-0045). Exposes:
  - `Signer` — token issuance (operator, agent, service, egress-lease).
  - `Verifier` — token verification (PASETO decode, `exp`/`aud`/`iss`/`jti` checks, typed `CapabilityToken` return).
  - `CapabilityToken` — the typed claim struct shared by issuer and verifier.
  - Workload-key bootstrap helpers + signing-key rotation helper (`auth rotate-key` operator action).
- **`packages/go/middleware/RequireCapability` imports `packages/go/auth/`** to verify the bearer token and extract `edge` + `scope`. The middleware's shape and signature (`func(http.Handler) http.Handler`) are unchanged — this ADR specifies what `RequireCapability` verifies, not where it lives. Same precedent as ADR-0044 specifying what `packages/go/migrate/` does without relocating ADR-0043's `middleware/`.
- **Operator authentication at P0: a single bootstrap operator account**, password-hashed with `argon2id` (stdlib `crypto/argon2`-compatible parameters), provisioned by `install.sh`. No self-service signup. No password reset UI. No OAuth providers. Operator login is `POST /v1/auth/login` on `services/api`; returns an operator session token. (Note: the file path is `services/api/internal/auth/` — handlers wired by `oapi-codegen`; the token-shape and verification primitives live in `packages/go/auth/`.)
- **Signing-key custody.** At P0 the cluster signing key lives in `services/api`'s secret store, mounted via the installer. Rotation is an operator action (`task auth rotate-key`) that emits an audit event; tokens issued under the prior key remain verifiable until their natural `exp` (key-rolling window: max key lifetime = max token lifetime = 8h).
- **Revocation at P0** is by **key rotation + short token lifetimes**, not by a revocation list. Per-token revocation (and JWKS-style asymmetric key rotation) is explicitly deferred to the day Zitadel lands.
- **Federation in (AD / Okta / SAML / OIDC): deferred to P1.** When the first enterprise customer requires it, **Zitadel** (single Go static binary, OIDC + SAML, event-sourced, actively maintained) is adopted as the IdP that fronts the in-process auth. A small mediator in `services/api` exchanges Zitadel-issued OIDC tokens for internal capability tokens. The internal token model, the `CapabilityToken` struct, and `RequireCapability` stay unchanged.

Keycloak, Authentik, Casdoor, the ORY suite, mTLS-only, and Dex-as-standalone are rejected at P0 under defined review triggers below.

## Alternatives considered

### A. Keycloak (Java + Quarkus)
Rejected at P0; **not held in reserve**.
- Pros: industry default for self-hosted enterprise SSO; deepest OIDC + SAML + LDAP + AD federation; RedHat-backed; every customer's IT department has run it.
- Cons:
  - JVM runtime (~700MB image, Infinispan-based clustering for HA) violates ADR-0041's single-static-binary posture by an order of magnitude.
  - Large CVE feed; non-trivial security-review surface.
  - Capability claims must be shoehorned into custom OIDC claim objects — stock `scope` strings do not encode the typed edges from `docs/security/agent-permission-model.md`.
  - At P0 we have one operator user and zero federation requirements. Paying enterprise-IdP cost for no enterprise benefit.
- Decisive: operational burden + supply-chain surface at P0 vs zero P0 benefit. Zitadel covers the same future enterprise-federation role with a Go-binary posture that matches ADR-0041.

### B. Authentik (Python + Go)
Rejected.
- Pros: modern UI, OIDC + SAML + LDAP outpost model.
- Cons: minimum four daemons (server + worker + redis + postgres). Python supply-chain surface (large pip dependency tree). LDAP/AD federation via "outposts" adds yet another daemon. Smaller community than Keycloak.
- Decisive: highest daemon count of any candidate for no P0 benefit.

### C. Zitadel (Go)
Rejected at P0; **held as the named P1 reserve pick.**
- Pros: single Go static binary (matches ADR-0041 posture exactly), OIDC + SAML, event-sourced (rhymes with our chained-hash mental model), multi-tenant native, actively maintained, modern.
- Cons:
  - Requires its own Postgres database + backup/restore story alongside per-service databases.
  - One more daemon to install, mirror, upgrade, monitor in restricted-network deploys.
  - At P0: one operator, zero federation. Pays daemon operational tax for zero P0 benefit. Exact same shape as ADR-0045's "NATS JetStream is right *eventually*, but premature at P0" calculus.
- Decisive: premature for P0. Adopt the day the first enterprise customer needs AD / Okta / SAML federation, or any of the other review triggers below fires. When adopted, `packages/go/auth/` becomes a verifier of Zitadel-issued OIDC tokens via a small mediator; the `CapabilityToken` schema and `RequireCapability` middleware stay unchanged.

### D. Dex (Go, OIDC federation gateway)
Rejected as standalone.
- Pros: tiny Go binary, federates to upstream IdPs.
- Cons: **not a user store.** No native user CRUD. Designed as a proxy to a customer's existing IdP — at P0 there is nothing to federate *to*.
- Disposition: not held in reserve in this ADR. If a P1+ deployment grows multiple upstream IdPs that Zitadel doesn't natively front-end, Dex may re-enter as a federation-gateway layer in a follow-up ADR.

### E. Casdoor (Go)
Rejected.
- Pros: single Go binary, OIDC + SAML.
- Cons: smaller, younger community than Zitadel; no compelling differentiator.
- Decisive: Zitadel dominates on the same axes.

### F. ORY suite (Hydra + Kratos + Keto + Oathkeeper)
Rejected.
- Pros: Go; capable; component-modular.
- Cons: four-daemon footprint. Operational burden disproportionate to P0 needs.
- Decisive: multi-daemon overhead with no P0 win over G.

### G. Minimal in-process auth in `packages/go/auth/` (adopted)

See *Decision*. Net-of-stdlib supply-chain delta: one MIT-licensed PASETO library (`github.com/aidantwoods/go-paseto`). No new daemon. No new database. No new operator action surface beyond a single `task auth rotate-key` and the bootstrap operator account in `install.sh`.

The shape is the ADR-0045 answer applied to identity: the smallest delta that preserves the load-bearing invariant (capability-edge enforcement under all four actor classes — operator, agent, service, lease) without standing up infrastructure we don't yet need.

### H. mTLS-only for service-to-service + no human auth at P0 (operator UI behind VPN only)
Rejected explicitly.
- Pros: zero token plumbing on the S2S edge.
- Cons:
  - Operator actions in `audit-service` MUST be attributable to a named operator. "Came from inside the VPN" is not an identity.
  - Adds cert provisioning + rotation + revocation operational burden on day one.
  - Forecloses on agent / lease tokens entirely (mTLS doesn't carry capability scopes).
- Decisive: cannot ship the cockpit's audit-attribution requirement. Held in reserve for a hardened-deploy profile *alongside* the token model, not in place of it.

## Decisive sub-questions — answers

### 1. Ship our own IdP at P0, or build minimal in-process auth? — In-process auth.

Same calculus as ADR-0045's "no broker at P0." P0 has one operator class, four actor classes inside the cluster, and zero federation requirements. The IdP-daemon question (federation in, user CRUD UI, password reset, OAuth providers) is *separable* from the token-verification question. Token verification is bounded, reviewable, and the typed `CapabilityToken` schema is *ours* — it does not map cleanly onto stock OIDC anyway. When federation is required, Zitadel fronts the in-process auth; the internal token model is unchanged.

### 2. Token shape. — PASETO v4 local with a typed `CapabilityToken` claim object.

PASETO over JWT: no `alg:none`, no algorithm confusion, no JWKS rotation infrastructure needed at P0. Local (symmetric) over public (asymmetric): smaller key-management surface at P0 with one signing key per cluster; the asymmetric variant becomes worthwhile when Zitadel lands and multiple services need to verify tokens minted by a third party.

Capability claims are a **typed claim object**, not stock OIDC `scope` strings. The `edge` field is one of the seven canonical edges from `docs/security/agent-permission-model.md` plus `service-service`. `scope` is a typed object containing `resource`, `operations`, and (for egress leases) `lease_id`. This shape is unrepresentable in stock OIDC `scope: "read write admin"` strings without lossy encoding — another reason an OIDC-daemon's "advantage" is illusory for this product.

### 3. Service-to-service auth. — Signed PASETO service tokens with workload identity. (Closes the ADR-0045 hangover.)

The outbox relay's HTTP call to `audit-service` (and every other internal RPC) carries `Authorization: Bearer <service-paseto>` with `edge: service-service`, `sub: <service-name>`, `aud: <target-service>`, 1-hour TTL. The service mints its own token at startup from a workload bootstrap key mounted at install time, refreshes hourly in-process, and the receiving service's `RequireCapability` middleware verifies via the same `packages/go/auth/Verifier` as human and agent traffic. **Not mTLS at P0.** mTLS held in reserve.

### 4. Short-lived capability tokens. — Yes; tiered by actor class. (Closes the deep-dive 30 open question.)

| Actor | TTL | Refresh | Revocation |
|---|---|---|---|
| Agent session | 5 min | While parent operator session active; audit event per refresh | Wait for `exp` or rotate signing key |
| Operator session | 8 h | Sliding refresh on activity | Rotate signing key |
| Service workload | 1 h | Auto-refresh in-process | Rotate workload bootstrap key |
| Egress lease | = lease expiry | None (single-use) | `jti` recorded in `policy-service`; replay rejected |

Signing key lives in `services/api`'s secret store at P0, mounted via `install.sh`. Key rotation = `task auth rotate-key`, emits an audit event, rolling window equals max token lifetime (8h). Per-token revocation (and asymmetric JWKS rotation) deferred to the day Zitadel lands.

### 5. Federation in. — Deferred to P1.

Zitadel (named reserve) fronts the in-process auth when the first enterprise customer requires AD / Okta / SAML / OIDC federation. Mediator: `services/api` exchanges Zitadel OIDC tokens for internal capability tokens. The internal token model and `RequireCapability` are unchanged.

### 6. Where does verification code live. — `packages/go/auth/`.

Mirrors the `packages/go/middleware/` (ADR-0043), `packages/go/migrate/` (ADR-0044), and `packages/go/outbox/` (ADR-0045) precedent. Exports `Signer`, `Verifier`, `CapabilityToken`, bootstrap-key helpers. **`packages/go/middleware/RequireCapability` imports `packages/go/auth/`** — middleware shape unchanged; auth module owns the token shape and crypto.

### 7. Approval workflow integration. — In scope for `packages/go/auth/` + `policy-service`; out of scope for any IdP daemon.

An approved action becomes a **one-shot capability token** with the approval `jti` recorded in `policy-service`'s decisions table. `connector-service` (or the relevant enforcement point) rejects token re-use by `jti` lookup. Approval emission flows through the ADR-0045 outbox into `audit-service`. No IdP daemon — even a future Zitadel — owns approval semantics; `policy-service` is the authority.

## Consequences

### Positive

- **No new daemon in the P0 offline installer.** No JVM. No Python+Redis+Postgres. No Zitadel-Postgres. One MIT-licensed PASETO library added to the Go module cache.
- **Capability-edge model preserved by construction.** The typed `CapabilityToken.edge` field encodes the model from `docs/security/agent-permission-model.md` directly; no shoehorning into stock OIDC claims.
- **Service-to-service auth is the same primitive as human and agent auth.** One verifier, one middleware, one audit shape. Closes the ADR-0045 hangover.
- **Supply-chain delta is one well-known MIT module** (`github.com/aidantwoods/go-paseto`) plus the typed claim struct. Within the budget set by ADR-0041 / ADR-0042.
- **Token issuance is itself a capability-edge event** — every issue and every refresh writes a structured audit event via the ADR-0045 outbox into the chained-hash log.
- **Egress leases per `docs/security/egress-policy.md` are encoded as the same primitive** — `connector-service` mints lease tokens via `packages/go/auth/Signer.IssueLease`; `jti` enforced by `policy-service`.
- **Federation-in is a clean P1 swap-in.** Zitadel adoption changes the *issuance front door*, not the internal token model or `RequireCapability`.
- **Pattern coherence with prior ADRs.** Fifth application of the `packages/go/<infra>/` shape:

  | ADR | Module | Role |
  |---|---|---|
  | ADR-0043 | `packages/go/middleware/` | shared HTTP middleware (capability-edge enforcement point) |
  | ADR-0044 | `packages/go/migrate/` | shared migration runner |
  | ADR-0045 | `packages/go/outbox/` | shared outbox writer + relay |
  | **ADR-0046** | **`packages/go/auth/`** | **shared signer + verifier + capability-token type** |

- **Closes the deep-dive 30 security question** *"How to design short-lived capability tokens"* — 5/60/8-hour tiered TTLs, refresh-audited, rotation-revoked.
- **Closes the Identity layer placeholder** from `docs/deep-dive/09-offline-self-hosting-deployment.md` — no IdP daemon at P0; Zitadel named as the P1 candidate (Keycloak is rejected).

### Negative

- **Rolling-our-own-auth optics.** We carry the burden of explaining that `packages/go/auth/` does *not* roll crypto (PASETO ref impl + stdlib `argon2id`), does *not* ship user CRUD beyond a bootstrap operator account, does *not* ship password reset / OAuth providers / SSO. The forbidden-features list is part of this ADR. Mitigation: explicit Security Reviewer trip-wire — if any of `password reset UI`, `self-service signup`, `OAuth provider integration`, or `JWKS-style asymmetric rotation` becomes a P0 ticket, that is the trigger to adopt Zitadel.
- **Per-token revocation requires key rotation at P0.** A leaked agent token cannot be revoked individually; the operator must rotate the signing key, invalidating all live tokens until they refresh. Acceptable at P0 (5-min agent TTL bounds blast radius) but documented as a gap.
- **Signing-key custody at P0 is single-cluster-key.** Multi-cluster federation requires asymmetric keys + JWKS; deferred to the Zitadel adoption window.
- **The `services/api` boot dependency on a signing-key secret** is one more thing `install.sh` must place. Mitigation: documented in the offline-install playbook; key generation is `openssl rand` / `crypto/rand` — no external dependency.
- **CI lint for "do not import the PASETO library outside `packages/go/auth/`"** is deferred to P1 (mirrors the ADR-0044/ADR-0045 review-enforced verification gaps).

### Held in reserve

- **Zitadel — adopted as the cluster IdP the day any one of these fires:**
  - First enterprise customer requires AD / Okta / SAML / OIDC federation.
  - Any of `password reset UI`, `self-service signup`, `OAuth provider integration`, or per-token revocation becomes a load-bearing requirement.
  - Operator count grows past a level where `install.sh`-bootstrapped account provisioning is a real friction (rough threshold: ≥3 distinct operator accounts across ≥2 customer environments).
  - JWKS-style asymmetric key rotation becomes load-bearing (e.g., multi-cluster trust).
- **mTLS for service-to-service** — adopted as a hardened-deploy-profile add-on layered *on top of* the service-token model, not in place of it. Trigger: customer-deploy regime that mandates transport-level peer authentication.
- **Dex** — held informally as a P1+ federation-gateway layer in front of Zitadel if multi-upstream-IdP scenarios arise. No ADR commitment.
- **Keycloak, Authentik, Casdoor, ORY suite** — not held in reserve. If a real IdP daemon is needed, Zitadel is the destination.

## Verification

This ADR is verified once the following hold:

1. `packages/go/auth/` exists as a Go module under `go.work` and exports `Signer`, `Verifier`, and the typed `CapabilityToken` struct with fields `sub`, `edge`, `scope`, `iat`, `exp`, `jti`, `aud`, `iss`.
2. At least one service (e.g., `services/api`) declares `github.com/aidantwoods/go-paseto` in its `go.mod`, mints operator session tokens via `packages/go/auth/Signer`, and verifies them via `packages/go/auth/Verifier`.
3. `packages/go/middleware/RequireCapability` (ADR-0043) imports `packages/go/auth/` and uses `Verifier` to extract `edge` + `scope` from the bearer token; middleware shape (`func(http.Handler) http.Handler`) is unchanged.
4. The ADR-0045 outbox relay's HTTP client to `audit-service` attaches `Authorization: Bearer <service-paseto>` with `edge: service-service`, and `services/audit-service`'s `POST /v1/events` accepts the call via the same `RequireCapability` middleware that gates human and agent traffic. The ADR-0045 verification target ("relay's HTTP client to `audit-service` will plug into whichever auth model lands") is satisfied.
5. `services/connector-service` mints egress lease tokens via `packages/go/auth/Signer.IssueLease` (or equivalent) with `lease_id` and per-domain `scope` matching `docs/security/egress-policy.md`; `policy-service` records lease `jti`s and rejects replay.
6. Token issuance and refresh emit structured audit events via the ADR-0045 outbox; the integrity test from ADR-0041 §Verification continues to pass under concurrent auth-event traffic.
7. The deploy artifact for every P0 service remains a single static binary; no IdP daemon ships in the offline installer at P0.
8. `install.sh` provisions the bootstrap operator account (argon2id-hashed) and the cluster signing key as part of the offline-install procedure.

Known verification gaps at P0:

- No CI lint enforces "do not import `github.com/aidantwoods/go-paseto` outside `packages/go/auth/`." Documented and review-enforced at P0; P1 lint ticket.
- No CI lint enforces the *forbidden features* list (no password reset UI / no self-service signup / no OAuth provider integration / no JWKS rotation). Documented and review-enforced at P0; P1 lint ticket.
- Per-token revocation list infrastructure does not exist at P0 (revocation = key rotation + short TTL).

## Review triggers

Re-open this ADR if any of these become true:

- **First enterprise customer requires AD / Okta / SAML / OIDC federation** → adopt **Zitadel**.
- Any of password reset UI, self-service signup, OAuth provider integration, or JWKS-style asymmetric rotation becomes a load-bearing requirement → adopt **Zitadel**.
- Operator count grows past ~3 distinct operator accounts across ≥2 customer environments → adopt **Zitadel** for the user-store role.
- Per-token revocation (without full key rotation) becomes load-bearing → adopt **Zitadel** *or* propose a follow-up ADR for an internal revocation-list service.
- A customer-deploy regime mandates transport-level peer authentication → adopt **mTLS** as a hardened-deploy-profile add-on layered on the service-token model.
- A PASETO supply-chain or correctness incident materially affects trust posture → re-evaluate the token format (next candidates: stdlib-only HMAC-SHA256 over a versioned binary envelope, or paseto-public asymmetric variant).
- The capability-edge model itself is revised (`docs/security/agent-permission-model.md` edges change shape) → re-evaluate the `CapabilityToken.edge` field and `RequireCapability` integration.
- The operator UI moves from "single bootstrap account" to multi-tenant SaaS posture → contradicts ADR-0001 and would force a wholesale revisit, not just this ADR.

## Output contract (per kit specialist-output format)

- **Scope**: authentication adapter for all P0+ services; consumed by every service-implementation ticket from T-002 onward; explicitly closes the deep-dive 30 security question and the deep-dive 09 Identity placeholder; closes the ADR-0045 hangover on service-to-service auth.
- **Findings**: P0 has one operator user, four actor classes (operator / agent / service / lease), and zero customer-IdP federation requirements. The capability-edge model from `docs/security/agent-permission-model.md` is too structured to encode in stock OIDC `scope` strings — every IdP-daemon candidate would require a custom claim object anyway.

# ADR-0047: Frontend framework for `apps/web` — no meta-framework at P0; plain Vite 6 + React 18 SPA served as static assets; Remix (SPA mode) held as the P1 reserve pick

## Status
Accepted — 2026-05-19.

## Context

ADR-0041 established Go as the primary backend language and TypeScript as the frontend-only language for `apps/web` (with `apps/admin` scoped for later), under a single-static-binary deploy posture with a tight supply-chain surface. ADR-0042 established Go workspaces + pnpm workspaces + Taskfile as the monorepo tooling, named `apps/web` and `apps/admin` as pnpm workspace members consuming shared `packages/{ui,shared-types,config}`, declined Turborepo/Nx at P0, and called out the Vercel-deploy-primitive footgun (remote cache, deploy-only features) as a release-guard hazard. ADR-0043 established `go-chi/chi` v5 + `oapi-codegen` (`chi-server` generator) over `docs/api-contracts/openapi.v3.fragment.yaml` as the canonical contract; the TypeScript client for `apps/web` is generated from the same source. ADR-0044, ADR-0045, and ADR-0046 are largely orthogonal to the frontend; ADR-0046 is the one that *does* bind: `packages/go/auth/` issues PASETO v4 capability tokens with a typed `CapabilityToken` claim object; tokens are **opaque to the browser**; operator session tokens have an 8-hour sliding refresh; service-side `RequireCapability` middleware is the security boundary.

This ADR picks the frontend framework for `apps/web` and closes the last Pending row in the `CANONICAL_SOURCE_OF_TRUTH.md` ADR ladder for the v3.0.1 + ADR-0041..ADR-0047 meta-decision baseline.

The decisive constraints are inherited:

1. **Self-hosted / offline-first** (ADR-0001). The build output must mirror cleanly into the restricted-network installer. No Vercel-only deploy primitives, no SaaS-hosted image/font pipelines, no Vercel remote cache (ADR-0042 footgun applies doubly here).
2. **Single static binary + no surprise daemons in production** (ADR-0041, in spirit). A `next start` / `remix start` Node process is a daemon — a surprise daemon if the framework choice forces SSR. Static-asset output served by the reverse proxy already named in deep-dive 09 (Caddy or Traefik) is the in-doctrine shape.
3. **Tight supply-chain surface** (ADR-0041). Every framework-level dep, every transitive npm tree, every plugin ecosystem is something the security review must vet on every minor bump.
4. **P0 ship velocity** (ADR-0041, ADR-0042). `apps/web` is the operator cockpit — the wedge requires it to land in the P0 vertical slice.
5. **Capability-edge model** (`docs/security/agent-permission-model.md`). Every UI action that crosses an edge must be gated by the operator's capability claims; the UI must hide/disable actions the token does not scope to.
6. **Egress approvals live in the UI** (`docs/security/egress-policy.md`). The human-approval prompt for sensitive access is a frontend component.
7. **Sandbox session hot path** (`docs/security/sandbox-security.md`, deep-dive 09). The cockpit embeds an HTML5 GUI gateway (Apache Guacamole) and an xterm.js terminal, and holds long-lived WebSocket / SSE channels into `services/session-broker`.
8. **Diff budget ≤12 files / ≤500 LoC per ticket** (`CLAUDE.md`).

Inventory of the cockpit's actual shape:

| Concern | Shape | Notes |
|---|---|---|
| Anonymous landing / SEO | None | Cockpit is post-login; no marketing surface in `apps/web`. |
| First paint timing | Post-login dashboard | SSR's main wins (FCP for anonymous users, crawler indexability) do not apply. |
| Routing | Modest at P0 (< 30 routes across `apps/web`) | File-based routing not yet load-bearing. |
| Data fetching | Typed HTTP against `services/api` + WebSocket / SSE against `services/session-broker` | Schema is OpenAPI; client is generated. |
| Interactivity | High — capability-gated actions, modals, forms, tables, live log tails, terminal, GUI gateway | SPA-shaped. |
| Component-library ecosystem | Radix / shadcn / Headless UI dominate the accessible-primitive space | All React. |

The decisive sub-question for this ADR is therefore the ADR-0045-shaped question, transposed onto the frontend: *"do we need a meta-framework at P0 at all, or can the vertical slice ship with a plain Vite SPA that the same Caddy/Traefik already in the deep-dive 09 stack serves as static files?"*

## Decision

- **No meta-framework at P0.** `apps/web` and `apps/admin` are **plain Vite 6 + React 18 single-page applications** built to static assets and served by the reverse proxy from `docs/deep-dive/09-offline-self-hosting-deployment.md` (Caddy or Traefik). No Node runtime ships in production. No SSR. No ISR. No server actions. No image optimization daemon. No middleware that runs server-side at request time.
- **Framework: React 18.** Picked for ecosystem reach (Radix / shadcn / Headless UI), hiring pool, and AI-tooling familiarity. Bundle-size delta vs. Svelte / Solid is not load-bearing for an authenticated cockpit.
- **Bundler / dev server: Vite 6.** Pinned to a specific minor; every minor bump is a security-review item per ADR-0001 doctrine.
- **Routing: `react-router` v7 in declarative SPA mode** (not its framework mode). Route tree authored in code; manual is fine at P0 scale. File-based routing is a P1 review trigger (≥30 routes across both apps).
- **Server-state caching: deferred.** `fetch` + React hooks at P0. **TanStack Query** is the named pick when caching becomes load-bearing (multi-component subscription on the same query, optimistic updates, stale-while-revalidate semantics). Not pre-added.
- **TypeScript client codegen: `openapi-typescript` (types-only) + `openapi-fetch` (~3 KB runtime).** Generated types and the fetch wrapper live in `packages/shared-types/`. Generator invocation extends the existing `task codegen` Taskfile target alongside the Go `oapi-codegen` invocation from ADR-0043 — one schema (`docs/api-contracts/openapi.v3.fragment.yaml`), two codegen consumers.
- **Styling: Tailwind CSS v4.** Zero-config; no PostCSS plugin chain. Tokens (color, typography, spacing, radius, elevation, motion, semantic states) defined in `packages/config/tailwind.config.ts`. Satisfies `design-system-governance.md` preflight's Token Map requirement.
- **Component primitives: vendored shadcn/ui pattern.** shadcn is *not* an npm dependency; components are copy-pasted into `packages/ui/src/components/` and version-controlled here. The team owns the component code. Underlying accessibility primitives are **Radix UI** (npm dep, pinned). Satisfies `design-system-governance.md` preflight's Component Registry requirement.
- **Auth-token storage: httpOnly cookie set by `services/api` on `POST /v1/auth/login`.** Cookie attributes: `HttpOnly; Secure; SameSite=Strict; Path=/`. The PASETO v4 token from ADR-0046 stays opaque to JS by construction (no `localStorage`, no in-memory copy). The browser sends it automatically on every same-origin request; the architectural equivalent of `Authorization: Bearer <token>` is satisfied without exposing the token to the JS context.
- **CSRF defense: double-submit token.** On login, `services/api` sets a second non-`HttpOnly` cookie (`csrf-token`) containing a random value bound to the session. The frontend reads it and echoes it in an `X-CSRF-Token` header on all non-idempotent requests (POST / PUT / PATCH / DELETE). The middleware (shared chain from ADR-0043) verifies equality. `SameSite=Strict` on the session cookie is the primary defense; the double-submit token is defense-in-depth and required because the cockpit also serves embedded GUI / terminal surfaces whose sub-resources can complicate strict cookie behavior.
- **Refresh: server-side cookie rotation.** ADR-0046's 8-hour sliding refresh is implemented by `services/api` re-issuing the session cookie whenever the current token is in the second half of its TTL (i.e., < 4h to `exp`). No explicit refresh endpoint at P0. No client-side refresh logic.
- **401 handling: single chokepoint.** The `openapi-fetch` client wraps responses in `packages/shared-types/src/client.ts`; a 401 triggers a redirect to `/login` and clears the in-memory `<CapabilityProvider>` cache. No retry, no silent re-auth.
- **Capability-edge UI enforcement: `GET /v1/auth/me` + `<CapabilityProvider>` + `<CapabilityGate>`.** Token stays opaque (the PASETO v4 *local* variant is symmetric — the browser couldn't verify it even if it had it). On app mount and after any auth transition, the frontend calls `GET /v1/auth/me` (typed by the OpenAPI fragment) which returns the operator's current capability claims (`edge` + `scope` array). A React context (`<CapabilityProvider>` in `packages/ui/`) exposes them; a `<CapabilityGate edge="agent-tool" scope={…}>` component conditionally renders children; route-level guards reject unauthorized navigation. **Server-side `RequireCapability` (ADR-0046) remains the security boundary. The UI is UX only** — bypassing the gate in the browser changes nothing the server will permit.
- **Approval-prompt component shape.** Egress and other approval-required actions surface an `<ApprovalPrompt>` component (in `packages/ui/`) that subscribes to the relevant approval stream (SSE or WS, from `services/api`), renders the operator-facing decision UI, and POSTs the decision back through the typed client. Detailed UX deferred to a UI spec; this ADR commits the *architecture* — approval lives in the cockpit, not in a separate channel.
- **Session-broker channel: native `WebSocket` + `EventSource`.** Thin React hooks (`useWebSocketChannel`, `useEventSource`) in `packages/ui/src/hooks/`. No heavyweight library at P0. Auto-reconnect with exponential backoff. Auth piggybacks on the same `HttpOnly` session cookie (the WS handshake is an HTTP upgrade; the cookie is sent automatically); the broker's `RequireCapability` middleware verifies the upgraded connection like any other capability-edge request.
- **GUI gateway embedding: `guacamole-common-js` from npm.** Mounted to a `<canvas>` element inside a `<RemoteSessionView>` React component in `packages/ui/`. Vite handles it as a normal ES module; no SSR-window-access concern because there is no SSR.
- **Terminal embedding: `xterm.js`.** Wired to a `services/session-broker` WebSocket channel via the same `useWebSocketChannel` hook; mounted in a `<TerminalView>` component in `packages/ui/`.
- **`packages/*` boundaries:**

  | Package | Owns |
  |---|---|
  | `packages/ui` | React component primitives (vendored shadcn), tokens, layouts, `<CapabilityProvider>` / `<CapabilityGate>` / `<ApprovalPrompt>` / `<RemoteSessionView>` / `<TerminalView>`, WS/SSE hooks. |
  | `packages/shared-types` | Generated OpenAPI types (`openapi-typescript` output, committed) + the `openapi-fetch` client wrapper (`client.ts`) including the 401 chokepoint. |
  | `packages/config` | Shared `eslint.config.ts`, `prettier.config.cjs`, `tsconfig.base.json`, `tailwind.config.ts`. ESLint rule forbidding `dangerouslySetInnerHTML` and equivalent XSS escape hatches lives here (Security Reviewer ask). |

- **`apps/admin` reuse.** Same framework choice (plain Vite 6 + React 18). Both apps consume `packages/{ui,shared-types,config}`. Different `app/` shells and `<Route>` trees.
- **Production serving:** the two apps build to `apps/web/dist/` and `apps/admin/dist/`. The deep-dive 09 reverse proxy (Caddy or Traefik) serves them as static asset bundles with cache-busting hashed filenames. **`services/api` and the static assets are served same-origin** (different paths, e.g., `/` and `/api/`) so the `SameSite=Strict` cookie posture holds without CORS gymnastics.

Next.js, Remix in its default SSR mode, SvelteKit (any), Astro, Nuxt, Solid Start, TanStack Start at P0, Plain Vite + Svelte, and meta-frameworks generally at P0 are rejected under defined review triggers below. **Remix (in SPA mode) — or TanStack Start when GA — is held as the named meta-framework reserve pick. Next.js is explicitly NOT held in reserve.**

## Alternatives considered

### A. Next.js (React; SSR/SSG/ISR/RSC; Vercel-favored)

Rejected. **Not held in reserve.**

- Pros: largest React meta-framework community; best-known data-loading conventions (RSC + server actions); first-class TypeScript; mature.
- Cons:
  - **Vercel-deploy-primitive footgun.** `next start` is a Node daemon. Image optimization wants a Node runtime. ISR wants a writable filesystem. Server actions want a server. `next build --output standalone` mitigates the daemon question but does not eliminate the framework's *gravity* toward server-first patterns — every Next.js release nudges further server-side. A future contributor following Next docs naturally drifts toward server-mode features.
  - The remote-cache hazard ADR-0042 named for Turborepo applies here too: Vercel's deploy stack is the framework's home; opting out is a permanent project tax.
  - Static export (`output: 'export'`) exists but is a degraded path with growing exclusions (RSC server components, server actions, middleware, image optimization API). Building a serious cockpit on the static-export edge of an actively-server-tilting framework invites churn.
  - Largest transitive npm dep tree of any candidate — single highest supply-chain delta.
- Decisive: the framework's center of gravity actively opposes the offline-install + no-surprise-daemons posture of ADR-0041 / ADR-0042. **Not held in reserve** for the same reason — committing to Next as the *future* answer commits to fighting the framework forever. Remix or TanStack Start are the honest reserve picks.

### B. Remix (React Router v7; web-fundamentals oriented; supports SPA mode)

Rejected at P0; **held as the named meta-framework reserve pick.**

- Pros: web-fundamentals philosophy (server-rendered HTML, progressive enhancement, `Form` actions); SPA mode is first-class (not bolt-on like Next's static export); the Remix → React Router v7 unification means a single library that scales from plain SPA up to full meta-framework as needs grow; less Vercel-locked.
- Cons:
  - At P0 there is no SSR need; the meta-framework value (file-based routing, loaders, actions) is mostly P1+ ergonomics.
  - Smaller community than Next; documentation post-merger with React Router is in flux as of 2026.
  - Even in SPA mode it commits the project to React Router's framework conventions; rolling back is feasible but not free.
- Decisive: premature for P0. **The right *eventual* meta-framework when conventions become load-bearing** — file-based routing past ~30 routes, recurring multi-step data prep on a single route, or a genuine SSR need (unlikely for a post-login cockpit). See *Review triggers*.

### C. SvelteKit (Svelte; SSR/SPA/SSG; Node or static adapter)

Rejected.

- Pros: smallest bundles of any candidate; static adapter ships a clean static-asset build; ergonomic.
- Cons:
  - **Non-React.** The accessible-primitive ecosystem (Radix, Headless UI, shadcn) is overwhelmingly React. Svelte alternatives (Bits UI, Melt UI, Skeleton) are real but a tier smaller. The cockpit's component surface is large enough that the ecosystem delta matters.
  - The bundle-size win Svelte trades for is not load-bearing for an authenticated dashboard the operator stays in for hours.
  - Hiring pool and AI-tooling familiarity are smaller.
- Decisive: trading the React component ecosystem for a bundle-size win the cockpit can't spend.

### D. Astro (multi-framework islands; static-first)

Rejected.

- Pros: static-first is genuinely the best offline-install fit on paper; islands let you mix React/Svelte/Solid components per page.
- Cons:
  - Astro's model is **content-site-shaped** (mostly-static pages with islands of interactivity). The cockpit is the opposite — mostly-interactive pages with islands of static content. Islands fight the SPA-dashboard shape.
  - Cross-island state management is awkward; the cockpit has app-wide state (auth, capabilities, active session) that wants a single React tree.
- Decisive: shape mismatch. Astro is built for the page archetype the cockpit is not.

### E. Nuxt (Vue)

Rejected.

- Pros: analogous to Next on the Vue side; mature.
- Cons: same SSR-tilt and Node-daemon concerns as Next; non-React ecosystem; no compelling differentiator.
- Decisive: combines the worst of Next (SSR gravity) with the worst of SvelteKit (smaller React-equivalent ecosystem).

### F. Solid Start (SolidJS; small/fast)

Rejected.

- Pros: smallest runtime; fast.
- Cons: smallest community; smallest hiring pool; smallest AI-tooling familiarity; non-React ecosystem; project still maturing.
- Decisive: ecosystem risk disproportionate to the runtime-size win.

### G. TanStack Start (React; newer; built on TanStack Router)

Rejected at P0; **held informally as an alternative to Remix in the meta-framework reserve.**

- Pros: type-safe routing best-in-class; built on TanStack Router which is excellent; React; actively developed.
- Cons: pre-GA / early as of 2026-05; not yet battle-tested for the cockpit's interactive surface area; reserve pick should be more proven at the moment of adoption.
- Disposition: held alongside Remix as the named reserve. The pick between them is deferred to the day the trigger fires; Remix wins today on maturity, TanStack Start may win by then.

### H. Plain Vite 6 + React 18 SPA (no meta-framework)

**Adopted.** See *Decision*. Net-of-stdlib supply-chain delta: Vite + React + React Router + Radix primitives + Tailwind + the codegen tools (`openapi-typescript`, `openapi-fetch`) + dev tooling. Substantially smaller than any meta-framework candidate on every transitive-dep axis.

The shape is the ADR-0045 answer applied to the frontend: the smallest delta that preserves the load-bearing invariant (an interactive React cockpit with capability-gated actions) without standing up infrastructure (SSR Node daemon, file-based router, server-action plumbing) we do not yet need.

### I. Plain Vite + Svelte SPA

Rejected. Same ecosystem-delta argument as C; the "no meta-framework" win is shared with H without compensating for the React-ecosystem loss.

## Decisive sub-questions — answers

### 1. SSR / SSG / SPA at P0 — SPA.

The cockpit is authenticated. There is no SEO (login wall), no anonymous-user TTFB to optimize, no public landing surface in `apps/web`. The two real SSR wins do not apply.

The *cost* of SSR is a `next start` / `remix start` Node daemon in production — a "surprise daemon" against ADR-0041's single-static-binary spirit and a release-guard regression against ADR-0042's offline-install posture and Vercel-footgun call-out. Static-asset SPA is the in-doctrine shape: build to `dist/`, mirror into `task offline-bundle`, serve via Caddy/Traefik already in the deep-dive 09 stack.

### 2. Meta-framework or plain Vite — Plain Vite.

Once SPA is the shape, ~80% of meta-framework value (SSR, server-rendered loaders, server actions, RSC) is unused. The remaining 20% (file-based routing, dev-time conventions) is real ergonomics but not load-bearing at P0 scale (< 30 routes total across both apps). The ADR-0045-shaped answer applies cleanly: **no meta-framework at P0; plain Vite + React SPA; Remix (SPA mode) or TanStack Start held as the named P1 reserve** if conventions become load-bearing.

### 3. React or non-React — React.

Component-library ecosystem (Radix, shadcn, Headless UI, Mantine) is overwhelmingly React. The cockpit's component surface (capability-gated actions, modals, forms, tables, live data, embedded GUI, terminal, approval prompts) is large enough that ecosystem reach is decisive. Hiring pool, AI-tooling familiarity, and Tech Lead / Frontend Lead consensus all point the same way. Bundle-size delta vs. Svelte/Solid is not load-bearing post-login.

### 4. TS client codegen — `openapi-typescript` + `openapi-fetch`.

Candidates: `openapi-typescript` + `openapi-fetch` (types-only generator + ~3 KB runtime fetch wrapper), `orval` (heavier, generates react-query hooks), `kubb` (newer, pluggable), hand-rolled (N/A given OpenAPI is canonical).

Pick: **`openapi-typescript` + `openapi-fetch`**. Reasoning:
- Smallest runtime footprint (matches ADR-0042's "smallest viable tooling kit" doctrine).
- Types-only generation = no data-fetching-layer lock-in. TanStack Query can layer cleanly when needed; or be replaced.
- Drops cleanly into `task codegen` alongside the Go `oapi-codegen` invocation from ADR-0043 — one schema, two consumers.
- Smallest supply-chain delta of the candidates.
- Mirrors the ADR-0043 stance: schema-first, generated code committed, no surprise runtime.

### 5. Auth-token storage — `HttpOnly; Secure; SameSite=Strict` cookie set by `services/api`.

The three real options:

| Option | XSS | CSRF | UX | Same-origin required |
|---|---|---|---|---|
| httpOnly cookie | Immune (JS can't read) | Mitigated (SameSite=Strict + double-submit) | Native (browser handles) | Yes |
| In-memory only | Immune | Immune | Lost on refresh — terrible for 8h session | No |
| `localStorage` | Exposed (any script) | N/A | Native | No |

The cockpit will eventually render operator-controllable content (terminal output, file contents, log lines, agent outputs). XSS surface is non-trivial. `localStorage` is the wrong answer for an ADR-aware product. In-memory destroys the 8-hour sliding refresh UX.

**Pick: httpOnly cookie.** Attributes: `HttpOnly; Secure; SameSite=Strict; Path=/`. Same-origin is the in-doctrine deploy posture anyway (Caddy/Traefik fronts both `apps/web` static and `services/api` from the same hostname). CSRF defense = `SameSite=Strict` primary, double-submit `X-CSRF-Token` header secondary (required because embedded GUI / terminal surfaces complicate strict cookie behavior). The PASETO v4 token stays opaque to JS by construction.

### 6. Capability-edge UI enforcement — `GET /v1/auth/me` + `<CapabilityProvider>` + `<CapabilityGate>` + route guards.

Parsing the PASETO token on the client is *impossible* with the v4 local variant — it's symmetric authenticated encryption; the browser doesn't have the key and shouldn't. Even with the public variant, parsing the token on the client to drive UI state is the wrong shape: the UI's notion of capabilities should be a regular typed API response, not a side-effect of token inspection.

**Pick:** `services/api` exposes `GET /v1/auth/me` (typed by the OpenAPI fragment) returning the operator's current `CapabilityToken.edge` + `scope` claims as a regular response. A React context provider `<CapabilityProvider>` (in `packages/ui`) fetches on mount and on auth transitions. A `<CapabilityGate edge="agent-tool" scope={...}>` component conditionally renders children; route-level guards reject unauthorized navigation.

**Server-side `RequireCapability` (ADR-0046) remains the security boundary.** The UI gate is UX only — a user with browser DevTools who edits the React context to claim capabilities they don't have will see additional buttons render and immediately receive 403s when they click them. This separation is explicit.

### 7. Where shared frontend code lives — split between `packages/ui`, `packages/shared-types`, `packages/config`.

| Package | Owns | Why here |
|---|---|---|
| `packages/ui` | React components, tokens, layouts, capability provider/gate, approval prompt, remote-session view, terminal view, WS/SSE hooks | React-shaped; consumed by both apps |
| `packages/shared-types` | Generated OpenAPI types + `openapi-fetch` client wrapper (incl. 401 chokepoint) | Contract-bound; consumed by both apps (and conceptually by anything else that talks to `services/api`) |
| `packages/config` | Shared `eslint.config.ts`, `prettier.config.cjs`, `tsconfig.base.json`, `tailwind.config.ts`, `dangerouslySetInnerHTML` lint rule | Cross-cutting build/lint surface |

### 8. `apps/admin` reuse — same framework.

Plain Vite 6 + React 18 + React Router v7 for both. `packages/ui` shared. Different `app/` shells and route trees. `apps/admin` is P1+ scoped but this ADR commits the choice serves both — no second framework gets introduced for the second app.

### 9. Session-broker channel — native `WebSocket` + `EventSource` with thin React hooks.

`useWebSocketChannel` and `useEventSource` hooks in `packages/ui/src/hooks/`. Auto-reconnect with exponential backoff. Auth via the same `HttpOnly` session cookie (sent automatically on the HTTP upgrade handshake). `services/session-broker`'s `RequireCapability` middleware (per ADR-0043 + ADR-0046) gates the upgraded connection identically to any other capability edge. No heavyweight WS client library at P0; revisit when reconnection / multiplexing / channel-fan-out becomes load-bearing.

### 10. Guacamole embedding — `guacamole-common-js` from npm, mounted in `<RemoteSessionView>`.

`guacamole-common-js` is a regular ES module; Vite handles it cleanly. Mounted to a `<canvas>` element inside `<RemoteSessionView>` in `packages/ui/`. No SSR concern because no SSR (no `window`-access pitfalls at build time). Auth piggybacks on the same session cookie for the underlying WebSocket tunnel via the session broker.

## Consequences

### Positive

- **No Node runtime in production.** The deploy artifact for the frontend is a directory of hashed static files. Mirrors trivially into `task offline-bundle` via the existing `pnpm fetch` pipeline from ADR-0042. Served by the Caddy/Traefik already named in deep-dive 09. **Vercel-deploy-primitive footgun avoided by construction.**
- **Supply-chain surface is the smallest of any candidate.** Vite + React + React Router + Radix primitives + Tailwind + two small codegen tools. No meta-framework dep tree.
- **Schema-first contract preserved end-to-end.** One OpenAPI fragment (`docs/api-contracts/openapi.v3.fragment.yaml`) drives `oapi-codegen` (Go server stubs, ADR-0043) AND `openapi-typescript` + `openapi-fetch` (TS client). Same `task codegen` target.
- **Capability-edge model preserved by construction.** `<CapabilityGate>` reads typed claims from `GET /v1/auth/me`; server-side `RequireCapability` (ADR-0046) remains the security boundary.
- **PASETO token stays opaque to the browser.** httpOnly cookie + SameSite=Strict + double-submit CSRF token. Same-origin deploy posture matches the in-doctrine reverse-proxy stack.
- **Sliding refresh is server-side.** `services/api` rotates the cookie in the second half of TTL. No client-side refresh logic; no client-side scheduler.
- **Both apps reuse `packages/{ui,shared-types,config}` cleanly.** `apps/admin` (P1+) lands without a framework re-decision.
- **Pattern coherence with prior ADRs.** Sixth application of the "no X at P0; in-process Y; Z as named P1 reserve" shape:

  | ADR | No X at P0 | In-process / minimal Y | Named P1 reserve |
  |---|---|---|---|
  | ADR-0045 | event broker | Postgres outbox + sync HTTP | NATS JetStream |
  | ADR-0046 | IdP daemon | `packages/go/auth/` PASETO | Zitadel |
  | **ADR-0047** | **meta-framework** | **plain Vite + React SPA** | **Remix (SPA mode) / TanStack Start** |

- **P0 ship velocity.** No framework conventions to learn; no SSR-vs-static-export pitfalls to litigate; no Vercel-vs-self-host trade-offs to manage. The cockpit team writes React.
- **Design-system governance preflight is satisfied.** Tokens via Tailwind config; component registry via vendored shadcn pattern; a11y baseline via Radix; explicit approval-required-changes list lands in `packages/ui/README.md`.

### Negative

- **No file-based routing at P0.** Manual `<Route>` tree maintenance is fine at < 30 routes; ergonomics degrade past that. Mitigated by the explicit review trigger below.
- **No framework-level data loaders.** Multi-step data prep on a route is hand-rolled with `useEffect` / TanStack Query patterns. Acceptable at P0 scale; same review trigger applies.
- **No RSC / streaming.** Authentication-gated dashboards do not benefit from RSC; if a future surface (e.g., a public marketing site) is added, that surface lives somewhere other than `apps/web`.
- **TanStack Query is not pre-added.** If multi-component shared cache becomes load-bearing before it's been added, contributors hand-roll fetch/cache patterns in the interim. Mitigation: pre-document the "when to add TanStack Query" trigger in `packages/shared-types/README.md`.
- **Vite minor bumps must be security-reviewed.** Standard ADR-0001 doctrine; called out here because Vite's plugin surface (rollup transitive deps) is non-trivial.
- **CSRF double-submit is implementation discipline.** A future contributor adding a new mutation endpoint must remember to send `X-CSRF-Token`. Mitigation: the `openapi-fetch` wrapper in `packages/shared-types/src/client.ts` attaches the header automatically for all non-`GET` requests; no per-call burden. CI lint to verify no direct `fetch` calls bypass the wrapper is deferred to P1 (review-enforced at P0).
- **The `<CapabilityProvider>` cache can drift.** If `services/api` revokes a capability mid-session (rotate signing key per ADR-0046), the cache won't reflect it until the next mount. Mitigation: the next API call returns 401 and the single 401 chokepoint clears the cache and routes to `/login`. Documented as expected behavior.

### Held in reserve

- **Remix (in SPA mode) — or TanStack Start when GA — as the meta-framework reserve.** Adopt the day any one of these fires:
  - Route count exceeds ~30 across `apps/web` + `apps/admin` AND manual route-tree maintenance is friction in code review or implementation tickets.
  - Multi-step data prep on a single route becomes recurring (≥3 cases in one quarter) where framework loaders (`useLoaderData` / `loader` functions) would simplify it.
  - A surface genuinely needs SSR (rare for a post-login cockpit; the trigger would be e.g. printable / shareable evidence packets that warrant server-side rendering).
- **TanStack Query** — adopt the day multi-component shared cache, optimistic updates, or stale-while-revalidate semantics become load-bearing (rough threshold: ≥3 routes need it concurrently, or one route has 4+ components subscribing to overlapping data).
- **File-based routing migration (TanStack Router or Remix v7 framework mode)** — adopt with the meta-framework reserve trigger.
- **`apps/admin` second framework** — not held in reserve. Both apps share the stack.
- **Next.js** — explicitly NOT held in reserve. The Vercel-deploy-primitive footgun named in ADR-0042 applies in spades.
- **Svelte / Solid / Vue stacks** — not held in reserve. If a future surface justifies a non-React stack, propose a follow-up ADR; the default answer for new frontend surfaces is the framework chosen here.
- **mTLS / per-token cookie variants** — out of scope; tracked under ADR-0046's hardened-deploy reserve.

## Review triggers

Re-open this ADR if any of these become true:

- Route count exceeds ~30 across `apps/web` + `apps/admin` AND manual `<Route>` tree maintenance becomes friction → adopt the meta-framework reserve (**Remix in SPA mode** or **TanStack Start** if GA).
- Multi-step data prep on a single route becomes recurring (≥3 cases in one quarter) where framework loaders would simplify it → same meta-framework reserve.
- A surface genuinely needs SSR (e.g., printable / shareable evidence packets that warrant server-side rendering, or a public marketing surface added to `apps/web`) → meta-framework reserve, with explicit re-assessment of whether SSR daemon is in or out of the offline installer.
- Multi-component shared cache, optimistic updates, or stale-while-revalidate semantics become load-bearing on ≥3 routes concurrently → adopt **TanStack Query**.
- The cockpit's bundle size exceeds an agreed first-load SLO (e.g., > 1 MB gzipped) across two customer environments → re-evaluate split-strategy and consider non-React alternatives only if the bundle is dominated by React itself, which is unlikely.
- A Vite, React, React Router, Radix, Tailwind, `openapi-typescript`, `openapi-fetch`, `guacamole-common-js`, or `xterm` supply-chain incident materially affects trust posture → re-evaluate the affected dep.
- The PASETO v4 local token format is replaced (ADR-0046 review trigger) → re-evaluate the cookie-vs-Bearer storage choice in tandem.
- The capability-edge model itself is revised (`docs/security/agent-permission-model.md` edges change shape) → re-evaluate the `<CapabilityGate>` API surface.
- The same-origin deploy posture becomes operationally infeasible across two or more customer environments → revisit the `SameSite=Strict` cookie strategy (next candidate: `SameSite=Lax` + a wider CSRF defense, or split-origin with explicit CORS).
- The product adds a second non-Go runtime in production for unrelated reasons → revisit the "no Node runtime in production" call.

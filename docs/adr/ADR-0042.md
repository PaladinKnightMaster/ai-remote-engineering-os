# ADR-0042: Monorepo tooling — Go workspaces + pnpm workspaces, orchestrated by a top-level Taskfile

## Status
Accepted — 2026-05-16.

## Context

ADR-0041 established Go as the primary backend language, TypeScript as the frontend-only language (`apps/web`, with `apps/admin` scoped for later), and Python as a sanctioned AI sidecar in P1+. This repo must now pick a monorepo tooling strategy that:

1. Honors ADR-0001 — self-hosted / offline-first is non-negotiable. The chosen tooling must mirror cleanly into a restricted-network installer.
2. Holds the supply-chain surface as small as the repo shape allows. Every dependency a tool drags in is a thing the security review must vet.
3. Lets P0 ship. Tooling that consumes engineering days of yak-shaving before the first feature lands is rejected.
4. Handles the actual repo shape: `services/{api,session-broker,audit-service,policy-service,connector-service}` (Go), `apps/{web,admin}` (TypeScript), `packages/{shared-types,shared-schemas,config,ui}` (TypeScript shared by both apps), and — per ADR-0041 — an eventual Python sidecar under `services/` or a new top-level directory.
5. Does not foreclose on Turborepo / Nx / Bazel later if scale changes.

The decisive sub-question is the JS side. `packages/ui`, `packages/shared-types`, and `packages/config` are consumed by both `apps/web` and `apps/admin` per `docs/architecture/module-map.md`. Some JS workspace mechanism is required; the alternative (copy / symlink / one-off codegen-into-each-app) fights the audit and offline stories.

## Decision

- **Go side:** `go.work` workspace at the repo root spans every `services/*` Go module. Per-service `go.mod` files pin toolchain version.
- **TypeScript side:** `pnpm` workspaces at the repo root span `apps/*` and `packages/*`. `pnpm-workspace.yaml` enumerates them. `.npmrc` pins the registry and enables `package-import-method=hardlink` and `prefer-offline=true` for restricted-network compatibility.
- **Top-level orchestration:** a `Taskfile.yml` at the repo root (using `go-task/task`) exposes the canonical entry points: `task lint`, `task test`, `task build`, `task offline-bundle`. Each target dispatches into the appropriate per-language workflow. Make is an acceptable substitute on hosts where Taskfile is not available, but the canonical command set lives in `Taskfile.yml`.
- **No JS-side monorepo orchestrator (Turborepo, Nx) at P0.** Adopting one is a follow-up ADR triggered by the conditions in *Review triggers* below.
- **No Bazel.** See *Alternatives considered*.

The Python sidecar (P1+) plugs into this scheme as either a `uv`-managed project under `services/<name>/` invoked from Taskfile targets, or via a dedicated `pyproject.toml` workspace. Its tooling choice is deferred to the ADR that introduces the first sidecar.

## Alternatives considered

### A. Go workspaces alone — TS frontend has its own package.json, no top-level JS orchestration
Rejected.
- Pros: zero JS-side tooling overhead.
- Cons: `packages/ui`, `packages/shared-types`, `packages/config` cannot be cleanly shared between `apps/web` and `apps/admin` without npm hacks (file: deps, copy steps, or hoisting workarounds). The module map already mandates this sharing.
- Decisive: fails the actual repo shape on day one.

### B. Go workspaces + pnpm workspaces, top-level Taskfile/Makefile (no JS monorepo orchestrator)
**Adopted.** See *Decision*.

### C. Go workspaces + pnpm workspaces + Turborepo
Rejected for P0.
- Pros: task graph caching, parallelism control, well-known on JS side.
- Cons:
  - With two JS apps and small builds, no measurable win at P0; the cost is the time spent authoring `turbo.json` and gating CI on it.
  - Turborepo's *default* remote cache points at Vercel. In a restricted-network product this must be disabled — a release-guard footgun if a future contributor toggles it back on.
  - One more npm dependency tree to vet for the supply-chain review.
- Decisive: premature. Re-evaluate when one of the *Review triggers* fires.

### D. Go workspaces + pnpm workspaces + Nx
Rejected for P0.
- Pros: code generators, broader orchestration than Turborepo, strong dependency-graph awareness.
- Cons: heavier than Turborepo on every axis (binary size, learning curve, plugin surface). Adopting Nx for two JS apps is overkill by an order of magnitude.
- Decisive: even more premature than C.

### E. Bazel for the whole repo
Rejected for P0.
- Pros: hermetic toolchains, polyglot-native, the strongest *theoretical* offline-build story.
- Cons:
  - Vendoring `rules_go` + `rules_nodejs` + (eventual) `rules_python` for a restricted-network mirror is a multi-month effort with non-trivial maintenance overhead per Bazel upgrade.
  - Highest learning curve of any candidate. Drains P0 velocity.
  - Largest supply-chain surface of any candidate (Bazel itself plus every ruleset).
  - Bazel's wins compound at large repo size and team size, neither of which apply to this repo today.
- Decisive: P0 velocity + offline operational tax. Reserved for re-evaluation if the repo grows polyglot beyond Go + TS + one Python sidecar.

### F. Plain Make-based polyglot (per-service Makefiles, no language workspace tool)
Rejected.
- Pros: minimal supply-chain footprint.
- Cons: same failure mode as A on the JS side (no clean way to share `packages/ui`). Make also loses on cross-platform reliability for the CEO's Windows host; Taskfile is single-binary cross-platform.
- Decisive: doesn't solve the JS-side multi-package problem.

## Consequences

### Positive

- Smallest viable tooling kit that matches the existing repo shape. No tool present that isn't pulling its weight.
- Offline posture is straightforward: `go mod download` populates the module cache; `pnpm fetch` populates the content-addressed store; both can be tarballed into the offline installer. Taskfile is a single Go binary, mirror-friendly.
- Supply-chain surface stays small: Go modules + pnpm registry only. No Vercel cache, no Bazel ruleset graph, no Nx plugin ecosystem.
- CI is simple: one job runs `task lint && task test && task build`. Per-language matrix only if performance demands it.
- Future-proof for the P1+ Python sidecar — Taskfile orchestrates any toolchain.
- Compatible with the schema-first contract from ADR-0041 (OpenAPI + JSON schemas drive codegen on both sides).

### Negative

- `pnpm fetch` for offline mirroring requires a documented procedure in `docs/devops/offline-install-v3.md`. (Mitigated: this is a one-page playbook, not a new system.)
- No cross-language task graph caching. Full `task build` is sequential by default; rebuild times will eventually demand parallelism. (Mitigated: review triggers below.)
- Taskfile is one more tool installers must place on developer hosts. (Mitigated: single static Go binary; Make remains an acceptable fallback.)
- Contributors must learn `pnpm` if they only know `npm` / `yarn`. (Mitigated: surface in `CONTRIBUTING.md` once it exists; pnpm CLI is npm-compatible for the common verbs.)

### Held in reserve

- **Turborepo** — adopt the day frontend cold build exceeds 60s wall-clock or the day a third JS app is added.
- **Bazel** — adopt only if the repo grows past three production languages or the offline-install playbook becomes unmaintainable under the chosen tooling.
- **Nx** — not held in reserve. If task-graph caching becomes a need, Turborepo is the preferred path.

## Verification

This ADR is verified once the following hold:

1. Repo root contains `go.work`, `pnpm-workspace.yaml`, `.npmrc`, and `Taskfile.yml`.
2. `task lint`, `task test`, and `task build` succeed on a fresh clone with no network access after `task offline-bundle` has been run once on a connected host.
3. `pnpm install --offline` succeeds against a populated store on a restricted-network host.
4. `go build ./...` against `go.work` produces one static binary per `services/*` module.
5. CI runs the canonical `task` targets and reports per-target pass/fail.
6. No `turbo.json`, `nx.json`, `WORKSPACE`, `BUILD.bazel`, or `MODULE.bazel` files are present at the repo root.

## Review triggers

Re-open this ADR if any of these become true:

- Frontend cold build exceeds 60s wall-clock OR `apps/*` count grows to ≥ 3 — re-evaluate Turborepo.
- A second polyglot dimension lands beyond Go + TS + one Python sidecar (e.g., a Rust hardened module per ADR-0041's reserve clause) — re-evaluate Bazel.
- A supply-chain incident materially affects `pnpm`, `go-task`, or the Go toolchain.
- The offline-install playbook for `pnpm fetch` proves unreliable across two or more customer environments.

## Output contract (per kit specialist-output format)

- **Scope**: monorepo tooling for a Go-primary + TS-frontend repo with an eventual Python sidecar; consumed by ADR-0043..ADR-0047 and by every implementation ticket from T-002 onward.
- **Findings**: the JS-side multi-package shape (mandated by `module-map.md`) forces *some* JS workspace tool. Offline + supply-chain + P0 velocity together rule out Bazel, Turborepo, and Nx at P0. Go workspaces is uncontested on the Go side.
- **Evidence**: `docs/architecture/module-map.md` (`apps/*` + `packages/*` shape), `docs/devops/offline-install-v3.md` (offline mirror requirements), ADR-0001 (offline-first), ADR-0041 (language matrix), `docs/security/` (supply-chain surface posture).
- **Risks**: contributor unfamiliarity with `pnpm` (LOW); offline mirror procedure for `pnpm fetch` (LOW–MEDIUM, mitigated by a documented playbook); no cross-language task graph caching (LOW at P0, MEDIUM if `apps/*` grows).
- **Recommendation**: Go workspaces + pnpm workspaces + Taskfile. No JS-side orchestrator, no Bazel.
- **Confidence**: HIGH for the Go workspaces + pnpm workspaces baseline; MEDIUM-HIGH for Taskfile-over-Make; RESERVED for the "no Turborepo at P0" call (explicit review triggers documented).
- **Hand-off notes**: T-002 (Docker Compose) should land `go.work`, `pnpm-workspace.yaml`, `.npmrc`, and `Taskfile.yml` as part of the skeleton commit, with a `task offline-bundle` target stub that the offline-install playbook can flesh out.

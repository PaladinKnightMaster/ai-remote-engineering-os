# v0.4.0 — Release Criteria

Status: **Accepted — 2026-06-21** after the War Room opening scoping consult (CEO
sign-off). Theme and in/out scope are locked here; the **single** architecture ADR
it depends on (**ADR-0060**)
is **Proposed** and is ratified in the first authoring consult (T-045-era), where
its open questions settle. The F3 command-at-rest-encryption decision is settled
at its own ticket consult (T-051) as an extension of the already-Accepted
ADR-0059 — **no new ADR** (CEO decision, 2026-06-21). Acceptance of *this*
document fixes the release intent; it does not pre-ratify ADR-0060's internal
decisions.

Owner: War Room Commander (synthesis); Permission Model Reviewer (asymmetric key
architecture + dual-mode verifier + subject-pinning); Tech Lead (PASETO v4 public
primitives + codegen + audit); Remote Cockpit Architect (broker exec verifier
migration); Offline-Install Engineer (keypair provisioning + bundle delta).

Future changes to this document require a new ADR (criteria drift is a
load-bearing decision — same rule as v0.1.0 / v0.2.0 / v0.3.0).

This document defines what shipping **v0.4.0 — "Hardened Agent Foundation"**
means. Every criterion is *pass* (must be true), *block* (presence stops
release), or *deferred-to-v0.5.0+* (explicitly out of scope, with the trigger
that promotes it back). The criteria are the exit gate for every v0.4.0 ticket: a
ticket is "done" when it closes one or more criteria here and breaks none.

---

## 1. Scope of v0.4.0

v0.4.0 is a **security-hardening release**, not a new product capability. v0.3.0
made an agent's tool call a first-class governed primitive — but it did so by
giving the first **agent-facing** service, `services/mcp-gateway`, the symmetric
**cluster** key (`AIREOS_PASETO_KEY`). Under PASETO v4 *local*, mint and verify
are the **same** capability, so the gateway can forge a token for *any* edge and
*any* audience. RCE on the gateway therefore equals total cluster compromise —
including minting a `service-service`/`connector-service` token to **lease and
decrypt any target's credentials**. This is the P1 trigger ADR-0046 named
("enterprise federation / key separation when the blast radius justifies it"); the
gateway going agent-facing at v0.3.0 fired it.

v0.4.0 **removes the symmetric cluster key from the gateway entirely** and
isolates its blast radius with **per-workload asymmetric keys** (PASETO v4
*public*, Ed25519) on every gateway-touching edge. Symmetric keys offer **no
partial isolation** — any key that can mint a valid token to a peer *is* the
cluster key — so the change is necessarily all-or-nothing **for the gateway**: its
inbound verification moves to public keys and its outbound minting moves to its
**own** private key. After v0.4.0 the gateway holds only verification material for
its callers plus its own narrow signing identity; an attacker who takes it cannot
mint a foreign-edge token.

The migration is deliberately **bounded to the gateway-touching edges**. The
operator cookie plane (operator → api) and the service planes that do not involve
the gateway (broker → connector lease, api → policy, api → broker, the other
outbox relays) **stay PASETO v4 local** — they are not in the gateway's blast
radius and converting them is out of scope.

Concretely, on top of the v0.3.0 spine, v0.4.0 delivers:

- **Asymmetric agent + service identity for the gateway plane** — api signs
  `agent-tool` tokens (and its gateway-bound `service-service` tokens) with an
  asymmetric **private** key; the gateway verifies them with api's **public** key.
  The gateway signs its outbound `service-service` calls (→ policy, broker, audit)
  with its **own** private key; those peers verify with the gateway's **public**
  key. The gateway boots with **no** `AIREOS_PASETO_KEY`.
- **A dual-mode verifier** — peers that the gateway calls and that *also* have
  existing symmetric callers (policy `Decide`, audit ingest) accept **either** a
  v4-local token under the cluster key **or** a registered workload's v4-public
  token, dispatched on the token type.
- **Command at-rest encryption (F3)** — the `invocations.command` column (added at
  v0.3.0 for informed approval, ADR-0059) is encrypted at rest under a
  **gateway-local** key, separate from the connector's resource-secret key;
  operator-only decrypt-on-read is preserved.
- **Service-subject pinning (R5-ext)** — the broker exec verifier and the
  connector lease verifier pin the caller's `subject` (only the gateway calls
  broker exec; only the broker leases), extending the T-041h defense-in-depth that
  pinned the gateway's internal operator plane to `subject == "api"`.

**Out of scope** (→ v0.5.0+, see §14): converting the non-gateway planes to
asymmetric; a **full per-workload key registry** for many agent identities
(v0.4.0 keeps the single bootstrap agent identity from v0.3.0 — the asymmetric
*shape* is built to grow, the registry is not); key **rotation tooling / JWKS**
(short agent TTL remains the revocation mechanism; keypair rotation is
redeploy-and-redistribute); Workstreams; Memory; TR-2 external-MCP proxying +
untrusted-server sandbox; full per-edge rate-limiting + quotas; SSH connection
pooling; the `resources.connection_secret` column drop.

The wedge is **the gateway running with no symmetric cluster key, driving the full
v0.3.0 governed-exec chain, and provably unable to mint a foreign-edge token**
(WD-4). Everything else exists to make that true and verifiable.

## 2. WD-4 — the single load-bearing wedge (the demo)

**WD-4.** A fresh installer-driven boot of the offline bundle produces a running
stack in which `services/mcp-gateway` holds **no** `AIREOS_PASETO_KEY` (only its
asymmetric private key + api's public key), and that stack passes the following,
end-to-end, against a real (not mocked) target resource:

1. **Agent identity (asymmetric).** An operator provisions an agent and api mints
   a scoped `agent-tool` token **signed with api's asymmetric private key**
   (5-min TTL, audience `mcp-gateway`). The gateway verifies it with api's
   **public** key. A token signed by anything other than api's private key is
   refused.
2. **Governed invocation (unchanged chain).** The agent invokes `remote.exec`
   against a `requires_approval`-flagged resource. The gateway opens an invocation
   and calls policy `Decide` — now authenticating to policy with a token **signed
   by the gateway's own private key** (policy verifies it in dual mode). The
   invocation parks; `<ApprovalPrompt>` surfaces to the operator.
3. **Approval + egress (unchanged chain).** Approve → the gateway leases the
   credential (broker → connector) and runs the command via the broker exec path
   (broker verifies the gateway's **asymmetric** token + pins `subject ==
   "mcp-gateway"`). Deny → blocked, typed error. The command was **encrypted at
   rest** while parked.
4. **Blast-radius proof (the new negative test).** The gateway, holding no
   symmetric cluster key, **cannot** produce a token that any peer accepts as a
   foreign edge: it cannot mint an `agent-tool`, `human-agent`, or
   `connector-service` token. The test asserts the gateway process has no path to
   a v4-local token and that a token bearing the gateway's identity is rejected by
   connector-service (wrong subject/edge).
5. **Replayable chain.** The full WD-3 chain (`tool.invoked` →
   `policy.decision:requires_approval` → `approval.granted` → `credential.leased`
   → broker exec egress → `tool.result`) remains hash-intact and replayable via
   `audit-service verify`, with the two-namespace anchor design (ADR-0057/0059)
   unchanged. The denied leg is unchanged.

**This single demo is the release gate.** It is built as an extension of the
`tests/e2e` live harness (the WD-3 agent-driven exec leg now runs with an
asymmetric-keyed gateway, plus the negative blast-radius assertions) and re-run on
the installer-produced stack (`task wd1`).

## 3. Capability-edge security (must-pass)

Every boundary stays gated by `packages/go/middleware` `RequireCapability` over
PASETO v4 capability tokens (ADR-0046). v0.4.0 changes the **key type** on the
gateway-touching edges; the edge semantics are unchanged.

| Edge | Mint key (issuer) | Verify key (peer) | Token type |
|---|---|---|---|
| `agent-tool` (agent → gateway) | api asymmetric private | gateway holds api public | **v4 public** |
| `service-service` (api → gateway, internal resolve/list) | api asymmetric private | gateway holds api public | **v4 public** |
| `service-service` (gateway → policy `Decide`) | gateway asymmetric private | policy holds gateway public (dual-mode) | **v4 public** |
| `service-service` (gateway → broker exec) | gateway asymmetric private | broker `ExecVerifier` holds gateway public | **v4 public** |
| `service-service` (gateway → audit ingest) | gateway asymmetric private | audit holds gateway public (dual-mode) | **v4 public** |
| `service-service` (broker → connector lease) | broker symmetric (unchanged) | connector symmetric (unchanged) | v4 local |
| `human-agent` / operator cookie (operator → api) | api symmetric (unchanged) | api symmetric (unchanged) | v4 local |

- **SEC-20 (block) — no cluster key on the agent surface.** `services/mcp-gateway`
  boots and serves with `AIREOS_PASETO_KEY` **unset**. Its process holds only its
  own asymmetric private key and the public keys of its callers. A boot path that
  still reads the symmetric cluster key into the gateway is a release blocker.
- **SEC-21 (block) — bounded blast radius.** A gateway compromise cannot mint a
  token any peer accepts for an edge other than the gateway's own
  `service-service` calls. Specifically it cannot mint `agent-tool`,
  `human-agent`, or a `connector-service`-audience lease token. Proven by the WD-4
  negative test (§2.4).
- **SEC-22 (block) — verifier integrity.** The dual-mode verifier accepts a
  v4-public token **only** from a registered issuer/key and **only** for the
  expected audience + edge; an unregistered issuer, a wrong-key signature, or a
  v4-local token presented where only the gateway's asymmetric identity is trusted
  (broker exec) is refused. No verifier silently widens trust.
- **SEC-17 (block, carried) — no decrypt path on the gateway.** The gateway still
  holds no resource-secret key; connector-service remains the sole credential
  custodian (the SEC-13 grep gate still names connector-service only).
- **SEC-18 (block, carried) — exec parity.** The broker exec path keeps host-key
  pinning, the capability gate, and connector-lease custody; now additionally
  subject-pinned (R5-ext).

## 4. Asymmetric key architecture & provisioning (must-pass)

- **KEY-1 (block).** `packages/go/auth` gains PASETO **v4 public** (Ed25519)
  primitives alongside the existing v4-local types: asymmetric keypair generation,
  hex import/export, an asymmetric `Signer` (private key) and `Verifier` (public
  key). The depguard rule still confines the PASETO import to `packages/go/auth`.
- **KEY-2 (block).** A **dual-mode verifier**, in `packages/go/auth` (the package
  that owns the PASETO import per the depguard rule), dispatches on the PASETO
  token type (`v4.local.*` vs `v4.public.*`): local → the cluster symmetric key;
  public → a public key selected by issuer/workload from a small registry. It
  enforces audience + edge identically to the symmetric verifier and returns the
  same typed `Capability`.
- **KEY-3 (block).** Exactly **two** new keypairs are provisioned: a **single api
  agent-plane** keypair — which signs **both** the `agent-tool` token and api's
  gateway-bound `service-service` token, so the gateway holds **one** api public
  key (CEO decision, 2026-06-21) — (private → api, public → gateway) and a
  **gateway** keypair (private → gateway, public → policy, broker, audit). They are
  generated at install time and distributed via per-service env files; private
  keys never leave their owning service's env. The cluster symmetric key continues
  to exist for the non-gateway planes.
- **KEY-4 (pass).** Rotation is **redeploy-and-redistribute** (regenerate the
  keypair, push the new public key to verifiers, restart). No JWKS endpoint, no
  online rotation, no key registry beyond the two pinned keypairs at v0.4.0. The
  5-min agent TTL remains the short-lived-token revocation mechanism.

## 5. Command at-rest encryption — F3 (must-pass)

- **ENC-1 (block).** The `invocations.command` column is stored **encrypted at
  rest** (pgcrypto), decrypted only on the operator-only read path that already
  shows the command in `<ApprovalPrompt>` (ADR-0059). The command is **never** on
  the agent plane and **never** logged — unchanged from v0.3.0.
- **ENC-2 (block).** The encryption key is **gateway-local**
  (`AIREOS_GATEWAY_COMMAND_KEY` or equivalent), **separate** from the connector's
  `AIREOS_RESOURCE_SECRET_KEY`. The gateway gains an encrypt/decrypt path for its
  *own* command column only; this does **not** make the gateway a resource-secret
  custodian (SEC-17 holds — the grep gate still excludes the gateway from the
  resource-secret key).
- **ENC-3 (pass).** Retention is unchanged: the reaper (ADR-0059) still finalizes
  parked invocations past TTL, bounding command retention to the approval window;
  encryption removes the plaintext-at-rest exposure for the retained terminal rows.
  Persisted-command GC/purge beyond the reaper stays deferred.

F3 is an extension of the Accepted ADR-0059 (which established command persistence
+ operator-only read) and is settled at the **T-051 ticket consult** — **no new
ADR** (CEO decision, 2026-06-21).

## 6. Service-subject pinning — R5-ext (must-pass)

- **PIN-1 (block).** The broker exec verifier (`ExecVerifier`, audience
  `session-broker`) pins `subject == "mcp-gateway"` — the gateway is the only
  legitimate caller of `/v1/exec`. Combined with the asymmetric token, an attacker
  cannot reach broker exec with any other identity.
- **PIN-2 (block).** The connector lease verifier pins `subject ==
  "session-broker"` — the broker is the only legitimate lease caller. Extends the
  defense-in-depth from T-041h (gateway internal plane pinned to `subject ==
  "api"`) to the credential-custody boundary.
- **PIN-3 (pass).** Subject pins are additive over the existing audience + edge
  checks (not a replacement); no edge semantics change.

R5-ext is a defense-in-depth tightening consistent with the existing audience
model and requires **no new ADR** (it is recorded here and in the ticket).

## 7. Audit (must-pass)

- **AUD-12 (pass).** The full WD-3/WD-4 chain remains hash-intact and replayable
  via `audit-service verify`; the event vocabulary, actors, and the two-namespace
  anchor design (gateway/broker `invocation:<id>`, policy/connector
  `session:<id>`) are **unchanged** — v0.4.0 changes how tokens are signed, not
  what is audited.
- **AUD-13 (pass).** The gateway's audit ingest continues via its transactional
  outbox (ADR-0045); the relay now authenticates to audit-service with the
  gateway's **asymmetric** token (audit verifies in dual mode). No event-shape
  change.

---

## 8. Frontend (must-pass)

- **FE-13 (pass).** No new operator surface is required. The existing
  `/invocations` approval surface and `<ApprovalPrompt>` are unchanged; the
  operator still reads the decrypted command (ENC-1) through the same api proxy.
  Any incidental change to `apps/web`/`packages/ui` rendering still carries the
  DoD browser-rendered-evidence requirement, but v0.4.0 is expected to touch no
  rendering output.

---

## 9. Offline install & operability (must-pass)

- **OI-11 (block).** `install.sh` generates the two new keypairs (KEY-3) and
  writes the private keys to the owning service's env file and the public keys to
  the verifying services' env files; it **removes** `AIREOS_PASETO_KEY` from the
  gateway's env (SEC-20). A fresh installer-driven boot brings the gateway and all
  peers `active` with the new key wiring, the WD-4 demo passes on the installed
  stack (`task wd1`), and `task offline-bundle`'s size gate still holds. Idempotent
  re-run preserves existing keys; a v0.3.0-layout upgrade relocates/rotates keys
  deterministically. No SaaS runtime dependency (doctrine gate holds).

---

## 10. Performance & resource safety (must-pass, carried)

- **PERF-5 (pass).** Asymmetric verification adds Ed25519 signature checks on the
  gateway-touching edges; the per-invocation cost is bounded and measured to be
  negligible against the existing SSH-dial + approval latency. No new unbounded
  work. The v0.3.0 floors (bounded exec PERF-1, idempotency PERF-2, per-agent
  concurrency PERF-3, fresh-dial PERF-4) are unchanged.
- SSH connection pooling and full per-edge rate-limiting remain **deferred**
  (§14) — v0.4.0 is a key-architecture release, not a perf release.

## 12. Verification & gates (VER)

- **VER-11 (block).** `task lint` / `task test` / `task build` / `task licenses` /
  `task sec13-gate` stay green across the changed surfaces (`packages/go/auth`,
  api, gateway, policy, broker, connector, audit). The SEC-13 grep gate's
  allowlist still names connector-service only (the gateway's new command-encrypt
  key is a *different* key and must not trip the resource-secret gate — the gate
  pattern is extended to also assert the gateway never reads
  `AIREOS_RESOURCE_SECRET_KEY`).
- **VER-12 (block).** Codegen drift (VER-2) stays zero. The asymmetric migration
  is **not** an OpenAPI surface change (it is transport/auth-internal); no fragment
  edit is expected. If any operator-facing route or shared type changes, it
  regenerates byte-deterministically.
- **VER-13 (block).** `task release-check` stays green end-to-end; its `e2e` leg
  runs WD-4 (asymmetric-keyed gateway + the blast-radius negative test) and its
  `smoke` leg is unchanged (no UI change expected).
- **G1.** WD-4 is the live cross-boundary proof — a real agent → asymmetric mint →
  gateway (no symmetric key) → policy → connector → broker → sshd → audit, plus the
  negative blast-radius assertion, no mocked boundary.
- **G2.** ADR-0060 is **new** (Proposed) — no Accepted ADR is edited (F3 extends
  ADR-0059 at its ticket consult, not by editing it). This document, once Accepted,
  is itself change-controlled.

## 13. ADR dependencies (Proposed — ratified in the first authoring consult)

- **ADR-0060 — Asymmetric per-workload keys on the agent-facing planes (promotes
  the ADR-0046 P1 trigger).** The **sole** new ADR for v0.4.0. Settles: PASETO
  **v4 public** (Ed25519) on the gateway-touching edges; the exact edge set that
  migrates and the planes that stay symmetric; the **dual-mode verifier** in
  `packages/go/auth` (dispatch on token type, public-key registry by issuer); the
  two new keypairs — a **single** api agent-plane keypair (signs both the
  `agent-tool` and the gateway-bound `service-service` token) and the gateway
  keypair — and their distribution; the gateway holding **no** symmetric cluster
  key; rotation scope (redeploy-and-redistribute, no JWKS); the deliberate decision
  to **not** build a full per-workload registry at v0.4.0 (the shape is extensible
  for Workstreams).

  *Settled in this consult (carried into ADR-0060 ratification at T-045):* one api
  agent-plane keypair (not two); the dual-mode verifier in `packages/go/auth`.

- **F3 command at-rest encryption — no new ADR.** Extends the Accepted ADR-0059;
  the gateway-local command-encryption key (separate from the connector
  resource-secret key), the pgcrypto pattern, and operator-only decrypt-on-read are
  decided at the **T-051 ticket consult** (CEO decision, 2026-06-21).

## 14. Deferred → v0.5.0+ (with promotion triggers)

- **Asymmetric conversion of the non-gateway planes** (operator cookie, broker →
  connector, api → policy/broker) — **trigger:** a second agent-facing surface, or
  a decision to retire the cluster symmetric key entirely.
- **Full per-workload key registry / many agent identities + key rotation tooling
  / JWKS** — **trigger:** Workstreams (many concurrent workloads) or enterprise
  federation (the ADR-0046 Zitadel reserve).
- **Workstreams; Memory** — the next P1 *product* modules, now landing on an
  isolated-key foundation (consume this gateway).
- **TR-2** external MCP-server proxying + untrusted-server sandbox — **trigger:**
  a scoped external-server use case with its own ADR.
- **Full per-edge rate-limiting + quotas; SSH connection pooling** — **trigger:**
  multi-agent / sustained load.
- Persisted-command GC/purge beyond the reaper; T-023 (`auth.service-token.mint`
  audit); mobile approval; durability residuals (WS-drop reconnect, broker
  heartbeat); `resources.connection_secret` column drop.

## 15. Ticket ladder (indicative; each JIT-authored with its own consult)

Strictly sequential where a rung consumes the prior's wire contract; diff budget
≤12 files / ≤500 LoC per ticket unless explicitly approved.

- **T-045** — `packages/go/auth` PASETO v4 public primitives: asymmetric keypair
  gen + hex import/export + asymmetric `Signer`/`Verifier` (KEY-1; ADR-0060).
- **T-046** — dual-mode verifier: dispatch on `v4.local`/`v4.public`, public-key
  registry by issuer, same `Capability` output + audience/edge enforcement (KEY-2;
  ADR-0060).
- **T-047** — api mints `agent-tool` + gateway-bound `service-service` tokens with
  the api agent-plane asymmetric private key; gateway verifies inbound with api's
  public key (drops symmetric inbound verify) (KEY-3, SEC-22).
- **T-048** — gateway outbound + key removal: gateway signs → policy/broker/audit
  with its own private key; gateway boots with **no** `AIREOS_PASETO_KEY`
  (SEC-20).
- **T-049** — dual-mode verify on policy `Decide` + audit ingest (accept cluster
  symmetric OR gateway asymmetric); broker `ExecVerifier` → gateway asymmetric +
  `subject == "mcp-gateway"` pin (SEC-22, PIN-1).
- **T-050** — connector lease verifier `subject == "session-broker"` pin (PIN-2)
  + finalize R5-ext.
- **T-051** — F3 command at-rest encryption: gateway pgcrypto, gateway-local key,
  operator-only decrypt-on-read (ENC-1/2/3; extends ADR-0059, decided at this
  ticket's consult — no new ADR).
- **T-052** — WD-4 live e2e capstone: asymmetric-keyed gateway drives the full
  chain + the blast-radius negative test; chain intact (G1, SEC-21).
- **T-053** — release closure: VER legs, **offline keypair provisioning +
  symmetric-key removal from the gateway (OI-11)**, **DOC-12**, ADR ratification,
  `docs/releases/v0.4.0/` artifacts.

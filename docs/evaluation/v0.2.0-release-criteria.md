# v0.2.0 — Release Criteria

Status: **Accepted — 2026-06-01** after the war-room scoping consult (CEO
sign-off). Theme and in/out scope are locked; the two architecture ADRs it
depends on (ADR-0053, ADR-0054) are **Proposed** and are ratified in the T-028
authoring consult (where their open questions settle). Acceptance of *this
document* fixes the release intent; it does not pre-ratify the ADRs' internal
decisions.

Owner: War Room Commander (synthesis); Permission Model Reviewer (security
gates + approval); Remote Cockpit Architect (connector re-point); Offline-Install
Engineer (bundle delta); Tech Lead (audit + codegen).

Future changes to this document require a new ADR (criteria drift is a
load-bearing decision — same rule as v0.1.0).

This document defines what shipping **v0.2.0 — "Governed Egress Foundation"**
means. Every criterion is *pass* (must be true), *block* (presence stops
release), or *deferred-to-v0.3.0* (explicitly out of scope, with the trigger
that promotes it back). The criteria are the exit gate for every v0.2.0 ticket:
a ticket is "done" when it closes one or more criteria here and breaks none.

---

## 1. Scope of v0.2.0

v0.2.0 is the **P1 spine** release: it is to the P1 "defensibility" ladder what
v0.1.0 was to P0 — a deliberately thin foundation every later module consumes.
It builds the two **already-scaffolded P0 capability-edge services**
(`services/connector-service` + `services/policy-service`, both `.gitkeep`-only
today, planned since ADR-0041/0043/0045) that the doctrine gate — *"No AI
autonomy before audit + policy + approval primitives exist"* — requires before
any agent surface (MCP Gateway, Workstreams, Memory) can ship.

Concretely, on top of the proven v0.1.0 SSH cockpit wedge, v0.2.0 delivers:

- **An egress + credential chokepoint** — `services/connector-service` becomes
  the sole custody/decrypt authority for target credentials (closing the SEC-12
  pgcrypto debt), and the existing SSH session leases its credential through it.
- **A human-approval primitive** — `services/policy-service` returns
  allow/deny/`requires_approval` for an action, and `<ApprovalPrompt>` (the last
  deferred v0.1.0 §FE-5 component) brokers the operator's decision; every
  decision is audit-chained.
- **Operational durability riders** — WS-drop reconnect (fresh shell, conforming
  to ADR-0049) and a session reaper (closing the orphan-close audit gap ADR-0049
  documented).

**Out of scope** (→ v0.3.0, see §10): the Typed MCP Gateway tool catalog,
Workstreams, Memory, T-023 (`auth.service-token.mint` audit), server-side
audit-timeline filtering, GUI/Guacamole adapters, mobile approval delivery.

The first agent-facing module (MCP Gateway) becomes the **first consumer** of
this spine — it is not built here.

## 2. Wedge demo (the single load-bearing criterion)

**WD-2.** A fresh installer-driven boot of the offline bundle produces a running
stack that passes the following scripted demo, end-to-end, against a real (not
mocked) target resource:

1. **No api decrypt path.** `services/api` holds neither
   `AIREOS_RESOURCE_SECRET_KEY` nor any `pgp_sym_decrypt` call —
   `services/connector-service` is the sole credential authority (grep-proven +
   runtime-proven). SEC-12 is **closed**, not interim debt.
2. **Credential via connector-service.** The operator starts an SSH session; the
   broker **leases the target credential from connector-service** (ADR-0045 sync
   RPC, `edge: service-service`) — it never reads the encrypted column. xterm.js
   renders the PTY exactly as v0.1.0.
3. **Approval round-trip.** An action flagged `requires_approval` (e.g. a session
   start / credential lease to a flagged resource) surfaces `<ApprovalPrompt>` to
   the operator. **Approve** → the action proceeds; **deny** → the action is
   blocked. Both outcomes are audit-chained.
4. **Replayable chain.** The whole path is hash-chained and replayable via
   `audit-service verify`; the chain contains the policy decision + approval
   outcome + the connector egress decision in canonical order.
5. **Durability (riders).** A dropped WebSocket reconnects with a **fresh shell**
   (ADR-0049); a session orphaned by an api-only `end` is **reaped** and emits its
   `session.close` (closing the ADR-0049-documented orphan-close gap).

**This single demo is the release gate.** Every other criterion exists to make
WD-2 trustworthy, repeatable, and safe. WD-2 supersedes WD-1 as the v0.2.0 live
demo and is built as an extension of the `tests/e2e` + `task wd1` harness
(§9 / G1).

## 3. Capability-edge security (must-pass)

Carries forward all of v0.1.0 §3 (SEC-1…SEC-11 unchanged) and adds:

- **SEC-12 — now CLOSED (was interim debt).** Target credentials are custodied by
  `services/connector-service`. The `resources.connection_secret` decrypt path is
  removed from `services/api` and from the `services/session-broker` mirror.
- **SEC-13. (BLOCKS RELEASE)** `services/connector-service` is the **sole**
  credential-decrypt authority. Enforced two ways: (a) a lint/grep gate — no
  `pgp_sym_decrypt` and no `AIREOS_RESOURCE_SECRET_KEY` read outside
  connector-service; (b) runtime — `services/api` cannot fetch a target secret.
- **SEC-14.** Every policy decision and human approve/deny emits a structured
  chained-hash audit event (`policy.decision`, `approval.granted` /
  `approval.denied`) via the ADR-0045 outbox, evidence as `sha256:<…>` (ADR-0049
  content model). A denied action is blocked **and** chained.
- **SEC-15.** The `api/broker → connector-service` credential lease and the
  enforcing-service → policy-service decision call are gated by
  `mw.RequireCapability` with `edge: service-service` (ADR-0046), identical to all
  S2S traffic. Bypass attempts return 401/403 deterministically.

## 4. Audit-chain integrity (must-pass)

Carries forward v0.1.0 §4 (AUD-1…AUD-6) and adds:

- **AUD-7.** No egress decision and no approval decision is unaudited: every
  connector-service egress decision and every policy-service decision crosses the
  outbox + sync-HTTP append-only ingest path into `audit-service` and chains in
  canonical order (the SEC-14/SEC-13 cross-link — SEC asserts the trigger, AUD
  asserts chain integrity of the record).
- **AUD-8.** `audit-service verify` re-walks the chain including the new
  `policy.decision` / `approval.*` / connector egress events and reports a single
  `OK` or the first integrity-failing event (extends AUD-5 for WD-2.4).

## 5. Frontend cockpit (must-pass)

- **FE-8. (§FE-5 closure)** `<ApprovalPrompt>` lands in `packages/ui` — the last
  of the three v0.1.0-deferred components (`<TerminalView>` shipped at v0.1.0;
  `<RemoteSessionView>` stays deferred with guacd). Capability-gated; consumes the
  typed client; a11y baseline per v0.1.0 §FE-7 (labeled controls, `role="alert"`
  error regions, keyboard-reachable).
- **FE-9.** The reconnect rider is operator-visible: a dropped session reconnects
  with a fresh shell and a clear notice (ADR-0049); no silent data loss, no
  infinite-reconnect loop.
- **FE-10.** Bundle SLO (v0.1.0 FE-2) re-verified: `<ApprovalPrompt>` adds no new
  heavy dep; first-load JS stays ≤ 600 KB gz (hard ceiling 1 MB gz).

## 6. Offline install (must-pass — release vehicle)

- **OI-6.** `task offline-bundle` gains the `services/connector-service` and
  `services/policy-service` static binaries; `install.sh` provisions them
  (including connector-service's custody of `AIREOS_RESOURCE_SECRET_KEY`, which
  **moves out of api's env**) and runs their migrations alongside the existing
  three. Idempotent (carries OI-2).
- **OI-7.** Bundle size budget re-verified against v0.1.0 OI-4 (≤ 500 MB
  uncompressed / ≤ 150 MB gzipped). Two new static Go binaries, no new heavy
  runtime dep — expected to stay comfortably under cap; the number is re-measured,
  not assumed.
- **OI-8.** WD-2 passes against the installer-produced stack with no manual steps
  after the documented postgres prerequisite (the OI-3 model from ADR-0051).
- **OI-9.** `SHA256_MANIFEST.txt` covers the new binaries and verifies via
  `sha256sum -c` (carries OI-5).
- **Upgrade note.** The v0.1.0 → v0.2.0 **offline upgrade path** (including the
  credential migration OQ-E) is in scope to *define* (release notes + a documented
  procedure); a fully automated in-place upgrade tool may itself defer — settled in
  the T-028 consult.

## 9. Verification + the two consult gates (must-pass)

- **VER-7 (= CI gate).** Every gate this document calls "must-pass" runs with a
  passing status in CI (the v0.1.0 VER-1/VER-2 command set + VER-5/VER-6). A
  failing run blocks release by definition.
- **G1 — end-to-end verification lens (MANDATORY before any sign-off).** WD-2
  spans `apps/web ↔ services/api ↔ services/connector-service ↔
  services/policy-service ↔ services/session-broker ↔ services/audit-service`
  (≫ 2 services). The **named live cross-boundary test** is the WD-2 extension of
  the `tests/e2e` + `task wd1` harness: real connector-service credential lease on
  the wire, real policy decision + approval round-trip, real audit chain — **no
  mocked boundary**. Per the v0.1.0 lesson, **rebuild the offline bundle from HEAD
  before any WD-2 verification run** (`dist/` is a gitignored stale artifact).
- **G2 — ADR-divergence gate.** ADR-0053 conforms to ADR-0048 §7 + ADR-0045
  (promotes a reserve; no divergence). ADR-0054 conforms to ADR-0041/0043 +
  ADR-0046/0045/0049 (builds scaffolding; no divergence). Reconnect conforms to
  ADR-0049 and the reaper sits under ADR-0048/0049 — **ticket-only, no new ADR**.
  Any option surfaced during a slice consult that contradicts an Accepted ADR is
  flagged at decision time and resolved by conform-or-new-ADR.

### 10a. Accepted residuals — governed-egress (T-030, consequences of ADR-0053)

These are *consequences of the Accepted ADR-0053 custody-centralization decision*,
not new decisions (so no new ADR — recorded here as named, phase-owned deferrals;
surfaced by the T-030a pre-T-030b review). v0.2.0 ships **with** these limitations:

| Residual | Why accepted at v0.2.0 | Defer target / trigger |
|---|---|---|
| **`resources.connection_secret` column not dropped** | T-030 closes SEC-13 by removing the decrypt *reads* + the key (leftover ciphertext is inert without the key, which only connector holds); proper expand-migrate-contract keeps the backfill upgrade-source intact | **v0.3.0** contract migration |
| **connector→broker lease hop carries plaintext, no TLS** | ADR-0046 defers mTLS past P0; ADR-0053 honest scope already states the broker receives plaintext to dial SSH (single-host deploy ≈ the old shared-DB read exposure) | **P2 / first multi-host deploy** — TLS the internal hop |
| **connector-service is a single point of failure on the session-open critical path** | Centralized custody = centralized dependency; single instance is acceptable for the P0/P1 self-hosted, low-concurrency threat model; behaviour is fail-closed (no session without governed egress) | **P1+** — connector HA / horizontal scale |

## 11. Open questions (must be answered before the dependent ticket)

Each is a war-room consult before the ticket that depends on it; ADR-0053 /
ADR-0054 carry the detailed text.

- **OQ-A.** connector-service store: own DB + migrations (stateful producer) vs a
  table in the shared cockpit DB. (ADR-0053)
- **OQ-B.** Credential-lease transport: in-process vs sync HTTP RPC; broker leases
  directly from connector-service vs via `services/api`. (ADR-0053)
- **OQ-C.** Approval shape for the WD-2 action: synchronous block-and-wait vs
  async queue; which concrete action triggers `requires_approval`. (ADR-0054)
- **OQ-D.** Approval-request persistence + un-actioned-approval timeout/expiry.
  (ADR-0054)
- **OQ-E.** Existing-credential migration: data-migrate the current
  `resources.connection_secret` rows into connector custody vs greenfield
  re-provision. (ADR-0053; also gates the OI upgrade note in §6.)
- **OQ-F.** Decision-point transport + which service enforces (api control-plane
  vs connector-service at the egress). (ADR-0054)

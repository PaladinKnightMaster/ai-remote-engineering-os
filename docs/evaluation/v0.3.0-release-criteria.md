# v0.3.0 — Release Criteria

Status: **Accepted — 2026-06-14** after the War Room scoping consult (CEO
sign-off). Theme and in/out scope are locked here; the architecture ADRs it
depends on (**ADR-0056**, **ADR-0057**, and **ADR-0058** if the broker-exec
contract warrants its own) are **Proposed** and are ratified in the first
authoring consult (T-035-era), where their open questions settle. Acceptance of
*this* document fixes the release intent; it does not pre-ratify the ADRs'
internal decisions.

Owner: War Room Commander (synthesis); Permission Model Reviewer (agent identity
+ per-tool policy + approval generalization); Remote Cockpit Architect (broker
exec egress + connector reuse); Tech Lead (gateway protocol surface + audit +
codegen); Offline-Install Engineer (bundle delta for the new service).

Future changes to this document require a new ADR (criteria drift is a
load-bearing decision — same rule as v0.1.0 / v0.2.0).

This document defines what shipping **v0.3.0 — "Typed MCP Gateway"** means. Every
criterion is *pass* (must be true), *block* (presence stops release), or
*deferred-to-v0.4.0* (explicitly out of scope, with the trigger that promotes it
back). The criteria are the exit gate for every v0.3.0 ticket: a ticket is "done"
when it closes one or more criteria here and breaks none.

---

## 1. Scope of v0.3.0

v0.3.0 is the **first agent surface**: it makes an *agent's tool call* a
first-class governed primitive that flows through the v0.2.0 spine (policy
decision → human approval → connector credential custody → audited egress). It is
to the P1 "defensibility" ladder what the cockpit was to P0 — the thin foundation
the rest of the agent layer (full tool catalog, Workstreams, Memory) consumes.

It stands up a **net-new** `services/mcp-gateway` (unlike v0.2.0, which activated
the already-scaffolded connector/policy services) and proves the doctrine-gated
claim — *"no AI autonomy before audit + policy + approval primitives exist"* — is
now satisfiable: an agent can act, but only through the spine.

Concretely, on top of the v0.2.0 governed-egress spine, v0.3.0 delivers:

- **An MCP-server agent surface** — `services/mcp-gateway` exposes a typed
  tool-catalog over the Model Context Protocol; agents authenticate with scoped,
  short-lived **`agent-tool`** capability tokens. The gateway is **MCP-compatible,
  not MCP-trusting**: at v0.3.0 it exposes only **internal-facade** tools whose
  egress we own — it does not proxy or trust any external/untrusted MCP server.
- **Agent identity & token lifecycle** — operator-gated provisioning + a minting
  path for scoped `agent-tool` tokens (5-min TTL, ADR-0046), closing the gap that
  agents have no authentication today.
- **Invocation-anchored governance** — the gateway models each tool call as an
  **invocation** with its own id; policy is consulted and `<ApprovalPrompt>` gates
  the **invocation** (not a session), generalizing the v0.2.0 approval primitive.
- **A governed egress tool** — one typed tool, `remote.exec(resourceId, command)`,
  whose egress reuses connector credential custody and runs as a **non-interactive
  command via a new minimal broker exec path** (the broker stays the sole SSH
  egress engine), with the command + result audit-chained.

**Out of scope** (→ v0.4.0, see §14): the full tool catalog + tool *discovery* /
typed-client codegen of third-party servers; **isolation/sandboxing of untrusted
external MCP servers**; Workstreams; Memory; T-023 (`auth.service-token.mint`
audit); mobile approval delivery; full per-edge rate-limiting / quotas and SSH
connection pooling (the v0.3.0 performance floor is in §10); the durability
residuals (WS-drop reconnect, broker heartbeat / active-orphan audit-close — each
needs its own ADR); the `resources.connection_secret` column drop.

The wedge is **one agent → one typed tool → policy/approval gate → connector
egress → audit chain**, end-to-end on real wires (WD-3). The full catalog and
untrusted-server isolation are deliberately *not* built here.

## 2. WD-3 — the single load-bearing wedge (the demo)

**WD-3.** A fresh installer-driven boot of the offline bundle produces a running
stack (now including `services/mcp-gateway`) that passes the following scripted
demo, end-to-end, against a real (not mocked) target resource:

1. **Agent identity.** An operator provisions an agent and the gateway mints a
   scoped **`agent-tool`** capability token (5-min TTL, audience `mcp-gateway`).
   The agent presents it; an unauthenticated/expired token is refused.
2. **Typed catalog.** The agent lists tools (MCP `tools/list`) and sees exactly
   **one** typed tool, `remote.exec`, with a typed input schema. No untrusted
   external server is exposed.
3. **Governed invocation.** The agent invokes `remote.exec` against a
   `requires_approval`-flagged resource. The gateway opens an **invocation**, calls
   policy `Decide` (passing the invocation id), and — because the resource is
   flagged — **parks the invocation** and surfaces `<ApprovalPrompt>` to the
   operator (a gateway-owned resolve surface, not a session).
4. **Approval gates the invocation.** **Deny** → the invocation is *blocked*: no
   credential is leased, no command runs, the agent gets a typed
   `denied`/permission error. **Approve** → the gateway leases the credential from
   **connector-service** and runs the command via the **broker exec path**,
   returning a typed result (stdout) to the agent.
5. **Replayable chain.** The whole path is hash-chained and replayable via
   `audit-service verify`; in canonical order the chain carries
   `tool.invoked` → `policy.decision:requires_approval` → `approval.granted` →
   `credential.leased` → the broker exec egress event (command anchored by stdout
   SHA) → `tool.result`. The denied leg carries `tool.invoked` →
   `policy.decision:requires_approval` → `approval.denied:operator` and **no**
   credential lease or egress event.

**This single demo is the release gate.** Every other criterion exists to make
WD-3 trustworthy, repeatable, and safe. WD-3 is built as an extension of the
`tests/e2e` live harness (the agent-driven exec leg, §12 / G1) plus the browser
smoke (`task smoke`) for the operator's invocation-approval UI (§7 / the DoD
addendum). It supersedes WD-2 as the v0.3.0 live demo.

## 3. Capability-edge security (must-pass)

Every boundary is gated by `packages/go/middleware` `RequireCapability` over
PASETO v4 capability tokens (ADR-0046). v0.3.0 adds:

| Edge | Decision enforced | Handler |
|---|---|---|
| `agent-tool` | The agent's right to reach the gateway + invoke a tool (audience `mcp-gateway`) | `services/mcp-gateway/internal/server` (MCP surface) |
| `service-service` (gateway → policy) | The per-invocation `requires_approval` decision + the operator-resolution relay | `services/policy-service` (existing decide/resolve; audience `policy-service`) |
| `service-service` (gateway → broker) | The non-interactive exec request (new broker exec RPC) | `services/session-broker` (new exec handler; audience `session-broker`) |
| `service-service` (broker → connector) | Just-in-time credential lease — the only decrypt path (unchanged) | `services/connector-service` (existing lease handler) |
| `human-agent` (operator) | The approve/deny verb on a **parked invocation** | `services/mcp-gateway` (resolve route, CSRF-gated) |

- **SEC-16 (block).** The `agent-tool` token is **scoped and short-lived**: a tool
  invocation outside the token's scope, or with an expired token, is refused at
  the gateway. Agents never receive operator/service tokens.
- **SEC-17 (block).** The gateway holds **no resource secret key** and has **no
  decrypt path** — connector-service remains the sole custodian (the SEC-13 grep
  gate extends to `services/mcp-gateway`).
- **SEC-18 (block).** The broker exec path enforces the **same** host-key pinning,
  capability gate, and connector-lease custody as the interactive PTY path — a
  non-interactive command is not a privilege escape hatch.
- **SEC-19 (block) — fail-closed.** A downstream outage never lets an invocation
  proceed: policy-service unreachable → invocation refused (no egress); connector
  lease failure → refused; broker exec failure → typed error. There is **no path**
  to egress without a positive policy decision *and* a successful credential lease.
  Degraded modes return typed errors to the agent, never a silent proceed.

## 4. Agent identity & token lifecycle (must-pass)

- **AG-1.** An `agent-tool` token issuance path exists (`IssueAgent` or equivalent
  in `packages/go/auth`), minting scoped tokens at the **agent TTL (5 min)** with
  audience `mcp-gateway`.
- **AG-2.** Agent provisioning is **operator-gated** — a single bootstrap agent
  identity for the wedge (analogous to the bootstrap operator), via a CLI and/or
  an operator-gated endpoint. **No** self-service agent signup, agent registry, or
  federation at v0.3.0.
- **AG-3.** Token minting + use is **audited** (`auth.agent-token.mint` / the
  per-invocation `tool.invoked` actor is `agent:<id>`).

---

## 5. Approval generalization — invocation-anchored (must-pass)

- **AP-1.** The gateway owns an **invocation** lifecycle (a row keyed on an
  invocation id). policy-service is consulted with the **invocation id in the
  `session_id` field** — which policy already treats as an opaque correlation key,
  so **no policy-service contract change** is required (verified against
  `services/policy-service/internal/server/server.go`).
- **AP-2.** A flagged invocation **parks**; an operator approves/denies it via a
  gateway resolve route (`POST /v1/invocations/{id}/resolve`, `human-agent` edge +
  double-submit CSRF). Approve → the invocation proceeds; deny → it is blocked
  (typed error to the agent). The fail-closed timeout sweeper behaviour
  (policy-service, ADR-0054) carries over unchanged.
- **AP-3.** `<ApprovalPrompt>` (the presentational `packages/ui` component, T-031c)
  is **reused** for the invocation; only the consumer plumbing (the gateway resolve
  route + an operator "pending tool invocations" surface) is new.

## 6. Audit (must-pass)

- **AUD-9 (block).** The gateway emits, via a transactional outbox (ADR-0045,
  the shared `packages/go/outbox` shape), `tool.invoked` (actor `agent:<id>`, edge
  `agent-tool`, target `tool:<name>`/`resource:<id>`, evidence `invocation:<id>`)
  and `tool.result` (outcome `success`/`error`).
- **AUD-10 (block).** The broker exec egress emits a lifecycle event anchored by
  the command's **stdout SHA256** (`evidencePacketId = sha256:<output>`), the
  non-interactive analogue of the PTY cast anchor (ADR-0048/0049).
- **AUD-11 (pass).** The full WD-3 chain (tool.invoked → policy.decision →
  approval.* → credential.leased → exec → tool.result) is **replayable and
  hash-intact** via `audit-service verify`, in canonical order. **Clarification
  (as-built):** the chain correlates one invocation across **two anchor namespaces
  by design** — the gateway + broker anchor `invocation:<uuid>` (tool.invoked,
  tool.result, remote.exec), while policy-service + connector-service anchor
  `session:<uuid>` (policy.decision, approval.*, credential.leased), **the same
  uuid** under each producer's fixed prefix. This is the deliberate opaque-key reuse
  (ADR-0054/0057) that leaves policy-service and connector-service unchanged; the
  global hash chain is single + intact regardless of anchor prefix.

## 8. Trust posture — MCP-compatible, not MCP-trusting (must-pass)

- **TR-1 (block).** At v0.3.0 the gateway exposes **only internal-facade tools**
  whose egress the platform owns (the `remote.exec` facade over connector+broker).
  It is an MCP **server**, not an MCP **client** of any third party.
- **TR-2 (deferred-to-v0.4.0, recorded).** Proxying / tool-discovery / typed-client
  generation of **external** MCP servers, and the **sandbox isolation** of
  untrusted servers (the architecture doc's "isolate untrusted servers"
  responsibility) are explicitly out of scope. **Trigger to promote:** the
  internal-facade wedge (WD-3) is green on `main` and a concrete external-server
  use case is scoped with its own ADR.

## 9. Offline install & operability (must-pass)

- **OI-10 (block).** `services/mcp-gateway` joins the offline bundle — a static
  `linux/amd64` binary + its systemd unit + its migrations + its env file entry —
  and a fresh installer-driven boot brings it `active` alongside the existing six

  **`:8085`** (after policy `:8084`); the Caddy gateway fronts the agent MCP
  endpoint same-origin. No SaaS runtime dependency (the doctrine gate holds).

## 10. Performance & resource safety (must-pass)

- **PERF-1 (block) — bounded exec.** The broker exec path enforces a **command
  timeout** and a **captured-output byte cap**; over-cap output is truncated with
  the truncation flagged, and the stdout-SHA anchor (AUD-10) is computed over the
  captured bytes. No unbounded buffering; a hung command cannot wedge the
  invocation or the agent.
- **PERF-2 (block) — idempotent invocation.** A tool invocation carries an
  idempotency key; a retried invocation (network blip / agent retry) does **not**
  double-execute the side-effecting command — it reconciles to the original
  invocation's outcome (the connector/policy `ON CONFLICT` idempotency precedent,
  ADR-0053/0054).
- **PERF-3 (pass) — per-agent concurrency cap.** The gateway bounds **concurrent
  in-flight invocations per agent** (a small fixed cap) so one agent cannot exhaust
  the broker / SSH targets. Full per-edge rate-limiting + quotas (the
  agent-permission-model "rate limits") are **deferred to v0.4.0** (trigger:
  multi-agent load).
- **PERF-4 (pass) — egress connection strategy.** v0.3.0 dials a **fresh SSH
  connection per invocation** (simple, stateless, matches the session model). SSH
  connection pooling / reuse is a **deferred** perf optimization (v0.4.0), not a
  wedge requirement — recorded so a later perf ticket has a clear baseline.

## 13. ADR dependencies (Proposed — ratified in the first authoring consult)

- **ADR-0056 — MCP Gateway protocol surface & trust boundary.** `services/mcp-gateway`
  as an **MCP server over streamable HTTP**; the JSON-RPC tool surface; `agent-tool`
  token auth (audience `mcp-gateway`); the **internal-facades-only** trust posture
  (TR-1/TR-2); and the **MCP-implementation dependency decision** (a vetted Go MCP
  library vs. a hand-rolled minimal JSON-RPC surface, weighed against the
  offline/supply-chain posture — a major dependency choice, so ADR-gated).
- **ADR-0057 — Typed tool-catalog schema + tool→capability-edge mapping +
  invocation-anchored policy/approval.** How a tool declares `{edge, target,
  action, requires_approval}`; the gateway's invocation lifecycle and its reuse of
  policy's opaque correlation id; the operator invocation-approval surface.
- **ADR-0058 (if warranted) — broker non-interactive exec contract.** The new
  service-service exec RPC (one command, captured stdout, stdout-SHA audit anchor),
  reusing host-key pinning + connector lease; keeps the broker the sole SSH egress.

## 14. Deferred → v0.4.0+ (with promotion triggers)

- Full tool catalog; external MCP-server proxying + **untrusted-server isolation /
  sandboxing**; tool discovery + typed-client codegen — **trigger:** WD-3 green +
  a scoped external-server ADR (TR-2).
- **Full per-edge rate-limiting + quotas** (beyond the §10 per-agent concurrency
  floor) and **SSH connection pooling** — **trigger:** multi-agent / sustained load.
- Workstreams; Memory — the next P1 modules (consume this gateway).
- T-023 (`auth.service-token.mint` audit) — low priority, unchanged.
- Mobile approval delivery.
- Durability residuals: WS-drop reconnect; broker heartbeat / active-orphan
  audit-close — each needs its own ADR (separate design pass).
- `resources.connection_secret` column drop (v0.2.0 §10a residual) — a cheap
  contract migration that may ride a later release.
